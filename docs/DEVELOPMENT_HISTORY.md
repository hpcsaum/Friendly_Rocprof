## 2026-07-30 — First tool: rocprof-sys CPU hotspots

Implemented the first tool per the approved plan in [docs/plans/01-rocprof-sys-hotspots.md](plans/01-rocprof-sys-hotspots.md): a quick "where's the time going, and what's still on the CPU" report for a first `rocprof-sys` profiling run, without needing the full Perfetto trace viewer.

Research into `rocprof-sys` (rocprofiler-systems, ex-Omnitrace) established that its text/JSON output only captures **host-side** timing — even rows that look like GPU work (`hipLaunchKernel`, etc.) are launch/API overhead, not real device execution time. True GPU kernel hotspots need a different tool (`rocprofv3 --stats --kernel-trace --summary`, already stable since ROCm 7.0.2) or Perfetto/rocpd trace parsing (rocpd itself isn't available before ROCm 7.1, so out of our 7.0.2 compatibility scope). Given that, this first tool deliberately scopes itself to CPU-side hotspots only — a GPU-only tool (built on `rocprofv3`) and a combined tool are planned as separate, later work.

Two pieces:
- `postprocess/rocprof_sys_hotspots.py` — standalone Python 3 (stdlib only) extractor. Parses rocprof-sys's pipe-delimited "timemory" text tables (e.g. `wall_clock-<pid>.txt`), aggregates by function name across however many files it finds (handles multiple MPI-rank files transparently), buckets entries into "CPU compute (offload candidates)" vs "GPU API/launch overhead" by name prefix, and writes a short `hotspots.txt`. Notable implementation detail: rocprof-sys's own docs describe the MPI row-prefix format as `|MM|NN>>>label`, which embeds an extra `|` inside what's conceptually one field — the parser handles this (and the similar case of hierarchy-indentation markers) generically by taking the last 11 pipe-delimited fields as the fixed numeric columns and treating everything before that as the label, rather than assuming a fixed field count.
- `scripts/rocprof_sys_profile.sh` — bash launcher wrapping `rocprof-sys-sample` (lightweight call-stack sampling, no binary instrumentation) with sane first-run defaults (flat profile, text+JSON output, Perfetto tracing off), and auto-invoking the extractor afterwards. Since `rocprof-sys-sample` wraps a single process, MPI usage is `mpirun -np N scripts/rocprof_sys_profile.sh -- ./app` (mpirun/srun goes *before* the script, not inside it) — the script detects `OMPI_COMM_WORLD_RANK`/`PMI_RANK`/`SLURM_PROCID` so only rank 0 runs the extractor against the shared output directory.

Verified locally (no ROCm/GPU available on this dev machine, per `CLAUDE.md`'s environment constraints): `python3 -m unittest` against hand-crafted fixtures under `postprocess/tests/fixtures/` (18 tests covering label-cleaning, table parsing, cross-file aggregation, GPU/CPU bucketing, and end-to-end report generation), `bash -n` on the launcher (shellcheck not installed in this environment, so that check was skipped), and manual dry-run / stubbed-`rocprof-sys-sample` runs exercising flag parsing, env var construction, and the rank-0-only summary gating. Real end-to-end validation against actual `rocprof-sys` output is left to the user on the HPC system.

## 2026-07-30 — rocprof-sys hotspots: %-of-total column, selectable output, header metadata

Extended the CPU hotspots tool with three follow-up requests:

1. **`%total` column**, computed purely from timemory data: each aggregated entry's share of a `total_runtime` denominator, itself the sum, across all scanned files, of that file's own single largest `SUM` value. A file's largest `SUM` is — barring unusual instrumentation — its outermost/root scope, since inclusive time only grows going up the call stack; this holds whether the file is a hierarchical or an already-flattened profile, without needing to guess the entry-point function's name (which the target codebase's language/build system might vary, e.g. Fortran's `MAIN__` vs C's `main`).
2. **Selectable output**: `-n/--top N` (unchanged default of 20), plus new `--threshold PCT` (only entries at/above PCT% of total runtime — falls back to showing everything, with a note, if total runtime couldn't be computed) and `--all` (no truncation), as a mutually-exclusive argparse group. `scripts/rocprof_sys_profile.sh` forwards whichever of the three the user passed through to the extractor unchanged.
3. **Best-effort header metadata** — executable name, run date/time, total runtime, and MPI rank count — read from `metadata.json` in the rocprof-sys output directory (never from the timemory files themselves, per the request). Since `metadata.json`'s schema isn't documented anywhere found during research, field lookup is a best-effort, case-insensitive search over several plausible key names (one level of nested dicts deep), with two concrete fallbacks grounded in documented rocprof-sys behavior rather than guesswork: run date/time falls back to rocprof-sys's own default output-subdirectory naming pattern (`%F_%H.%M`, e.g. `2025-01-21_07.40`) if present in the path, and rank count falls back to the number of distinct PIDs among the scanned `<component>-<pid>.txt` filenames. Any field that still can't be determined is left blank — never an error, per the request.

Extended `postprocess/tests/fixtures/mpi_2rank/` with a `metadata.json` fixture (exercising both a direct top-level key and one nested under a `settings` object) and left `single_rank/` without one, to test the all-fields-blank-plus-PID-fallback path. Added 15 new tests (33 total) covering the total-runtime computation, all three selection modes (including the threshold/unknown-total-runtime fallback), and metadata guessing with and without `metadata.json` present.

## 2026-07-31 — Second tool: rocprofv3 GPU kernel hotspots

Implemented the second tool per the approved plan in [docs/plans/02-rocprofv3-gpu-hotspots.md](plans/02-rocprofv3-gpu-hotspots.md): the GPU-kernel-only counterpart to the first tool, completing the roadmap item flagged when tool 1 was built (`rocprof-sys` never has real device execution time; `rocprofv3` does).

Research into `rocprofv3` (rocprofiler-sdk), cross-checked against the ROCm 7.0.2-tagged docs and the tool's own source on GitHub, found it considerably more straightforward to build on than `rocprof-sys`:
- `rocprofv3 --kernel-trace --stats --output-format csv -- <app>` needs no instrumentation/rebuild step, and writes a `kernel_stats.csv` whose schema was confirmed directly from the tool's source (`generateCSV.cpp`, `statistics.cpp`): `Name,Calls,TotalDurationNs,AverageNs,Percentage,MinNs,MaxNs,StdDev`. rocprofv3 also already aggregates by kernel name internally (confirmed in `generateStats.cpp`) — no per-file dedup needed on our end, unlike `rocprof-sys`'s hierarchical text tables.
- Its own default output format is `rocpd` (SQLite), not CSV — `--output-format csv` must always be passed explicitly, so the launcher hardcodes it rather than exposing it as an option.
- Default output path is `<output_dir>/<hostname>/<pid>_kernel_stats.csv` (PID-based naming avoids MPI-rank collisions the same way `rocprof-sys` does) — the extractor globs recursively (`<output_dir>/**/*_kernel_stats.csv`) to find these one level down.
- No `metadata.json`-equivalent exists for ROCm 7.0.2 — the one candidate (`--output-config` → `<pid>_config.json`) is a post-7.0.2 addition, confirmed absent from the 7.0.2-tagged docs. The header's executable/run-datetime/total-runtime fields therefore stay blank on 7.0.2 in practice; only the MPI-rank-count fallback (distinct PIDs among scanned filenames) is reliable regardless of version.

Two pieces, mirroring tool 1's shape for a consistent tool family:
- `postprocess/rocprofv3_hotspots.py` — standalone Python 3 (stdlib only) extractor. Recursively finds `*_kernel_stats.csv`, aggregates by kernel name across however many files it finds, recomputes a global `%total` (sum of that kernel's `TotalDurationNs` across files, divided by the sum of every row's `TotalDurationNs` across every file — no root-detection ambiguity here, since `kernel_stats.csv` has no call-stack hierarchy at all) and a recomputed per-call average, and writes a single-table `hotspots.txt` (no CPU/GPU split needed — this tool is GPU-kernel-only by design). Same `-n/--top | --threshold | --all` selection modes as tool 1, duplicated rather than shared, since each extractor is meant to stand alone.
- `scripts/rocprofv3_profile.sh` — bash launcher wrapping `rocprofv3` with `--kernel-trace --stats --summary --truncate-kernels --output-format csv` and auto-invoking the extractor afterward, using the same MPI pattern and rank-0-only summary gating as tool 1's launcher.

Also updated tool 1's footer note (`postprocess/rocprof_sys_hotspots.py`, plus its checked-in sample `hotspots.txt` fixtures and the corresponding test assertion) to point at `scripts/rocprofv3_profile.sh` now that it exists, instead of a raw `rocprofv3` command line.

Verified locally (no ROCm/GPU available, same constraint as tool 1): `python3 -m unittest` against new hand-crafted fixtures under `postprocess/tests/fixtures/rocprofv3_*` (22 new tests; 55 total across both tools), including one row with scientific-notation values to exercise float parsing, and a `<pid>_config.json` fixture (with one directly-keyed and one nested-under-an-object field) to test the header-guessing path. `bash -n` on the launcher (shellcheck still not installed here). Manual verification used a stubbed `rocprofv3` on `PATH` (same technique as tool 1) to confirm the missing-dependency error, dry-run command construction (`--output-format csv` always present), a full run producing a real `hotspots.txt` from copied fixture data, and rank-0-only summary gating under a simulated `OMPI_COMM_WORLD_RANK=1`. Real end-to-end validation against actual `rocprofv3` output is left to the user on the HPC system.

## 2026-07-31 — Third tool: combined CPU+GPU hotspots, double-counting-safe

Implemented the third tool per the approved plan in [docs/plans/03-combined-hotspots.md](plans/03-combined-hotspots.md): runs `rocprof-sys` and `rocprofv3` against the same command, one after the other, and merges their two separate rankings into one coherent report.

Two design problems were worked out with the user in conversation before this plan existed:

1. **The user's first idea — average the two runs' totals, rescale every entry as if its run's total were that average — is a mathematical no-op.** Rescaling every entry in a run by `k = avg/T_run` and then dividing by `avg` cancels `k` out exactly, leaving every entry's `%total` identical to what it already was pre-"combination." Two runs of very different absolute duration but the same 90%-of-their-own-total hotspot would both show 90%, indistinguishable, despite one representing far more absolute time. The fix that actually changes the outcome — and is simpler — is to use the plain sum `T_A + T_B` as one shared denominator, with no per-entry rescaling at all.
2. **`T_A + T_B` alone double-counts GPU time.** `rocprof-sys`'s CPU `wall_clock` total is inclusive of time blocked inside `hipStreamSynchronize`/`hipDeviceSynchronize`/a synchronous `hipMemcpy`, etc. — the CPU is literally waiting on the GPU during that interval, which is the same physical time `rocprofv3`'s kernel `TotalDurationNs` counts again from the device side. The fix reuses machinery `rocprof_sys_hotspots.py` already has: that tool already buckets `hip*`/`hsa*`/`roctx*`/`kfd*` entries away from its "CPU compute" bucket into a "GPU API / launch overhead" bucket. Subtracting that bucket's sum from the CPU run's raw total before adding the GPU run's total removes the double-counted wait time: `combined pool = (CPU total − GPU API/overhead) + GPU kernel total`. Accepted approximation (confirmed with the user, who noted non-blocking HIP calls are out of scope for a beginner tool): this also strips the comparatively tiny non-blocking launch overhead in the same bucket, since there's no reliable way to distinguish blocking from non-blocking HIP/HSA calls by name alone.

Per the user's explicit instruction, the extractor takes both tools' output directories as independent inputs and does **not** cross-check that they came from the same executable/test case/run — that responsibility is the caller's (garbage in, garbage out).

The user also specified the report should show four tables, not just the fused one: (1) the fused CPU+GPU ranking against the combined pool; (2) CPU compute hotspots exactly as `rocprof_sys_hotspots.py` reports them standalone; (3) GPU kernel hotspots exactly as `rocprofv3_hotspots.py` reports them standalone; (4) the GPU API/launch-overhead bucket subtracted out of table 1, so nothing is hidden and the fused numbers can be audited.

Two pieces:
- `postprocess/rocprof_combined_hotspots.py` — imports its two sibling modules directly (`import rocprof_sys_hotspots as cpu_tool` / `import rocprofv3_hotspots as gpu_tool`, relying on Python putting a directly-run script's own directory on `sys.path`) rather than duplicating their parsing logic a third time. `build_combined_view()` computes the five transparency numbers (raw CPU total, GPU-API overhead subtracted, pure CPU total, GPU total, combined pool) and the fused list; `write_report()` renders all four tables, reusing each sibling's own `select_entries`/`format_table` directly for tables 2–4 (both already generic over any list of `{"sum", "pct_total", ...}` dicts) and one new `format_table_fused()` for table 1's CPU/GPU-tagged rows.
- `scripts/rocprof_combined_profile.sh` — rather than re-implementing dependency checks and flag handling a third time, calls the two existing launchers sequentially with `--no-summary` (splitting `-o DIR` into `DIR/rocprof-sys` and `DIR/rocprofv3`), then runs the combined extractor once, rank-0-gated the same way as the other two launchers. No `set +e` around either sub-launcher call: a CPU-side failure aborts before the GPU run ever starts, since there's no single "the app ran once" exit code to forward when the app runs twice under two different profilers. `--dry-run` forwards `--dry-run --no-summary` to both sub-launchers (reusing their own tested dry-run output) rather than reimplementing it.

Verified locally (no ROCm/GPU available, same constraint as tools 1 and 2): `python3 -m unittest` reusing the *existing* fixtures from tools 1 and 2 as the two input directories — no new fixture files needed (13 new tests; 68 total across all three tools), including one test that independently recomputes the subtraction arithmetic from the same fixtures via the sibling modules' own `aggregate()` (proving the formula, not a hand-typed number) and one that pairs deliberately mismatched fixtures to confirm no cross-validation happens. `bash -n` on the launcher (shellcheck still not installed here). Manual verification used stubbed `rocprof-sys-sample`/`rocprofv3` on `PATH`: `--dry-run` correctly shows both sub-launchers' own dry-run output plus the combined-extractor invocation; a full run with both stubs copying real fixture data through produced a correct four-table report; removing the CPU stub confirmed the script aborts before the GPU sub-launcher ever runs; a simulated `OMPI_COMM_WORLD_RANK=1` confirmed the combined summary step is skipped. Real end-to-end validation against actual ROCm output is left to the user on the HPC system.

## 2026-07-31 — Fourth tool: selective instrumentation helper

Implemented the fourth tool per the approved plan in [docs/plans/04-selective-instrumentation.md](plans/04-selective-instrumentation.md): once `profile_hotspots.sh` has already identified hotspots, this tool builds a `rocprof-sys-instrument` binary rewrite covering *only* those functions — much lower overhead than instrumenting every function in the binary — and can also run the result to produce a full trace.

Research into `rocprof-sys-instrument` (cross-checked against ROCm 7.0.2-tagged docs and the tool's own source, `module_function.cpp`/`details.cpp`/`function_signature.cpp`) established several facts the design depends on directly: binary-rewrite mode (`-o <new-exe>`) is the documented/recommended mode for MPI apps, since runtime/dynamic mode's fork+ptrace is explicitly incompatible with MPI process spawning; `-R/--function-restrict <regex>` is an exclusive allow-list matched via `std::regex_search` against demangled names, so a plain function name only needs its regex metacharacters escaped, not full-signature matching; "instrument" vs. "trace" is the *same* rewritten binary, differing only in runtime env vars (`ROCPROFSYS_TRACE=1` for the full perfetto backend); and the rewrite step unconditionally writes `instrumented.json`, the authoritative post-filter list of what actually got instrumented — used here to detect "lost" functions instead of an independent heuristic like `nm`.

Two design points came directly from the user during planning, both changing the shape of the tool from an early draft:
- **MPI is driven by the script itself, not by wrapping it in `mpirun`/`srun`.** The other three tools rely on "`mpirun` wraps the whole script, once per rank, self-detected via env vars" — wrong here, since the binary rewrite must happen exactly once, never once per rank. Per the user's direction (citing the pattern used by HPE's `gbb4hpc`-style tools), this script instead takes the MPI launch command as data via `--mpi "<launch command>"` and applies it only where it's actually needed (the auto-profiling run, and `trace` mode's final run) — never to the rewrite step itself, which doesn't execute the target program at all. This is a deliberate, scoped exception to the other three tools' convention, not a change to theirs.
- **`trace` mode runs every step `instrument` mode runs, then continues one step further** — not a second pipeline that consumes a prior `instrument` invocation's output. Every `trace` call builds its own instrumented binary; there is no "run `instrument` first, then `trace`" required workflow. Both modes end by printing a ready-to-paste command for producing/reproducing a trace (`instrument` suggests the `trace` invocation that would use what it just built; `trace` echoes back the exact invocation it itself just ran).
- Also per explicit user direction: `trace` mode always exports `ROCPROFSYS_USE_ROCM=1`/`ROCPROFSYS_USE_OMPT=1`/`ROCPROFSYS_USE_MPIP=1` alongside `ROCPROFSYS_TRACE=1`, regardless of their own defaults, so the trace captures GPU kernels, OpenMP regions, and MPI calls automatically — not just the selectively-instrumented hotspot functions — since these are separate, lightweight runtime interceptors unrelated to the Dyninst rewrite itself.

Two pieces:
- `postprocess/select_hotspot_functions.py` — `labels_from_report()`/`labels_from_output_dir()` resolve a hotspot function list from either a saved `hotspots.txt` (reusing `extract_CPU_hotspots.py`'s exact table format) or a live rocprof-sys output directory (reusing `extract_CPU_hotspots.aggregate()`/`select_entries()` directly); `escape_for_instrument_regex()` builds a safe unanchored substring regex per label; `find_lost_functions()` diffs the resolved labels against `rocprof-sys-instrument`'s own `instrumented.json`; a `--check-instrumented` CLI mode reads labels from stdin and always exits 0, since a lost function is a warning, never a failure.
- `scripts/instrument_hotspots.sh` — one script, `instrument`/`trace` subcommands sharing the same build pipeline (auto-profile or `--report` → resolve labels → rewrite → lost-function check), with `trace` continuing into a final `rocprof-sys-run` step the other mode never reaches.

Verified locally (no ROCm/GPU available, same constraint as tools 1-3): `python3 -m unittest` added 25 new tests (93 total across all four tools) covering the regex escaper, both label-resolution paths against existing fixtures (including a combined report generated fresh at test time, to stay in sync with the real generator rather than a fixture that could drift), `find_lost_functions` against a hand-crafted `instrumented.json` matching the confirmed schema, and both CLI modes. `bash -n` on the launcher (shellcheck still not installed here). Manual verification used stubbed `rocprof-sys-instrument`/`rocprof-sys-run`/`rocprof-sys-sample`/`rocprofv3` on `PATH`: confirmed `--mpi` is applied to the auto-profiling and final-run commands but never to the rewrite command in the same `--dry-run` output; a full `instrument` run building a real (stubbed) instrumented binary and correctly warning about one deliberately-dropped function; a full `trace` run continuing straight into a produced trace file; `--report` short-circuiting auto-profiling entirely, with and without `--mpi` (which has no effect on that path); missing-dependency and non-existent/non-executable-binary errors for both modes. ## 2026-08-03 — Load-imbalance tables added to tools 1, 2, and 3

The user ran `profile_CPU_hotspots.sh` on the real HPC system and confirmed it already captures `MPI_*` function calls even without the launcher setting `ROCPROFSYS_USE_MPIP` explicitly — that variable defaults to `true` in rocprof-sys itself, confirming the target system's rocprof-sys build has full MPI support compiled in. Combined with an already-established fact — rocprof-sys's raw label format is `|MM|NN>>>label` (MM = rank, NN = thread) and every `wall_clock-<PID>.txt` file is already one-file-per-process — this meant a per-rank load-imbalance analysis needed no rebuild or instrumentation (tool 4's mechanism): the data was already present in tools 1-3's normal sampling output. Implemented per the approved plan in [docs/plans/05-load-imbalance.md](plans/05-load-imbalance.md).

Design decisions, made explicit during planning:
- **Rank = scanned file, not the raw `MM` digit.** Grouping by which output file a row came from (the same assumption `guess_num_ranks()` already relies on) is simpler and more robust than re-parsing `MM` out of every raw label, and needed zero changes to `clean_label()`/the existing text-table parsing.
- **A rank missing a function scores 0.0 for that rank, not skipped.** A function that only runs on some ranks (rank-dependent branching) is real, extreme imbalance and should show up, not be hidden by only averaging over the ranks that happened to call it.
- **The new table is an independent ranking by `std_dev`** (the user's explicit choice over reusing the hotspots table's already-selected entries) — a function small in total time but wildly imbalanced across ranks would otherwise never be visible. Uses the same `--top`/`--threshold`/`--all` flags already exposed by each tool; `--threshold PCT` is reinterpreted for this table only as *coefficient of variation* (`std_dev / avg >= PCT%`), since "% of total runtime" has no equivalent meaning for a std_dev ranking.
- **Fewer than 2 ranks/files scanned → skip the table**, with a one-line note, rather than showing a table comparing one rank to itself.

Implementation, in `postprocess/extract_CPU_hotspots.py` and `postprocess/extract_GPU_hotspots.py` (duplicated between the two, matching their existing stand-alone-by-design relationship): `aggregate_per_rank()` mirrors each module's own `aggregate()` file-scanning loop but keeps each file's per-label/per-kernel sums separate instead of merging across files; `compute_load_imbalance()` computes `avg`/`std_dev` (`statistics.mean`/`statistics.pstdev` — population, not sample, since every rank is captured, not a subset)/`min`/`max` per label across ranks (missing ranks scored 0.0) and applies the top/CV%-threshold/all selection described above; `format_table_load_imbalance()` renders `#, avg(s), std_dev, min(s), max(s), function|kernel`. Both modules' `write_report()` append the new table right after their existing hotspots table(s). `postprocess/extract_hotspots.py` (tool 3) adds tables 5 (CPU) and 6 (GPU) after the existing four, calling `cpu_tool`'s and `gpu_tool`'s new functions directly — exactly the "reuse tool 1 and 2's new capabilities" the user anticipated, no new statistics logic of its own. All three launchers' `-h`/`--help` text gained one sentence about the new table and a note on `--threshold`'s dual meaning; no new CLI flags were needed anywhere.

Verified locally (no ROCm/GPU available, same constraint as the other four tools): `python3 -m unittest` added 26 new tests (119 total across all four tools) — `aggregate_per_rank` returning one dict per scanned file; `compute_load_imbalance`'s avg/std_dev/min/max matching independently-computed `statistics.mean`/`pstdev` on the same known fixture values (not hand-typed decimals); a label present on only one of several synthetic ranks scoring 0.0 for the others; the CV%-threshold and top-N-by-std_dev selections; single-rank fixtures producing the skip note instead of a table; the combined report's tables 5/6 appearing after table 4 in order and matching `cpu_tool`/`gpu_tool`'s own functions called directly on the same fixtures. `bash -n` on all three launchers. Follow-up to the nested-directory fix above: the user pointed out that even after that fix, tool 1's "CPU compute hotspots" table was still dominated by functions that do nothing themselves except call the next thing down (`main`, `start_thread`, `__libc_start_call_main`, `rocprofsys_main`, `__libc_start_main`, and user wrapper functions like `solver_run`/`solver_step`/`convection_step`), plus the same MPI operation appearing 3-4 times under different internal names (`mpi_allreduce_f08ts_`, `MPIR_Allreduce_cdesc`, `PMPI_Allreduce`, `MPIR_CRAY_Allreduce`). Given the risk of this change (it alters what gets *captured*, not just how it's reported, and can't be validated against real ROCm hardware from this dev machine), the user asked for it to be done on a separate branch (`calltree`) rather than `master`.

Root-cause research (a background agent fetched AMD's `ROCm/rocprofiler-systems` docs directly from the `rocm-7.0.2` tag) found that `profile_CPU_hotspots.sh` was itself setting `ROCPROFSYS_FLAT_PROFILE=1` — a setting that **defaults to `false`** in rocprof-sys itself. Flat mode forces every row's DEPTH to 0 and merges all call-stack occurrences of a symbol into one row, which is why `% SELF` came out as `100.0` for literally every row in the real captured data: there's no way to distinguish a real hotspot from a pass-through wrapper once the call tree has been flattened. Given a choice between (a) keeping flat-profile capture and hiding pollution via a name-based block-list plus MPI-name canonicalization, (b) switching to self-time ranking on real hierarchical data, or (c) both, the user chose self-time ranking alone (b) — it fixes the *whole* problem (including the pass-through user-wrapper case a block-list can't reach), not just the system-function slice, and the MPI-duplicate problem was expected to mostly resolve itself too (only the call-tree node doing the actual blocking/communication work keeps meaningful self-time; wrapper layers around it drop toward zero and fall out of the ranking).

**Capture side:** `scripts/profile_CPU_hotspots.sh` now sets `ROCPROFSYS_FLAT_PROFILE=0` (was `1`) — real call-tree data, at the qualitative overhead cost AMD's docs mention ("flat has less overhead than hierarchical", no numbers given); a user who needs the lighter flat mode back for an overhead-sensitive run can still set the env var themselves before invoking the script.

## 2026-08-03 — Fixed the flagged `gpu_api_overhead_sec` double-count (branch `calltree`)

Follow-up to the self-time-ranking work above: the user asked to fix the `gpu_api_overhead_sec` bug that had been flagged (via `spawn_task`) as a pre-existing, out-of-scope issue during that work, rather than spinning it off separately.

`extract_hotspots.py`'s `build_combined_view()` computes the CPU-side "double-counting fix" (subtracting time the CPU spent blocked inside `hipStreamSynchronize`/`hipMemcpy`/etc. from its total before adding the GPU run's kernel total, to avoid counting that overlap twice) as `gpu_api_overhead_sec = sum(e["sum"] for e in cpu_gpu_api_entries)` — summing every GPU-API-classified row's *inclusive* time. The bug: several of those rows are themselves nested inside each other (confirmed in the real `Heat_Convection_Solver` sample data — `hipStreamCreate`/`hip::hipStreamCreate(...)`/`hip::ihipStreamCreate(...)`/`hip::Stream::Stream(...)` all show the *identical* total, i.e. one call chain measured four times, not four independent calls), so summing inclusive time across the whole bucket counts that one overlapping wall-clock interval once per nesting level.

Fixed by switching to `sum(e["self_sum"] for e in cpu_gpu_api_entries)` — self-time rather than inclusive time. This is correct by construction: every call-tree node's self-time is disjoint from every other node's (parent, child, GPU-API-classified or not), so summing self-time over any subset of nodes always recovers the real total wall-clock time spent inside that subset, regardless of how deep a matched chain nests — unlike inclusive time, which double/triple-counts exactly the overlap between a node and its also-matched ancestors. `self_sum` was only available to reach for here because of the self-time infrastructure the ranking change above just added to `extract_CPU_hotspots.py`'s `aggregate()`; this bug couldn't have been fixed this way before that. Same caveat as the parent fix: this only actually changes anything once real hierarchical data exists — on old flat-profile-captured data (`% SELF` uniformly 100), `self_sum == sum` and the bucket total is unchanged, still exhibiting the original bug's numbers.

Added a new fixture, `postprocess/tests/fixtures/gpu_api_nested_chain/`, modeling exactly the reported shape (three nested HIP-stream-creation labels, each inclusive sum 1.0s, but only the innermost holding real self-time — the outer two are ~0.1%-self pass-through wrappers) so the fix is proven end-to-end rather than just by code inspection: the old (buggy) inclusive-sum formula gives 3.0s for this fixture; the fixed self-time formula gives the correct 1.0s. `test_subtraction_arithmetic_matches_documented_formula`'s own independent recomputation of the documented formula was updated to match (it happened to still pass numerically beforehand, since every pre-existing GPU-API fixture entry has `% SELF` = 100, but its own formula would otherwise have silently verified the wrong thing).

Verified: full suite now 137 tests, all passing (136 → 137, the one new regression test). `bash -n` unaffected (Python-only change). No script/CLI changes needed — this was purely an arithmetic fix inside `extract_hotspots.py`.

**Not a two-subcommand tool like tool 4.** Tool 4 splits into `instrument` (build a rewritten binary, stop) and `trace` (build, then run) because the Dyninst rewrite is a separate, reusable, expensive artifact. `rocprof-compute` has no such build step — `rocprof-compute profile` *is* the run — so per the user's explicit choice, this is a single-mode script: find kernels → run a `-k`-filtered `rocprof-compute profile` → auto-run `rocprof-compute analyze` and surface its own output verbatim (no custom parsing needed, unlike rocprof-sys's raw text tables — `analyze` is already a human-facing summary tool).

**Skipping each kernel's first call.** The user wanted to avoid re-profiling the same kernel across every one of its iterations (overhead, and 99% redundant data), and specifically wanted to skip each kernel's *first* call (skewed by one-time first-touch/page-fault overhead, not representative of steady-state cost). This went through a real correction during research: ROCm 7.0.2's own tagged docs state "dispatch filtering is based on the *global* dispatch index of kernels in a run" — which would have required parsing rocprofv3's per-dispatch trace CSV and re-deriving global launch-order indices ourselves, a much larger and less certain feature. The user corrected this directly from their own repeated hands-on use: `-d`, combined with `-k`, actually selects the Nth occurrence *of each `-k`-matched kernel* (1-based), not a global index — docs can be stale/imprecise, direct usage wins. This collapsed the design back to its simplest form: `-k <name1> <name2> ...` (kernel names from tool 2, exactly as first designed) plus a fixed `-d 2`. Kernels dispatched only once (no second call to target) are excluded from selection entirely, per the user's own call that they're "irrelevant anyway in the optimization process" for a beginner tool. `--all-dispatches` is an escape hatch that drops `-d 2` and the single-call exclusion, printing a loud runtime-multiplication warning (a kernel called N times can multiply profiling time by roughly N) — intentionally not the default.

**MPI multi-rank safety.** `rocprof-compute`'s own per-rank output isolation (`%rank%`/`%hostname%` path placeholders, so concurrent ranks don't overwrite each other's data) is a real feature in AMD's current "latest" published docs, but research (checking `src/argparser.py` directly at every `rocm-7.x` git tag through `rocm-7.2.4`/rocprofiler-compute 3.4.0, plus the `develop`/`amd-staging` branches' current HEAD) confirmed it's absent from every publicly tagged/branched version reachable from the public repo — newer than 3.4.0, with no exact "added in version X.Y.Z" pinnable from available sources. Rather than hardcode a version-number threshold this research couldn't actually confirm, the script probes the installed tool's own capability at runtime: `rocprof-compute -v` for display, `rocprof-compute profile --help | grep -q '%rank%'` as the capability signal, and (only when `--mpi` is given) a generic rank-count probe that works for any launcher — running the user's own `--mpi` command against a trivial `echo` instead of the real app and counting how many copies come back, since any MPI launcher spawns N copies of whatever it's given. More than one rank detected with no `%rank%` support found → hard error rather than risk silent data corruption from concurrent ranks writing into the same directory; a probe that produces no output at all also aborts rather than silently assuming one rank when the true count is unknown. This check runs early (before even calling into tool 2) and even under `--dry-run`, since both probes are cheap/side-effect-free relative to the real workload and a dry-run preview should reach the same go/no-go outcome a real run would.

**New files**: `postprocess/select_hotspot_kernels.py` (GPU-kernel analog of `select_hotspot_functions.py`, substantially simpler — `rocprof-compute -k` takes plain substrings, not a regex, so no escaping logic, and no `--check-instrumented`/ground-truth-JSON equivalent exists since there's no rewrite step to verify against) and `scripts/profile_hotspot_kernels.sh`. `select_hotspot_kernels.py`'s `labels_from_output_dir()`/`labels_from_report()` both take a `require_multiple_calls` parameter (default `True`) implementing the single-call exclusion; `labels_from_report()` mirrors the CPU extractor's report-parsing technique exactly but with `maxsplit=5`/`parts[5]` instead of `maxsplit=6`/`parts[6]`, since `extract_GPU_hotspots.format_table()`'s columns are one shorter (no self-time metric).

**Deliberately out of scope for v1**, called out rather than silently skipped: no cross-check confirming a requested kernel actually got profiled (tool 4's equivalent works because `rocprof-sys-instrument` writes a ground-truth `instrumented.json`; rocprof-compute's raw per-run output schema for this isn't researched here); no custom parsing/reformatting of `analyze`'s own output.

Verified locally (no ROCm/GPU available, same constraint as every prior tool): `python3 -m unittest` added 17 new tests (154 total) covering the default single-call exclusion and its `--all-dispatches` override (both against `rocprofv3_single_rank`'s real `__hipRegisterFatBinary` row, `Calls=1` — no new fixture needed), top-N/threshold selection, the dual-format (`labels_from_report` covering both tool 2's own report and tool 3's combined report) proof, and a `maxsplit=5` column-count regression test. `bash -n` on the new script. Manual verification with a stubbed `rocprof-compute` on `PATH` (stubbing `-v`, `profile --help` with/without a `%rank%` line, and `analyze`) exercised every branch of the MPI safety gate: single rank proceeds regardless of capability; multiple ranks proceed when the stub reports `%rank%` support and abort with the documented error when it doesn't; a probe against a nonexistent launch command aborts rather than guessing (this last case caught a real bug during manual testing — `grep -c` on zero matches exits non-zero, which under `set -e` skipped the intended error message entirely and just exited silently; fixed with `|| true` on that assignment). ## 2026-08-04 — Three real-HPC-data bugs found and fixed in the combined hotspots tool

The user copied a real `profile_hotspots.sh` (tool 3) output directory from the HPC system (`Heat_Convection_Solver/profile_hotspots-output-2026-08-04_08.58.53`, 4 real MPI ranks, user-confirmed 940s rocprof-sys / 931s rocprofv3 wall-clock runtime) and asked for `extract_hotspots.py` to be re-run against it as a sanity check ("does it give the same results I have"). It didn't — and chasing down why surfaced three separate, real bugs, each found using this one real dataset, each fixed and re-verified against it before moving to the next.

**Part A — rank/sampling-metric-file dedup.** Table 5 ("CPU load imbalance") reported 12 ranks instead of the real 4, and the header's "CPU run raw total" was 11335.58s — roughly 3x the real `940s × 4 ranks = 3760s`. Root cause: rocprof-sys's default config (sampling on, set by tool 1's own launcher) writes **three** per-rank text tables, not one — `wall_clock-<N>.txt` (exact instrumented call-tree), `sampling_wall_clock-<N>.txt` and `sampling_cpu_clock-<N>.txt` (the same statistically-sampled call tree, timed two different ways). `aggregate()`/`aggregate_per_rank()` in `postprocess/extract_CPU_hotspots.py` treated every file that parsed as its own rank, so 4 real ranks × 3 metric files = 12 "ranks", and `total_runtime` summed 12 files' own maxes instead of 4 ranks'. This bug has been live since sampling was turned on by default and affects every consumer of `aggregate()`/`aggregate_per_rank()` (tools 1, 3, 4) — it was never caught by the test suite because every existing fixture only ever had one `wall_clock` file per rank.

Fixed with a new shared helper, `scan_ranks()`, replacing the near-duplicated glob-and-parse loop inside both functions: files are grouped by rank (via the same numeric-suffix regex `guess_num_ranks()` already used correctly), `sampling_cpu_clock-*.txt` is excluded outright (per the user's decision — of the two sampling views, `sampling_wall_clock` is authoritative; `sampling_cpu_clock` is an alternate measurement of the *same* intervals, not an independent contribution), and within a rank, `wall_clock`'s row for a label wins over the sampling bucket's row for that same label (closing a smaller residual double-count: ~5 labels are both explicitly instrumented and separately caught by sampling). A second issue was caught during the *same* verification pass, before the user ever saw it: merging same-labeled rows within a rank *before* picking that rank's root-scope value let a label with multiple raw rows (e.g. `start_thread`, once per worker thread) outweigh the true root (`main`) once merged, silently re-inflating the total. Fixed by computing each rank's root scope (`root_sum`) from the *raw*, pre-merge rows, with a fabricated regression fixture (multiple `worker_loop` rows summing to more than `main`'s own value) pinning it down. Re-verified against the real directory: table 5 now says "across 4 ranks"; CPU run raw total is 3794.26s (≈ 948.5s × 4, matching the user's reported figure).

**Part B — GPU-API overhead narrowed to actual sync-wait calls.** Fixing Part A exposed a second, related problem: the header's "CPU pure-compute total" clamped to `0.000000` again — the same *symptom* an earlier fix (`gpu_api_overhead_sec`, self-time not inclusive-time, see the `calltree`-branch entry above) had already addressed, but from a genuinely different cause. `build_combined_view()` summed self-time across *every* GPU-API-classified entry (`hsakmt_ioctl`, `rocr::core::BusyWaitSignal::WaitAcquire`, etc.), and on a real multi-threaded run those self-times are summed across however many concurrent threads call them — which can legitimately exceed one rank's own single-threaded wall-clock span (several threads can be blocked on the GPU at once). The user's proposed fix, in three parts: (1) narrow the table-1 subtraction to just `hipStreamSynchronize`+`hipDeviceSynchronize` self-time — the two calls that actually mean "block the CPU until the GPU catches up" — good enough for a beginner tool without the multi-thread-sum inflation; (2) table 4 keeps showing every GPU-API entry, unabridged, for anyone who wants to dig in; (3) `rocr::` (ROCm Runtime internals — `BusyWaitSignal::WaitAcquire`, `ThreadTrampoline`, `Runtime::AsyncEventsLoop`) added to `GPU_API_PREFIXES` in `extract_CPU_hotspots.py`, moving those out of tables 1/2 (where they'd been mistaken for real CPU application work) into table 4.

Implemented in `postprocess/extract_hotspots.py` (`SYNC_WAIT_LABELS = {"hipStreamSynchronize", "hipDeviceSynchronize"}`, filtering `build_combined_view()`'s sum) and `extract_CPU_hotspots.py` (the `rocr` prefix addition). New fixtures `gpu_sync_wait` and `rocr_runtime_internals`; the two existing `BuildCombinedViewTests` cases whose assumptions the old formula baked in were rewritten rather than patched (`hipStreamCreate`'s whole nested chain now correctly contributes `0.0`, not `1.0`, to the subtraction — it's a real GPU-API cost, just not a blocking sync wait). Re-verified: combined pool no longer clamps — `CPU pure-compute total: 2579.615599 sec`, `combined pool: 3780.798144 sec` — and `rocr::*` entries confirmed moved from tables 1/2 into table 4 on the real data.

**Part C — call-tree-ancestry-based thread reclassification.** With A and B fixed, `start_thread` still sat at ~200% of the CPU run's own total in tables 1/2 — the single biggest remaining distortion. Tracing the raw `wall_clock-0.txt` file found the mechanism: `main` (thread 0, ~948.4s) is the only real application thread; two *other* "threads" (1 and 3) are background threads the **HIP runtime itself** spawns as a side effect of `hipRuntimeGetVersion`/`hipStreamCreate` (almost certainly async-completion/event-polling threads) — rocprof-sys instruments their entry point (`pthread_create` → the spawned thread's own `start_thread` root, one depth deeper, in the *same* file listing), but since nothing inside them is explicitly instrumented, their entire ~948s lifetime lands under the generic label `start_thread` at 100% self. Two such full-run-length ghost threads per rank, on top of `main`'s own span, is exactly why it summed to ~200%.

Unlike `rocr::`, `start_thread` is a generic libc/pthread entry symbol — any application spawning its own real compute thread would use the exact same label, so blanket-excluding it by name would have violated `CLAUDE.md`'s own no-target-specific-assumptions principle (and the user explicitly considered and rejected doing exactly that). Fixed structurally instead, by ancestry: a thread-root row (one whose OS thread differs from its parent's, detected via a new `attach_ancestry()` depth-stack walk over `DEPTH`+file order — previously parsed by `parse_table_file()` and silently discarded) is only reclassified as GPU-API overhead if walking up its own call-tree ancestors finds a GPU-API-classified call; a thread spawned directly by real application code has no such ancestor and keeps its label-based classification untouched (a normal, non-thread-root row is *never* affected by ancestry, regardless of its ancestors — only a thread-root node's own classification can come from something other than its own label). Per the user's explicit direction, this was also built as reusable groundwork for a future real call-tree view, not a one-off hack: `attach_ancestry()` is a standalone, independently-testable utility over `parse_table_file()`'s rows, not inlined into the classification decision.

One thing the plan didn't anticipate until implementation: the same generic label (`start_thread`) can now be classified *differently* across occurrences within one rank (the HIP-spawned one vs. a hypothetical app-spawned one) — `scan_ranks()`'s and `aggregate()`'s per-label merge dictionaries were both keyed by plain `label`, which would have silently recombined exactly what ancestry just told apart. Caught via the negative-case test fixture (`gpu_spawned_thread`, modeling both a HIP-spawned and an app-spawned thread sharing the identical `start_thread` label) before it ever reached real data; fixed by switching both merge keys to `(label, gpu)`. Implemented per the approved plan, [docs/plans/09-calltree-ancestry-thread-classification.md](plans/09-calltree-ancestry-thread-classification.md). Re-verified against the real directory: `start_thread` is gone from tables 1/2 entirely (`main` correctly leads table 1 at 57.9%, not `start_thread` at ~200%) and now appears in table 4 instead, magnitude unchanged (self=7562.5s, 12 occurrences) — just correctly bucketed.

Verified locally (no ROCm/GPU available, same constraint as every prior tool): full suite grew from 154 to 173 tests across the three parts (new fixtures: `multi_metric_rank`, `gpu_sync_wait`, `rocr_runtime_internals`, `gpu_spawned_thread`; new test classes `ScanRanksMultiMetricFileTests`, `RocrClassificationTests`, `AttachAncestryTests`, `ClassifyGpuTests`, `GpuSpawnedThreadFixtureTests`), all passing; `bash -n` on all five scripts (no shell changes this round, sanity-checked anyway). Each of the three parts was re-verified end-to-end against the same real `Heat_Convection_Solver` HPC directory before moving to the next, with each regenerated report written to its own file so all versions (original, and after each fix) remain comparable on disk. Real end-to-end validation against actual ROCm/GPU hardware is left to the user, as with every prior tool.

## 2026-08-10 — GPU-specific extensions to the POP metrics tool

Looking at POP's hybrid MPI+OpenMP metrics page
(https://pop-coe.eu/further-information/learning-material/pop-standard-hybrid-metrics-for-parallel-performance-analysis)
prompted a design question: can the OpenMP-level metrics (Thread Load Balance, Serial Region
Efficiency) be adapted into GPU metrics by substituting "time on GPU" for "time in an OpenMP
parallel region"? Research conclusion: mostly no — POP's OpenMP formulas rely on per-thread
timing across a handful of persistent, comparable workers (each thread does a slice of the same
region for its whole duration), which `rocprof-sys` genuinely captures for CPU threads.
`rocprofv3` only gives per-dispatch aggregate kernel duration, not per-GPU-thread timing (a
different instrument, `rocprof-compute`'s occupancy counters), so a literal translation would
measure the wrong thing.

Three (later four) GPU-specific questions turned out to be well-posed anyway, all built on
[docs/plans/12-gpu-specific-pop-metrics.md](plans/12-gpu-specific-pop-metrics.md):

1. **GPU Offload Efficiency** (`GPU-Off`) — an Amdahl's-law-style question: how much of a rank's
   time is still CPU-only compute (serial, not-yet-ported, or not-worth-porting code)? The tool
   already computed this quantity internally (`cpu_pure` in `compute_run_metrics()`) as a step
   toward `useful_compute`, just never surfaced it.
2. **GPU Load Balance** (`GPU-LB`) — the overall `LB` already mixes GPU kernel time into the
   combined pool per rank, so imbalance *between GPUs specifically* was otherwise invisible.
3. **GPU Efficiency** (`GPU-Eff`) — the user's own framing: GPU kernel time should scale roughly
   linearly with the work assigned to it; in strong scaling, the classic failure is the per-rank
   problem size shrinking below what keeps the GPU saturated ("the GPU lost its power"). Built as
   `Computation Efficiency`'s ref/scaled ratio, restricted to just the GPU-busy-time bucket
   instead of the whole CPU+GPU pool — isolating whether it's specifically the GPU's contribution
   that stopped scaling.

**A real bug caught by validating against real data, not by a test.** All three metrics passed
their unit tests (194 → 204 total). But regenerating the real 2-rank vs. 4-rank strong-scaling
report (the same pair used to validate the base tool) showed `GPU-Off` moving the *wrong*
direction: 0.48 → 0.84 (apparently "improving") between the two runs, even though per-rank GPU
busy time stayed roughly flat and — per the user's own expectation from the raw numbers — more
of each rank's time should have looked CPU-bound going into 4 ranks. Diagnosis (dumping per-rank
`cpu_only`/`comm`/`gpu_busy`/`total` values directly): `cpu_only` compute actually *shrank*
(62s → 15s, expected under strong scaling) while `comm` nearly tripled (23s → 64s) and `total`
wall time dropped only modestly. `GPU-Off`'s formula (`1 - cpu_only/total`) normalizes against
*total* elapsed time, which includes communication — the communication blowup diluted the ratio
and made offload look artificially better, even though nothing about offload itself changed. Two
candidate fixes (normalizing against `useful_compute` instead of `total`) were tried and both
still moved the wrong way, since they were still fundamentally measuring the CPU-compute split,
not overall GPU business.

The actual fix, once correctly diagnosed: this isn't a bug in `GPU-Off`'s formula, it's a missing
*fourth* metric answering a different question. Added **GPU Utilization** (`GPU-Util` =
`max GPU busy time / max total elapsed time`) — the GPU's raw share of wall-clock time,
including any idling caused by growing communication overhead. Verified against the real data:
`GPU-Util` moved the way intuition expects (0.295 → 0.191, the GPU sat idle a larger fraction of
the time as communication grew to dominate), while `GPU-Off` correctly continued to isolate the
comm-independent CPU-compute-offload question. `gpu_busy_time` doesn't nest additively inside
`total_time` (async kernels can overlap CPU work), so `GPU-Util` is a genuinely separate
quantity, not `GPU-Off`'s complement — keeping both is more informative than picking one.
Documented in `docs/pop_metrics_reference.md`'s "Why both `GPU-Off` and `GPU-Util` exist" note,
with the real before/after numbers as the worked example.

**Follow-up polish**, both from direct user feedback: column order changed to
`LB, CommE, PE, GPU-Util, GPU-Off, GPU-LB, CompE, GE, GPU-Eff` (GPU-Util immediately before
GPU-Off), and every GPU column name gained a hyphen (`GPUOff→GPU-Off`, `GPUUtil→GPU-Util`,
`GPULB→GPU-LB`, `GPUEff→GPU-Eff`) for readability, widening the column format accordingly.

Verified: full suite grew 193 → 204 tests (no new fixtures needed — the existing
`pop_combined_2rank`/`pop_ref_2rank`/`pop_combined_mismatch` fixtures and inline metrics dicts for
`compute_gpu_efficiency()`'s isolated branches were sufficient), all green throughout, including
after the mid-course `GPU-Util` addition and the column-order/naming follow-ups. The real
2-vs-4-rank report was regenerated and re-inspected after every change. Real end-to-end validation
against ROCm/GPU hardware and a proper multi-point scaling study is left to the user, as with
every prior tool.

## 2026-08-11 — Calltree split in two: sampling-based `calltree` + `calltree_traced`

real Cray OpenACC/HIP-offload runtime frames and Fortran subroutines. Two throwaway experiments

regardless of instrumentation) shows the true structure — at the cost of an unusably noisy raw

asked for this built properly as the new default `calltree` tool, plus a `wall_clock` timing

**Four independent, real-data-confirmed noise tiers** in the new `extract_calltree.py`, each

GPU/offload-runtime noise (broadened from `startswith` to substring matching, plus new substrings

than it did against the traced tool's shallower trees.

**`WALL(s)` cross-reference column**: each rendered line's exact `wall_clock` self-time for that
label, built from a dedicated `wall_clock_self_by_rank()` (summed across every occurrence of that

Real-data testing found this column is `-` for nearly every row by design, not by bug: GOTCHA
hooks the library-level C symbol (e.g. `MPI_Isend`) while sampling unwinds through the

3 in common). Also documented a real subtlety found via the same check: since a label can recur at
multiple tree positions (e.g. one `start_thread` row per spawned worker thread), the column shows
the *same* rank-wide total on every occurrence, not a per-node-exact match — the two trees are
reconstructed independently and can't be correlated node-by-node.

**Fourth real-data-driven fix, found immediately after delivery**: the user spotted a `start_thread`
root in `calltree.txt` carrying ~88s of unfiltered self/total time per rank, despite this exact
class of noise having already been ruled out for removal (the 2026-08-04 "call-tree-ancestry thread
reclassification" fix, for the *other* tool). Traced to a real, previously-anticipated data-shape
gap: `classify_gpu_broad()`'s ancestor-walk (same idea as `extract_CPU_hotspots.classify_gpu()`)
only works when a thread-root row still has a real parent link to walk up through. In
`sampling_wall_clock`, a background HIP/ROCr event-loop thread's samples reset DEPTH to 0 for its
own OS thread — `attach_ancestry()` correctly gives it `parent=None`, same as a genuine
application-spawned root, so there's no ancestor to walk at all. Confirmed directly against the raw
file: `start_thread` (thread 3) sits at DEPTH 0, its only child is rocprof-sys's own
`pthread_create_gotcha` wrapper hop, and *that* leads straight into `rocr::os::ThreadTrampoline` and
deeper ROCm-runtime internals — exactly the pattern `GPU_API_PREFIXES`'s own `rocr` entry was added
for, just unreachable by upward-ancestry alone this time. Fixed with a new downward counterpart,
`propagate_gpu_to_untethered_thread_roots()`: an untethered root (no parent, not already
GPU-classified) walks down through any wrapper hop to its first real content, and inherits GPU
classification if that's GPU/ROCm-runtime noise — deliberately independent of
`--show-rocprofsys-internals`, so this subtree stays gated by `--show-gpu-api` alone, consistent
with every other GPU-noise block. New fixture data (a second, unrelated thread-3 root reproducing
the exact real shape) added to `calltree_sampling_filters`; suite grew to 264 tests. Re-verified
against both real directories: `start_thread` no longer appears by default, reappears correctly
under `--show-gpu-api`.

**Fifth and sixth real-data-driven fixes, both raised by the user after reviewing the delivered
`calltree.txt`.** (5) GPU kernel data was landing at the *nearest launch-call ancestor* — a purely
structural guess — even though the compiler had already told this tool exactly which subroutine
each kernel came from: Cray's OpenACC/HIP-offload kernel naming embeds the enclosing subroutine
directly in the kernel name (`<subroutine>$<module>_mod_$ck_L<line>_<n>[...]`). Checked against
real `rocprofv3` kernel names and the real CPU tree: **every** kernel's owner subroutine showed up
as its own sampled CPU node (10/10 checked). The old proportional-split logic was scattering every
kernel across every launch-call anchor in the whole rank, weighted by call count, regardless of
which subroutine actually contained it — real output showed `jacobi_sweep`'s kernel duplicated
under `convection_stable_dt`, `compute_momentum_rhs`, and every other unrelated anchor at once,
each copy scaled down and labeled "~N% estimate." Fixed by adding `kernel_owner_label()` to
`calltree_common.py` and rewriting `attach_kernel_summaries()` to try an **exact label match**
against the kernel's compiler-embedded owner first, falling back to the old nearest-launch-anchor
heuristic only for a kernel that doesn't name-match anything (no Cray-style naming, or its owner
subroutine wasn't sampled as its own frame this rank). Return contract changed from an
all-or-nothing "found an anchor" boolean to the actual subset of kernels that couldn't be placed
anywhere, so a partial name-match doesn't dump the rest into the top-level fallback section
needlessly. On the real `Heat_Convection_Solver` data this cut `calltree.txt` from 1618 to 370
lines — not from hiding anything, but from no longer duplicating the same real kernels across
every plausible anchor.

(6) The `WALL(s)` cross-reference column was "-" almost everywhere, which the user correctly
suspected was because visible nodes were being looked up by their own exact label only, while the
real wall_clock-measured time for the same underlying call often sits on a *different, hidden*
node just beneath it (rocprof-sys's own instrumentation hides the wall_clock-matching label behind
whichever filter tier applies — MPI internals collapsed, GPU-API pruned, etc.). The user's own fix:
compute the wall value before filtering, and when a line is filtered, fold its value into its
direct parent's. Implemented as a two-pass system in `extract_calltree.py`: `compute_hidden_flags()`
(a forward, pre-order pass) tags every row with whether it will render at all under the current
flags, and separately whether it hides its *entire* subtree — true for PRUNE and MPI-COLLAPSE, but
deliberately false for SPLICE, since a spliced wrapper's children are reparented and shown
normally, not hidden along with it. `fold_hidden_wall_values()` (a reverse-order pass, exploiting
that every descendant precedes its ancestor in a pre-order list) then adds each hidden row's
`WALL(s)` value into its direct parent's and clears it, cascading correctly through an arbitrarily
deep hidden chain to whichever ancestor actually renders. Confirmed against real data: `MPI_Isend`
GOTCHA-hooked self-time (10.580366s in `wall_clock`) now surfaces correctly on the visible
`mpi_isend_f08ts_` node — the Fortran binding shim sampling shows instead — despite the two labels
never matching directly.

New fixtures `calltree_sampling_mpi_cascade` (a 3-level MPI-collapsed chain with a real wall_clock
value at the bottom, pinning the cascade) plus kernel-owner-matching cases added directly to
`test_calltree_common.py`; suite grew to 271 tests, all green; the two existing fixture-based WALL
tests were updated for the new fold-inclusive expected values (the assertions changed, not just
grew, since the column's meaning materially changed). Re-verified against both real directories.

## 2026-08-11 — Cross-rank aggregation for both calltree tools; dropped `WALL(s)`

Two follow-up requests after the user reviewed the delivered `calltree.txt` from the kernel-name-
matching/`WALL(s)`-fold round above. First: **`WALL(s)` wasn't worth keeping** — even with the
fold-up fix, it stayed mostly `-` on real data (GOTCHA-hooked C symbols and the compiler-generated
wrapper names sampling shows rarely coincide), and `extract_calltree_traced.py` already provides
exact wall-clock timing as its own dedicated tool. Removed entirely from `extract_calltree.py`:
`wall_clock_self_by_rank()`, `compute_hidden_flags()`, `fold_hidden_wall_values()`, the 4th report
column, and every related caveat/help-text paragraph.

Second, and larger: **aggregate every rank into one call tree, with load-balance columns, instead
of printing one call tree per rank** — for both tools. Implemented as new shared machinery in
`calltree_common.py`:

- `merge_rank_trees(ranks)` — merges N independent per-rank trees (each rank's rows are separate
  Python objects, parsed from separate files, never the same object) into one, by walking every
  rank's tree top-down and matching children by LABEL under the already-matched merged parent —
  reliable because the same binary produces the same call structure on every rank, even though
  there's no object identity to match by. Each merged node keeps a `per_rank` dict
  (`{rank_key: {count, self_sum, sum}}`) instead of flat fields, plus a real `parent` pointer (so
  `nearest_visible_ancestor()` and friends work completely unchanged against merged nodes) and
  `gpu`/`compiler_runtime`/`mpi_territory` OR'd across every contributing rank.
- `aggregate_node_stats(per_rank, rank_keys)` — `{calls_avg, self_avg, self_std, self_min,
  self_max, total_avg}` for one node across every rank, treating a rank missing from `per_rank` as
  a genuine `0` (not omitted) — the same "missing is real, not skipped" rule
  `extract_CPU_hotspots.compute_load_imbalance()` already established for its own load-imbalance
  tables, reused here rather than reinvented. `SELF` gets the full avg/std_dev/min/max breakdown
  (matching that same precedent, which only ever does this for self-time, not inclusive time);
  `CALLS`/`TOTAL` are plain averages — a second full breakdown for inclusive time would mostly
  restate whatever a node's own children already show individually.
- `flatten_tree(roots)` — turns the merged tree back into the same flat, parent-linked row list
  shape `render_node()`/`build_children_map()`/`find_kernel_anchors()` already expect, so none of
  those rendering primitives needed to change at all.
- GPU kernel attachment (`attach_kernel_summaries()`) reworked to accept `{rank_key: {kernel_name:
  (count, total_seconds)}}` instead of one pre-combined dict, so synthetic kernel nodes keep a real
  per-rank breakdown too and get proper load-balance columns instead of a single averaged number.
  Its return contract changed from an all-or-nothing "found an anchor" boolean (already changed
  once, in the previous round) to the set of kernel *names* that couldn't be placed anywhere,
  since "per rank" no longer makes sense once there's only one merged tree.

Both `extract_calltree.py` and `extract_calltree_traced.py`'s `write_report()` were restructured
around this: `load_rank_trees()` (and, for the sampling tool, all four filter-tier tagging) is
unchanged and still runs per rank, but the old per-rank render loop is gone — `merge_rank_trees()`
runs once, `flatten_tree()` once, and rendering happens once against the merged tree. The report
header now states `ranks aggregated: N (rank keys: ...)` instead of repeating `=== Rank X ===`
per rank. `REPORT_HEADERS` (`CALLS`, `SELF-AVG(s)`, `SELF-STD(s)`, `SELF-MIN(s)`, `SELF-MAX(s)`,
`TOTAL-AVG(s)`) and a `make_node_values(rank_keys)` factory are now shared in `calltree_common.py`
too, used identically by both tools — a further DRY win beyond what either tool needed alone.

One bug caught before it reached the user: an early caveats-text draft for the traced tool still
said "SELF(s)"/"TOTAL(s)" in prose (copy-pasted from an earlier version), which happened to make a
stale test assertion pass for the wrong reason — the test was matching the CAVEATS PARAGRAPH's own
words, not the actual rendered column header (`SELF-AVG(s)`/`TOTAL-AVG(s)`). Caught by inspecting
the test failure's full report text rather than trusting a green run; fixed the caveats prose in
both tools to match the real header names, which promptly turned the test red for the right reason
until the assertion itself was updated too.

New fixture `calltree_sampling_multi_rank` (three ranks sharing one real structure with different
self-times, plus a `rare_error_path` only one rank hits, to pin the "missing rank counts as 0"
rule) plus a `MergeRankTreesTests`/`AggregateNodeStatsTests` pair testing the shared math directly;
the now-defunct `calltree_sampling_mpi_cascade` WALL-cascade fixture was deleted rather than kept
around unused. Suite is at 279 tests, all green. Re-verified against both real
`Heat_Convection_Solver` directories: `calltree.txt` shrank from 370 lines (one tree per rank) to
126 (one aggregated tree) on the same data, with real load-balance columns visible throughout (e.g.
`PMPI_Waitall`'s self-time varies 15.4s–20.9s across the 4 real ranks in `calltree_traced.txt`) —
exactly the kind of imbalance signal a single flat number would have hidden.

- `test_apps/fortran_app/` — HIP (via a `bind(C)`/`iso_c_binding` interface module calling into a

## 2026-08-12 — Real HPC build fix: OpenMP-offload link failure in `test_apps/`

The first real HPC build of `cpp_app` under `COMPILER=amd` failed at link time:

```
mpicxx main.o kernel_omp.o kernel_hip.o kernel_stdpar.o -o cpp_app -fopenmp --offload-arch=gfx942 -lamdhip64 --hipstdpar
ld.lld: error: undefined symbol: __tgt_target_kernel
```

Root cause: `__tgt_target_kernel` is an LLVM OpenMP-offload runtime symbol, defined in
`libomptarget`. Clang/amdclang only invoke the device-code linking step that pulls that runtime
in — and registers the embedded offload device image — when `-fopenmp`/`--offload-arch=...` are
present on the *final link command*, not just on the compile step that produced the object file.
All three apps' `$(TARGET)` rule linked with only `$(EXTRA_LDFLAGS)` (plus `$(STDPAR_LDFLAGS)` for
`cpp_app`) — `kernel_omp.o` was compiled with `$(OMP_OFFLOAD_FLAGS)`, but that never made it back
onto the link line, so the offload linker-wrapper never ran despite the object file compiling
cleanly. This is exactly the kind of bug `make -n` dry-running can't catch (the command syntax was
valid, it just omitted a flag) and only real HPC hardware — actually reaching the link step against
real ROCm libraries — surfaced.

Fixed identically in `test_apps/c_app/Makefile`, `test_apps/fortran_app/Makefile`, and
`test_apps/cpp_app/Makefile`: `$(OMP_OFFLOAD_FLAGS)` added to each `$(TARGET)` rule's link command,

## 2026-08-12 — Fixed a pre-existing `start_thread` distortion (generalizing plan 09)

After the fix above, the user asked why `start_thread` was still dominating `hotspots.txt`'s
table 1 (94.2% of the combined pool in `profile_hotspots_C_cray`, per plan 09's docs). Checking the
*original* captured `hotspots.txt` (saved before any change this session) showed the exact same
number — proving this predates every fix in this session, not a regression from any of them.

Root cause, traced from the real raw `wall_clock-0.txt`:
```
|0>>> |_MPI_Init                    depth=1
|0>>>   |_pthread_create            depth=2   <- spawned directly under MPI_Init
|1>>>     |_start_thread            depth=3, 100% self, lives ~the whole run
|0>>>   |_hipRuntimeGetVersion      depth=2   <- a SIBLING of pthread_create, not its parent
```
Plan 09 (`docs/plans/09-calltree-ancestry-thread-classification.md`) fixed exactly this same
"whole-lifetime dumped under a generic entry symbol" pattern for background threads the HIP runtime
spawns under `hipRuntimeGetVersion`/`hipStreamCreate` -- reclassifying a thread-root as GPU-API
overhead if its ancestry leads to a GPU-API call. Here, `pthread_create` is called directly under
`MPI_Init` instead -- almost certainly Cray MPICH's own async-progress threads -- a real data shape
plan 09 was never built against, so its HIP-only ancestry check finds nothing and these three
near-full-runtime `start_thread` rows get counted as real CPU compute.

Fixed by generalizing the same ancestry idea, not by name (per `CLAUDE.md`'s no-target-assumptions
principle, plan 09's own explicit reasoning too): a new `is_runtime_thread_noise(row)` in
`extract_CPU_hotspots.py` walks a thread-root's ancestors for an MPI-territory match, the same
structural pattern `classify_gpu()` already uses for GPU-territory. Unlike the HIP case, an MPI
progress thread has no GPU relationship at all, so it's dropped entirely in `scan_ranks()` (same
treatment as `ROCPROFSYS_WRAPPER_SUBSTRINGS`) rather than folded into the "GPU API overhead" bucket
-- mislabeling it as GPU-related would be wrong, not just imprecise. This needed `MPI_PREFIXES`/
`MPI_FORTRAN_SHIM_SUFFIXES`/`is_mpi_territory()`, which only existed in `extract_calltree.py` --
moved into the shared base module alongside `ROCPROFSYS_WRAPPER_SUBSTRINGS` for the same reason,
with `extract_calltree.py` and `extract_pop_metrics.py` now both referencing
`cpu_tool.MPI_PREFIXES` instead of their own copies, fully closing the three-independent-lists gap
Finding 4 (two changes ago) had only partially reconciled.

## 2026-08-13 — Structural (not substring) fix for the `std::pair<..._Rb_tree...>` noise

Full untruncated symbols from `functions-<rank>.json` (the rendered `.txt`/`calltree.txt` column
width truncates long C++ template signatures) confirmed the `std::pair<..._Rb_tree...>` chain from
two entries above is rocprof-sys/GOTCHA's own startup library/symbol-registration bookkeeping --
`std::set<std::string>::emplace()` of a 15-character string literal baked into rocprof-sys's own
source, `std::map<unsigned long, std::set<unsigned long>>::_M_erase()` -- byte-for-byte identical
across all 3 `amd` apps (C/C++/Fortran), proving it's independent of the profiled program's
language. Only a few frames genuinely deep inside actually match anything (`get_library`,
`create_hashtable`, `add_binding_to_tool`, `get_tool`, `lookup_exported_symbol`, `prepare_symbol` --
real GOTCHA API function names, added to `ROCPROFSYS_WRAPPER_SUBSTRINGS`); most of the chain is
generic STL container internals that don't match anything on their own, so per-label substring
filtering (this session's approach for every other noise category) can't clean it without risking a
real application's own `std::map`/`std::set` usage -- exactly what the user had already flagged as
unacceptable.

Per the user's proposal, fixed structurally instead: at any branching point (2+ rows/nodes sharing
the same parent, including top-level roots), a sibling has its *whole subtree* dropped if a wrapper
match exists anywhere within it AND at least one other sibling's subtree has none -- i.e. only when
there's a genuinely clean sibling to tell it apart from. Implemented in both tools:
`extract_CPU_hotspots.py`'s `mark_wrapper_contaminated_branches()` (flags rows, checked in
`scan_ranks()`'s existing per-row exclusion) and `extract_calltree.py`'s
`prune_wrapper_contaminated_branches()` (drops rows outright, called PER RANK before
`splice_out_wrapper_nodes()` -- order matters: splicing already removes any row whose own label
matches, which would erase the very anchor this needs to detect contamination in the first place).

Two safety bugs were caught before this was correct, both via the project's own real data and
tests, not by inspection alone:
1. **First unit-test run** caught an over-aggressive version: a sibling whose *own* label already
   matches directly (e.g. `gotcha_wrapper_call`) was being swept away wholesale, deleting real
   content legitimately nested underneath it (`real_child_under_wrapper`) that
   `splice_out_wrapper_nodes()` already correctly preserves (reparented, not deleted). Fixed by
   excluding directly-matching siblings from this function's own targeting -- it only targets a
   sibling whose own label is generic/non-matching but has a match buried inside it, the opposite
   shape from an ancestor-wrapper.
2. **Re-running against the 6 real directories** surfaced a second, more fundamental finding: one
   surviving `std::pair<..._Rb_tree_iterator<std::string>...>` node under `run_simulation` traced,
   in the raw `sampling_wall_clock-0.txt`, to a REAL ancestor of `PMPI_Allreduce -> MPIR_CRAY_
   Allreduce -> MPIDI_CRAY_Setup_Shared_Mem_Coll -> ...` -- i.e. the exact same generic label shape
   genuinely occurs in legitimate Cray MPICH internal call chains too, not only in GOTCHA's startup
   noise. The "needs a clean sibling" guard correctly left it untouched (nothing inside its subtree
   matches `ROCPROFSYS_WRAPPER_SUBSTRINGS`), which is exactly why some residual `std::pair<int,
   int>...` entries still appear in `hotspots.txt` -- not a filtering gap, but live confirmation
   that a broader, less conservative rule would have deleted real MPI-internal timing data.

Added `MarkWrapperContaminatedBranchesTests`/`WrapperContaminatedBranchFixtureTests` (a new fixture,
`tests/fixtures/wrapper_contaminated_branch/`, with a two-layer generic-noise chain to prove
cascading deletion, not just the top row) to `test_extract_CPU_hotspots.py`, and
`WrapperContaminatedBranchTests` to `test_extract_calltree.py` (extending the existing
`calltree_sampling_filters` fixture) -- both explicitly include the "directly-matching sibling with
real content must survive" case. Full suite: 303 tests, all passing. Re-ran against all 6 real
`test_apps/` directories: the dominant occurrence (previously ~39-41% of `hotspots.txt` table 1's
combined pool in `C_amd`/`CPP_amd`/`fortran_amd`) dropped to ~4-5%; `calltree.txt`'s top-level
noise branch (previously a large block of repeated templated STL frames directly under `main`) is
gone in all 3 `amd` apps. Real branches (`run_simulation`, `MPI_Allreduce`, `stencil_kernel`, the
real MPI-internal ancestor chain found above) confirmed present and untouched in all 6.
