# Plan 2.15: `extract_hotspot_callers.py` — capstone architecture validation (new, beyond the original roadmap)

> **Deferred**: do not start this plan until plans 2.13 and 2.14 are both implemented AND
> committed. `extract_hotspot_callers.py` is meant to be the first real consumer of plan 2.14's
> `stage6_cli_common.py` helpers (directory validation, `--max-depth`, `--show-*` tiers) — building
> it against those helpers only after they exist and are landed is itself part of the architecture
> test this plan is for.

## Context

The explicit goal here isn't a polished tool, it's a test: can a genuinely new report be built
almost entirely out of stage1–6 primitives that already exist, and if not, what's actually missing?
Per your direction: build the top-N-hotspots + caller-tree tool in two phases — CPU-only first,
then a GPU-aware version — and treat whatever new code each phase needs as the real deliverable
(the answer to "is the architecture solid"), not just the tool itself.

**What it shows**: the top N (default 10) CPU hotspots (same ranked table
`extract_CPU_hotspots.py` already produces), then, for each of those N functions, a "caller tree" —
the chain of ancestors from a real program root down to every distinct call site where that
function was actually reached (a function can have more than one caller in the data, so more than
one chain). This is architecturally the *inverse* of what every existing calltree tool does (walk
DOWN from roots, rendering descendants) — nothing in stage4/stage5 today answers "who called this,
all the way up to the root," which is exactly the kind of gap this exercise exists to surface.

## Phase A — CPU-only

**Reused entirely, zero new code**: `stage4_rocprofsys_flat.aggregate()` (top-N selection, via
`stage5_table_render.select_entries()`/`stage5_cpu_hotspots_table.CPU_HOTSPOTS_COLUMNS`/
`render_table()` — identical to `extract_CPU_hotspots.py`'s own table 1),
`stage5_tree_render.load_rank_trees()` (the same per-rank parsed+tagged+merged rows every calltree
tool already builds via `stage4_rocprofsys_tree.merge_rank_trees()`), `stage6_report_builder`'s
`standard_header()`/`render_report()`/`write_report_file()` (the report shape here — one numbered
section per hotspot, title = the function name — needs nothing new from that module),
`stage6_run_metadata`, `stage6_noise_config` (same tagging/filtering every other tool already gets
for free), and `stage1_run_dirs.resolve_run_dirs()`.

**The one new primitive** (the actual finding this phase is testing for): a function that, given
the merged tree's flat row list and a target label, finds every row whose label matches and walks
each one's `parent` chain up to its root, returning one ordered root→target path per distinct
occurrence (not a full descendant subtree — just the ancestor chain). Proposed home:
`stage4_rocprofsys_tree.py`, next to `merge_rank_trees()`/`find_kernel_anchors()` — it operates on
the exact same merged-row shape (`parent`, `label`, per-rank stats) those already do:
```python
def caller_chains_for_label(rows, target_label):
    """Every distinct root-to-target ancestor chain for rows matching target_label -- a function
    called from N different call sites returns N chains, each a list of rows from the real root
    down to (and including) the matching row itself."""
```
**Rendering**: a caller chain is a *linear* path, not a branching tree — no new renderer needed.
`stage5_tree_render.format_aligned_rows()` already accepts a flat list of `(label_text, values)`
tuples and handles the aligned-numeric-column layout generically; this tool just builds that list
itself (one entry per ancestor, indented by depth with a simple `└─` connector, no
`render_forest()`/`build_children_map()` needed since there's no branching to walk) instead of
calling `render_forest()`. If this turns out awkward in practice, that's itself a real finding
(maybe `format_aligned_rows()` wants a "linear chain" convenience wrapper) — worth noting either
way, not deciding upfront.

**New tool file**: `extract_hotspot_callers.py` (naming convention: named for what it shows, not
the AMD tool it wraps), one CLI arg (`output_dir`) plus `-n/--top` (default 10) and
`-o/--output`/`--extra-noise-config` via whatever `stage6_cli_common.py` plan 2.14 lands (this
tool is built after 2.14, so it's the first real consumer proving that module's helpers generalize
to a brand-new tool, not just retrofitted onto existing ones).

## Phase B — GPU-aware

Extends Phase A once it's built and reviewed: an optional second (`rocprofv3`) directory (same
`resolve_two_dirs()` pattern every CPU+GPU tool already uses), the hotspots table becomes the
*fused* CPU+GPU pool (`stage5_fused_hotspots_table.build_combined_view()` +
`FUSED_HOTSPOTS_COLUMNS` — identical to `extract_hotspots.py`'s own table 1, reused as-is), and a
top-N entry that's a GPU kernel needs its caller chain resolved differently: a kernel isn't a CPU
tree node, so its "caller" is whichever CPU call site launched it. `stage4_rocprofsys_tree.py`
already has exactly this matching logic (`find_kernel_anchors()`, `kernel_owner_label()`, built for
attaching kernel data into a rendered descendant tree) — Phase B's real test is whether that
existing matching logic can be reused/adapted to go the *other* direction (kernel → its one
launching CPU node → that node's own ancestor chain via Phase A's new function) without needing a
parallel, kernel-specific version of the whole mechanism. Whatever does or doesn't reuse cleanly
here is Phase B's actual finding.

Deferring exact Phase B design specifics until Phase A is built and reviewed, per your framing —
this section states the direction and the specific existing primitives it's expected to lean on,
not a locked implementation.

## Tests

- Phase B: same shape, extended with a kernel-anchor fixture (e.g. `calltree_kernel_anchor`,

## Phase B — detailed plan (written after Phase A, informed by its actual code)

Phase A is implemented and committed (see the divergence note at the top of this file and
[docs/DEVELOPMENT_HISTORY.md](../DEVELOPMENT_HISTORY.md)). This section replaces the sketch above
with a concrete plan grounded in Phase A's real function signatures, written before Phase B is
implemented -- not yet built.

### Context

Phase A proved the CPU-only direction needed almost nothing new. Phase B's own test is narrower and
sharper: can the *existing* kernel-attachment machinery (`stage4_rocprofsys_tree.
attach_kernel_summaries()`/`find_kernel_anchors()`/`kernel_owner_label()`/`make_kernel_node()`),
built entirely for rendering kernels as descendants in the calltree tools, be reused for the
opposite direction -- walking a kernel's caller chain *upward*, the same way Phase A's
`caller_chains_for_label()` already does for CPU functions?

**The real gap, found by reading (not guessing at) the existing code**: `make_kernel_node()` builds
a synthetic node with `label`/`per_rank`/`tags`/`structural_drop_tags`/`static_children`, but no
`parent` key -- every other row shape in this codebase carries `parent` (that's what
`caller_chains_for_label()` walks), but a synthetic kernel node has never needed one, since
`render_forest()`/`get_children()` only ever walk *down* through `static_children`, never back up.
`_attach_kernel_group()` (the function that actually builds and wires in these synthetic nodes)
never sets `parent` either. This is exactly the kind of gap Phase A's exercise exists to surface --
the mechanism is *almost* reusable, but was quietly built one-directional.

### Design

**1. Give synthetic kernel nodes a real `parent` link (additive, backward compatible).**
- `make_kernel_node(label, per_rank, parent=None)` -- new optional param, defaulting to `None` so
  every existing call site (both inside `_attach_kernel_group()` and
  `stage5_tree_render.attach_and_render_gpu_kernels()`'s own "no anchor" fallback-table construction)
  is unaffected unless it opts in.
- `_attach_kernel_group()` sets it where it already has the values in scope: the group wrapper node
  (`"[GPU kernels -- rocprofv3]"` or its multi-anchor percentage-estimate variant) gets
  `parent=anchor`; each individual per-kernel-name leaf node gets `parent=group_node`. No other
  logic in that function changes.
- Nothing downstream reads `parent` off these nodes today, so this cannot change any existing
  rendered output -- verified by the full suite staying green unchanged, and by real-data
  regeneration of both calltree tools' reports staying byte-identical.

**2. Let the caller collect the synthetic nodes it just created.**
- `attach_kernel_summaries(rows, gpu_kernel_by_rank, is_pruned, collect_into=None)` -- new optional
  param. Whenever a group node (and its per-kernel-name children) gets attached to an anchor, if
  `collect_into` is not `None`, append the group node and every one of its kernel leaves to it, in
  addition to wiring them into `anchor["static_children"]` as today. `collect_into=None` (every
  existing caller) changes nothing.
- `stage5_tree_render.attach_and_render_gpu_kernels(flat, gpu_per_rank, gpu_dir, rank_keys,
  is_pruned, node_values, collect_into=None)` gains the same param, threaded straight through to
  `attach_kernel_summaries()` -- so `extract_hotspot_callers.py` can call this *exact* existing
  function (same one both calltree tools already call), passing `collect_into=flat`, instead of
  re-deriving `gpu_kernel_by_rank`/looping ranks itself.

**With (1) and (2) done, no new tree-walking primitive is needed at all.** Once
`attach_and_render_gpu_kernels(flat, gpu_per_rank, gpu_dir, rank_keys, is_pruned, node_values,
collect_into=flat)` has run, every attached kernel's synthetic leaf node is a real member of `flat`,
carrying a real `parent` chain up through the group node to its anchor to the root -- so Phase A's
own `caller_chains_for_label(flat, kernel_name)` finds it and walks it unchanged. A kernel attached
at more than one anchor (the proportional-split case) naturally yields more than one leaf node with
that label, so `caller_chains_for_label()` already returns one chain per site, exactly like a CPU
function called from multiple call sites. A kernel `attach_kernel_summaries()` couldn't place
anywhere (`still_unattached`) never gets a node appended to `flat`, so
`caller_chains_for_label(flat, kernel_name)` correctly returns `[]` -- the same "no caller chain
found" message Phase A already prints, no new fallback text needed either.

**3. Fused hotspot pool, only when a GPU directory resolves.**
- New optional second positional CLI arg `gpu_dir` (`nargs="?"`, default `None`), resolved via
  `stage1_run_dirs.resolve_two_dirs(output_dir, gpu_dir)` -- the same optional-GPU-pairing shape
  `extract_calltree.py`/`extract_calltree_traced.py` already use (unlike `extract_hotspots.py`,
  which *requires* its GPU side; this tool's GPU side stays optional, matching the calltree tools'
  own convention, since Phase A's CPU-only report is still a complete, useful report on its own).
  `stage6_cli_common.require_directories([cpu_dir, gpu_dir])` replaces Phase A's single
  `require_directory()` call -- already `None`-tolerant, no new helper needed (this is the exact
  case plan 2.14 built `require_directories()` for).
- When `gpu_dir` resolves: swap `stage4_rocprofsys_flat.aggregate()`'s bare `cpu_entries` for
  `stage5_fused_hotspots_table.build_combined_view(cpu_dir, gpu_dir)`'s `fused_entries` (already
  "domain"-tagged `"CPU"`/`"GPU"`, double-counting-corrected `pct_total`) and swap
  `CPU_HOTSPOTS_COLUMNS` for `FUSED_HOTSPOTS_COLUMNS` for that table's rendering -- both reused as
  literally the same objects `extract_hotspots.py` already uses for its own table 1. Threshold
  wording and `pct_total` basis switch to `combined_total_sec`, mirroring `extract_hotspots.py`'s
  own `_prepare_pct_total()` helper (small enough it can stay inlined here, like it does there,
  rather than becoming a fifth stage6_cli_common-style shared helper for a single reuse site).
- When `gpu_dir` is `None`: table, columns, entries, and every existing code path stay *exactly*
  Phase A's -- this is a strict superset, not a rewrite. `extract_hotspot_callers.py`'s existing
  Phase A tests must keep passing completely unchanged.
- Run-info/header: merge `cpu_tool.gather_run_info()` and `gpu_tool.gather_run_info()` the same way
  `extract_calltree.py` already does (CPU's own metadata preferred, GPU's fills in only what CPU
  didn't have), and add a second `("GPU run directory", gpu_dir)` entry to `standard_header()`'s
  `directories` list when present.

**4. Per-hotspot caller-chain loop.** For each selected entry: if `entry.get("domain", "CPU") ==
"GPU"`, look it up in `flat` (now containing the attached synthetic kernel nodes from step 2) via
`caller_chains_for_label(flat, entry["label"])` -- literally the same call Phase A already makes
for a CPU function, no branching needed inside that function at all. The only real branch is
*building* `flat` with kernels attached (once, before the loop) versus not, depending on whether
`gpu_dir` resolved.

### Open questions this plan deliberately leaves for implementation, not silently decided

- **GPU-API noise around kernel-anchor resolution**: `find_kernel_anchors()`/`attach_kernel_summaries()`
  take an `is_pruned` predicate (used by `nearest_visible_ancestor()` to skip past pruned frames when
  picking an anchor). Phase A builds no `is_pruned` at all (it has nothing to prune -- noise removal
  there is purely splice-based). Phase B needs *some* `is_pruned` to pass in; the plan's default is
  `stage3_rocprofsys.make_is_pruned({"gpu_api"})`, matching every other tool's default-hidden
  behavior, with no new `--show-gpu-api` flag in this first cut (deferred, not decided against
  permanently).
- **A GPU kernel name colliding with a real CPU function label**: theoretically possible, not
  handled specially -- the same assumption `merge_rank_trees()`/every calltree tool's kernel
  attachment already makes implicitly. Not worth engineering around unless real data ever shows it.
- **Section title wording** for a GPU-domain hotspot's caller-chain section (e.g. whether to say
  "kernel" explicitly) is left to implementation, not locked in here.

### Tests

- `MakeKernelNodeTests`/`AttachKernelSummariesTests` additions in `test_stage4_rocprofsys_tree.py`:
  `parent` defaults to `None` and is set correctly when given; `collect_into` gathers exactly the
  group node + every kernel leaf, in the same order they're attached; omitting `collect_into` changes
  nothing (existing tests already cover this implicitly by continuing to pass unchanged).
- A new fixture-driven test proving the actual point of Phase B: build a small merged tree with a
  named-owner-matched kernel and a structurally-anchored (fallback) kernel, run
  `attach_kernel_summaries(..., collect_into=flat)`, then call
  `caller_chains_for_label(flat, kernel_name)` directly and confirm the chain ends in the kernel
  and passes through the expected anchor -- this is the test that actually validates "no new
  tree-walking code was needed."
- End-to-end `extract_hotspot_callers.py` tests using `calltree_kernel_anchor`/
  `calltree_kernel_multi_anchor` fixtures (already used by the existing calltree tools' own tests):
  a GPU-domain top-N entry gets a real caller chain ending in the kernel's own name; a
  `calltree_kernel_no_anchor`-style fixture confirms "no caller chain found" for an unplaceable
  kernel; CPU-only invocation (no `gpu_dir`) stays byte-identical to Phase A's own existing tests.
