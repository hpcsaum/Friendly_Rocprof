# Plan 2.15: `extract_hotspot_callers.py` — capstone architecture validation (new, beyond the original roadmap)

> **Deferred**: do not start this plan until plans 2.13 and 2.14 are both implemented AND
> committed. `extract_hotspot_callers.py` is meant to be the first real consumer of plan 2.14's
> `stage6_cli_common.py` helpers (directory validation, `--max-depth`, `--show-*` tiers) — building
> it against those helpers only after they exist and are landed is itself part of the architecture
> test this plan is for.

## Context

The explicit goal here isn't a polished tool, it's a test: can a genuinely new report be built
almost entirely out of stage1–6 primitives that already exist, and if not, what's actually missing?
Per your direction: build the top-N-hotspots + caller-tree tool in two phases — CPU-only first,
then a GPU-aware version — and treat whatever new code each phase needs as the real deliverable
(the answer to "is the architecture solid"), not just the tool itself.

**What it shows**: the top N (default 10) CPU hotspots (same ranked table
`extract_CPU_hotspots.py` already produces), then, for each of those N functions, a "caller tree" —
the chain of ancestors from a real program root down to every distinct call site where that
function was actually reached (a function can have more than one caller in the data, so more than
one chain). This is architecturally the *inverse* of what every existing calltree tool does (walk
DOWN from roots, rendering descendants) — nothing in stage4/stage5 today answers "who called this,
all the way up to the root," which is exactly the kind of gap this exercise exists to surface.

## Phase A — CPU-only

**Reused entirely, zero new code**: `stage4_rocprofsys_flat.aggregate()` (top-N selection, via
`stage5_table_render.select_entries()`/`stage5_cpu_hotspots_table.CPU_HOTSPOTS_COLUMNS`/
`render_table()` — identical to `extract_CPU_hotspots.py`'s own table 1),
`stage5_tree_render.load_rank_trees()` (the same per-rank parsed+tagged+merged rows every calltree
tool already builds via `stage4_rocprofsys_tree.merge_rank_trees()`), `stage6_report_builder`'s
`standard_header()`/`render_report()`/`write_report_file()` (the report shape here — one numbered
section per hotspot, title = the function name — needs nothing new from that module),
`stage6_run_metadata`, `stage6_noise_config` (same tagging/filtering every other tool already gets
for free), and `stage1_run_dirs.resolve_run_dirs()`.

**The one new primitive** (the actual finding this phase is testing for): a function that, given
the merged tree's flat row list and a target label, finds every row whose label matches and walks
each one's `parent` chain up to its root, returning one ordered root→target path per distinct
occurrence (not a full descendant subtree — just the ancestor chain). Proposed home:
`stage4_rocprofsys_tree.py`, next to `merge_rank_trees()`/`find_kernel_anchors()` — it operates on
the exact same merged-row shape (`parent`, `label`, per-rank stats) those already do:
```python
def caller_chains_for_label(rows, target_label):
    """Every distinct root-to-target ancestor chain for rows matching target_label -- a function
    called from N different call sites returns N chains, each a list of rows from the real root
    down to (and including) the matching row itself."""
```
**Rendering**: a caller chain is a *linear* path, not a branching tree — no new renderer needed.
`stage5_tree_render.format_aligned_rows()` already accepts a flat list of `(label_text, values)`
tuples and handles the aligned-numeric-column layout generically; this tool just builds that list
itself (one entry per ancestor, indented by depth with a simple `└─` connector, no
`render_forest()`/`build_children_map()` needed since there's no branching to walk) instead of
calling `render_forest()`. If this turns out awkward in practice, that's itself a real finding
(maybe `format_aligned_rows()` wants a "linear chain" convenience wrapper) — worth noting either
way, not deciding upfront.

**New tool file**: `extract_hotspot_callers.py` (naming convention: named for what it shows, not
the AMD tool it wraps), one CLI arg (`output_dir`) plus `-n/--top` (default 10) and
`-o/--output`/`--extra-noise-config` via whatever `stage6_cli_common.py` plan 2.14 lands (this
tool is built after 2.14, so it's the first real consumer proving that module's helpers generalize
to a brand-new tool, not just retrofitted onto existing ones).

## Phase B — GPU-aware

Extends Phase A once it's built and reviewed: an optional second (`rocprofv3`) directory (same
`resolve_two_dirs()` pattern every CPU+GPU tool already uses), the hotspots table becomes the
*fused* CPU+GPU pool (`stage5_fused_hotspots_table.build_combined_view()` +
`FUSED_HOTSPOTS_COLUMNS` — identical to `extract_hotspots.py`'s own table 1, reused as-is), and a
top-N entry that's a GPU kernel needs its caller chain resolved differently: a kernel isn't a CPU
tree node, so its "caller" is whichever CPU call site launched it. `stage4_rocprofsys_tree.py`
already has exactly this matching logic (`find_kernel_anchors()`, `kernel_owner_label()`, built for
attaching kernel data into a rendered descendant tree) — Phase B's real test is whether that
existing matching logic can be reused/adapted to go the *other* direction (kernel → its one
launching CPU node → that node's own ancestor chain via Phase A's new function) without needing a
parallel, kernel-specific version of the whole mechanism. Whatever does or doesn't reuse cleanly
here is Phase B's actual finding.

Deferring exact Phase B design specifics until Phase A is built and reviewed, per your framing —
this section states the direction and the specific existing primitives it's expected to lean on,
not a locked implementation.
