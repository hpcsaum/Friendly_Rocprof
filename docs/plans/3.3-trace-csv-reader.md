# Plan 3.3: `stage1_rocprofsys_trace.py` — full-fidelity trace-CSV reader + parent-link resolution

## Context

Roadmap step 2 of `docs/plans/3.1-trace-postprocessing-family.md`'s implementation sequence — the
first genuinely new module (no existing file touched). Reads the flat per-rank trace-CSV
(established this session against real Perfetto data: `pid, process_name, tid, thread_name,
slice_id, parent_slice_id, depth, name, category, ts, dur` as core columns, plus a long, sparse
tail of GPU-arg columns populated only on some rows) and resolves the call-tree links Perfetto
already computed.

**Corrected scope boundary** (this plan initially got this wrong, corrected directly): stage1+2
keeps every CSV column intact — no dropping `tid`/`pid`/`depth`, no carving GPU-arg columns into a
separate sub-dict, no renaming `name`→`label`, no synthesizing `count`/`self_sum`. Producing the
exact shape `stage4_rocprofsys_sample_tree.merge_rank_trees()` needs (label, count, sum, self_sum)
is **stage4's job** (a later plan, `stage4_rocprofsys_trace_tree.py`) — matching this project's
own existing split, where a stage4 module's whole charter is "merge ranks... creates the
tree/table" and stage1/stage2 for the *existing* text-table format already work this way too
(`stage1_rocprofsys_sample.parse_table_file()` happens to output `label`/`count`/`sum`/`self_sum`
directly only because the raw timemory table already has that exact shape natively — not because
shaping data for stage4 is stage1's job in general).

**Two explicit decisions confirmed directly**:
- `self_sum` derivation (needs children durations, i.e. needs a tree) is stage4's
  responsibility, not this plan's — it's squarely "shape data for `merge_rank_trees()`."
- Unit conversion (`ts`/`dur` nanoseconds → seconds, matching every other stage's seconds
  convention) **does** happen here in stage1 — a lossless, reversible normalization, not a loss of
  information, and worth doing once rather than leaving every future consumer to remember the raw
  CSV is in nanoseconds.

## Approach

### `postprocess/stage1/stage1_rocprofsys_trace.py` — two functions

**`parse_trace_csv(paths)`** — `paths` is a single path or list of paths (normalized to a list
immediately; multi-file input supports the confirmed "single full CSV OR the complete
category-partitioned set for one rank" shape from plan 3.1 — rows from multiple files are simply
concatenated, in the order given, since resolution below is by `slice_id`, never by position).
Reads via stdlib `csv.DictReader` (no pandas — stdlib-only per `CLAUDE.md`). Per row:
- **Every column from the CSV header becomes a key on the row dict, unfiltered** — `pid`,
  `process_name`, `tid`, `thread_name`, `name`, `category`, and every GPU-arg column
  (`grid_size`, `corr_id`, `workgroup_size`, ...) pass through exactly as the CSV gave them (empty
  string → `None`, otherwise left as a raw string — no attempt to parse `grid_size`'s
  `"(256,1,1)"`-shaped values or similar; that's a future plan's job when it actually needs them).
- **Minimal, non-interpretive type handling**, only for the columns this module's own logic
  needs: `slice_id`/`parent_slice_id` → `int` (empty → `None`) since stage2's lookup below needs
  them as real dict keys; `ts`/`dur` → `float`, divided by `1e9` (ns → seconds) per the confirmed
  decision, **stored back under the same `ts`/`dur` keys** — not renamed to `sum`, since that
  mapping is stage4's job.
- `depth`, `tid`, `pid` and every other column: passed through untouched, no coercion attempted —
  nothing in this module needs them as anything but opaque values to preserve.
- Skip a row (matching `stage1_rocprofsys_sample.parse_table_file()`'s existing skip-on-bad-row
  precedent) only if `ts`/`dur` fail to parse as numbers at all — not on any other column being
  missing/empty, since sparse columns are expected and normal.

**A real, worth-documenting consequence of "preserve columns as given" + multi-file concatenation**:
if a partitioned set's files have genuinely different headers (e.g. a GPU-only export carrying
extra columns an MPI-only export never had at all), rows from different source files in one
combined list can have different key sets. Documented explicitly as standing behavior — a
consumer should use `.get()`, never assume every row has every key, which is already how
`merge_rank_trees()`/`tag_rows()` read rows today (`row.get("tags", set())`, etc.).

**`attach_ancestry(rows)`** — mutates in place, returns `rows` (same signature shape as the
existing `stage2_rocprofsys_sample.attach_ancestry()`, for parity). Purely link resolution, no
derived statistics:
1. Build `by_slice_id = {row["slice_id"]: row for row in rows}`.
2. For each row: `parent_slice_id is None` → `row["parent"] = None` (a legitimate untethered root
   — e.g. a `rocm_kernel_dispatch` row on its own GPU-queue track, not nested in any CPU thread's
   tree). `parent_slice_id` set but not found in `by_slice_id` → the **partial-input case**: also
   `row["parent"] = None`, but collected for one summary warning (not per-row), matching
   `stage4_rocprofsys_sample_tree.pair_gpu_per_rank()`'s existing warning style:
   `warning: N row(s) reference a parent_slice_id not present in the given data -- treating as new
   roots rather than guess a parent (pass the complete category-partitioned file set, or the
   single unfiltered CSV, for this rank to avoid this)`

`parent_slice_id` itself stays on the row (not removed just because `parent` now exists — "keep
data intact" applies here too). The caller computes `roots = [r for r in rows if r["parent"] is
None]` itself — one line, same as today's `load_rank_trees()` does for the existing format;
`attach_ancestry()` doesn't return a second value, keeping its signature identical in shape to the
existing stage2 function.

**No children-map, no self_sum, no count/label synthesis anywhere in this file** — building the
children-by-parent map and deriving `self_sum` from it belongs entirely to the later
`stage4_rocprofsys_trace_tree.py` plan, once it has both `parent` links (from here) and needs to
produce a `merge_rank_trees()`-shaped node. Nothing in this plan anticipates that logic.

### Docstring

Standard scope/functions/philosophy convention. States explicitly: this module preserves every
CSV column, does no domain-specific renaming/derivation, and both `label` mapping and
`count`/`self_sum` computation are deliberately left to whichever later stage actually needs that
shape (naming it: a later `stage4_rocprofsys_trace_tree.py`) — not because they're hard, but
because deciding what a "count" or "self time" even means for a given consumer is that consumer's
job, not the parser's. Also states category→tag tagging, cross-rank merging, multi-rank file
discovery, and `corr_id`-based kernel correlation are out of scope here.

### Tests — `postprocess/tests/stage1/test_stage1_rocprofsys_trace.py`

Verified by direct read of every existing `tests/stage1-4/test_*.py` file: all of them use
`importlib.util.spec_from_file_location` (not a plain `from stageN_x import y`) — the new test
file follows that actually-universal convention.

- `ParseTraceCsvTests`: every CSV column present on the returned rows (spot-check a GPU row keeps
  `grid_size`/`corr_id`, a non-GPU row has them as `None`, nothing dropped); `slice_id`/
  `parent_slice_id` come back as `int`/`None`; `ts`/`dur` come back correctly converted to seconds;
  single-path input and list-of-paths input on the same data produce the same rows; partitioned
  files concatenate to the same combined row set a single unfiltered file would give (allowing for
  the documented differing-key-sets caveat above).
- `AttachAncestryTests`: multi-level `parent` chain resolves to real object references; an
  untethered root (`parent_slice_id` empty) gets `parent = None` with no warning; the partitioned-
  3-files case resolves identically to the single-file case; the deliberately-partial-file case
  (GPU file only, no siblings) fires exactly one warning (captured via `contextlib.redirect_stdout`)
  and the affected row becomes a root instead of crashing.

**New fixtures** under the shared `postprocess/tests/fixtures/` (scenario-named, matching e.g.
`mpi_2rank`/`calltree_kernel_anchor`):
- `trace_single_rank/rank0.csv` — small multi-level tree: `main`(root, `host`) →
  `jacobi_sweep`(`ompt`) → [`hipLaunchKernel`(`rocm_hip_api`, `corr_id=42`, populated
  `blockDimX`/`gridDimX`), `MPI_Barrier`(`mpi`)]; plus `jacobi_kernel`(`rocm_kernel_dispatch`, own
  root, `corr_id=42`, populated `grid_size`/`workgroup_size`) — a normal tree, an MPI leaf, and a
  `corr_id`-bearing HIP-launch/kernel-dispatch pair (not joined here — that's a later plan; this
  fixture just needs the columns present and preserved).
- `trace_partitioned_rank/rank0-gpu.csv` + `rank0-mpi.csv` + `rank0-other.csv` — the same rows
  split by category, to verify concatenation + resolution matches the single-file case.
- `trace_partial_gpu_only/rank0-gpu.csv` — just the GPU rows, no siblings, to verify the
  missing-parent warning path.

### Explicitly out of scope for this plan

Label/count/self_sum derivation, `corr_id`-based kernel-to-launch-site join, category→tag mapping,
cross-rank merge orchestration, multi-rank file discovery/glob, on-disk aggregate caching — all
later plans. This plan produces full-fidelity, ancestry-linked rows and nothing shaped for any
particular downstream consumer.
