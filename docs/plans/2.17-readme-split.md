# Split README.md into a beginner-facing user guide + a developer-facing postprocess/ architecture doc

## Context

`README.md` (409 lines) currently mixes two audiences in one document: simple "what do I run and
what do I get" usage instructions, and deep implementation rationale (the CPU+GPU double-counting
arithmetic, the exact 4-tier noise-filtering mechanism and its substring lists, the two-tier
Cray-name-match-vs-structural-fallback kernel-attachment algorithm, the `rocprof-compute` MPI
safety-check mechanism). It's also stale: `extract_hotspot_callers.py` (added in plan 2.15) isn't
documented at all, the "Layout" section still describes the old flat `postprocess/` (pre-plan-2.16
reorg), and `--extra-noise-config` (added in plan 2.12, now on 6 tools) is never mentioned anywhere.

This plan splits it into:
1. **`README.md`** (rewritten in place) — simple, direct, per-tool descriptions for a beginner who
   has never used `rocprofv3`/`rocprof-sys`/`rocprof-compute`: what each script/tool does, why
   you'd reach for it, how to run it, what it produces. No implementation rationale.
2. **`postprocess/README.md`** (new) — the workflow philosophy (raw rocprof output → comprehensible
   report) and the `stage1`-`stage6` pipeline architecture, for a developer extending or debugging
   the post-processing tools. This is where the deep mechanism explanations trimmed out of #1 move
   to, reframed as current-state architecture description, not development history (no plan
   numbers, no "used to"/"this replaces" framing — that belongs in `docs/DEVELOPMENT_HISTORY.md`,
   per this project's own established `CLAUDE.md` convention, already followed throughout every
   prior plan this session).

`docs/pop_metrics_reference.md` already exists as a similar deep-reference doc and needs no
restructuring — just a link from `postprocess/README.md` alongside the existing link from
`README.md`.

## `README.md` (rewritten) — structure

- Title + 1-paragraph project description (kept close to today's), trimmed "Layout" section
  (`scripts/` = launchers, `postprocess/tools/` = the report generators described below, pointing
  to `postprocess/README.md` for anyone who wants the architecture).
- One section per **launcher script** (`profile_CPU_hotspots.sh`, `profile_GPU_hotspots.sh`,
  `profile_hotspots.sh`, `instrument_hotspots.sh`, `profile_hotspot_kernels.sh`): what it's for in
  plain language, the non-MPI + `--mpi` usage examples, what file(s) it produces, the
  user-relevant flags (`--top`/`--threshold`/`--all`, `--unfiltered`, `--max-depth`,
  `--extra-noise-config`, `--all-dispatches`) stated as *what they do*, not *why they're built that
  way* — e.g. "combines CPU and GPU timing into one ranking, correcting for the overlap between
  CPU-side GPU-wait time and GPU-side kernel time" instead of today's explicit
  `combined pool = (CPU total − GPU API/overhead) + GPU kernel total` arithmetic walkthrough;
  "hides internal/runtime noise by default, `--show-*` flags reveal it" instead of the 4-tier
  substring-list breakdown; "kernel data is attached to the CPU code that launched it, when it can
  be determined" instead of the Cray-`$ck_`-naming-vs-structural-fallback explanation.
- One section per **standalone post-processing tool** not covered above:
  `extract_calltree.py`/`extract_calltree_traced.py` (already covered similarly, trimmed the same
  way), **`extract_hotspot_callers.py` (new — currently undocumented)**, `extract_pop_metrics.py`
  (keep practical usage + the "not every POP metric is computable, see
  [docs/pop_metrics_reference.md]" pointer; drop the GPU-extension formula details into that
  existing reference doc's own territory, not restated here).
- Every standalone tool's direct-invocation command line included (`python3
  postprocess/tools/extract_X.py ...`), matching today's convention.
- Explicitly current-state only: no mention of plan numbers, "added in", or past designs.

## `postprocess/README.md` (new) — structure

- **Philosophy**: one section framing the whole pipeline's job — turning raw per-rank
  `rocprof-sys`/`rocprofv3` text/CSV files into a comprehensible report — as a layered pipeline
  where each stage owns exactly one transformation and stages compose freely, so a new report tool
  is mostly assembly, not new parsing/rendering code (this is the actual point plan 2.15's capstone
  tool validated — described here as a standing architectural fact, not as "plan 2.15 proved").
- **The `stage1`-`stage6` pipeline**, one subsection per stage naming its real files and what it
  owns (scope, not history), e.g.:
  - `stage1/` — parsing raw `rocprof-sys`/`rocprofv3` output into row/entry dicts, plus
    run-directory resolution (`stage1_rocprofsys.py`, `stage1_rocprofv3.py`, `stage1_run_dirs.py`).
  - `stage2/` — attaching parent/ancestry links, turning flat parsed rows into a real call-tree
    shape (`stage2_rocprofsys.py`).
  - `stage3/` — noise classification: tagging rows via JSON-defined patterns
    (`default_noise_patterns.json`, user-overridable — see stage6) plus generic tag-driven
    tree-surgery primitives (splice/remove/collapse/prune) — classification and treatment are
    deliberately separate (`stage3_rocprofsys.py`).
  - `stage4/` — aggregation: flat by-label merging for ranked tables vs. tree-shaped merging for
    call-tree tools, rocprofv3's own GPU-kernel aggregation, and the shared rank-statistics math
    (`stage4_rocprofsys_flat.py`, `stage4_rocprofsys_tree.py`, `stage4_rocprofv3.py`,
    `stage4_rank_merge_math.py`).
  - `stage5/` — table/tree rendering: column specs, ranking/selection/threshold logic, text
    alignment/wrapping, and each tool's own "view" glue module
    (`stage5_table_render.py`/`stage5_tree_render.py` + the `stage5_*_table.py`/
    `stage5_calltree*_view.py` files).
  - `stage6/` — report assembly: the shared header/footer/section shape every report uses
    (`stage6_report_builder.py`), best-effort run-metadata guessing (`stage6_run_metadata.py`),
    the user-facing noise-pattern override system (`stage6_noise_config.py`,
    `default_noise_patterns.json`), and the shared CLI argument-handling helpers every tool's
    `main()` uses (`stage6_cli_common.py`).
  - `tools/` — the 9 CLI entry points; each is a compose-and-print script over the stages above.
- **Cross-stage import graph + `_stage_paths.py`**: state as fact (not "we moved files") that the
  import graph is intentionally cross-cutting (a report tool typically touches most stages), so
  every stage/tools directory is mutually importable via the shared `_stage_paths.py` bootstrap —
  point to that module's own docstring rather than re-explaining the mechanism in full here.
- **Two subsystems worth a deeper look** (real complexity a future developer needs, currently only
  explained in scattered docstrings/comments): the noise-classification tag system (JSON schema,
  splice-vs-prune-vs-collapse actions, the `--extra-noise-config` diff format) and the
  kernel-to-CPU-launch-site attachment algorithm (name-match via Cray's embedded subroutine naming,
  falling back to nearest-launch-call structural estimate) — both stated as current mechanism, with
  pointers to `stage3_rocprofsys.py`/`stage6_noise_config.py` and `stage4_rocprofsys_tree.py`
  respectively rather than duplicated in full.
- **Building a new tool**: short, concrete guide pointing at the actual reusable entry points a new
  `tools/extract_X.py` would compose — `stage1_run_dirs.resolve_run_dirs()`/`resolve_two_dirs()`,
  `stageN_rocprofsys_flat.aggregate()`/`stage5_table_render.select_entries()`/`render_table()` for
  a flat ranked table, `stage5_tree_render.load_rank_trees()`/`stage4_rocprofsys_tree.
  merge_rank_trees()` for a call-tree tool, `stage6_report_builder.standard_header()`/
  `render_report()`/`write_report_file()` for assembly, and `stage6_cli_common`'s
  `add_selection_args()`/`add_max_depth_arg()`/`require_directory(ies)()`/`resolve_dest()` for the
  argparse boilerplate every tool shares.
- **Tests**: brief note that `tests/` mirrors this same `stageN/`/`tools/` layout with a shared
  `tests/fixtures/` directory, and the two module-loading conventions in use (plain `from stageN_x
  import y` after the `_stage_paths` bootstrap for most stage-module tests; `importlib.util.
  spec_from_file_location` for tool-level tests, since tools are meant to be run as scripts).
- Link to `docs/pop_metrics_reference.md` for the POP-metrics-specific math.
