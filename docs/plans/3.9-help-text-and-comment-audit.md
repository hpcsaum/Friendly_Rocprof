# Plan 3.9: help text + final comment/docstring audit + README updates

## Context

Plan 3.1's original implementation roadmap table (`docs/plans/3.1-trace-postprocessing-family.md`)
enumerated its own last step as "3.8: help text + final comment/docstring audit" -- jargon-free
`HELP_BLURB` + Perfetto doc link for each of the 3 new trace tools, plus a sweep of every
new/moved/renamed file from this whole `3.x` effort for `CLAUDE.md`'s Code Comments rules, mirroring
`docs/plans/2.13-comment-docstring-audit.md`'s identical audit for the `2.x` consolidation. Since
that plan number got used instead for a real bug fix found while smoke-testing plan 3.7's tools
(`docs/plans/3.8-kernel-owner-reanchoring.md`), this roadmap-closing step becomes plan 3.9 -- the
last item in the `3.x` trace-postprocessing-family roadmap.

Also folds in a related gap found while scoping this: neither `README.md` nor
`postprocess/README.md` mentions any part of the `3.x` trace pipeline at all yet (confirmed by
direct read of both, in full) -- both need updating to cover the new tools/modules, per explicit
request.

Two Explore agents swept every new/renamed file from the `3.x` effort against `CLAUDE.md`'s Code
Comments rules and the `HELP_BLURB` convention. Findings below; two of the "possible violations"
they flagged didn't survive a check against this codebase's own established precedent and are
recorded as such rather than acted on.

As expected: plan 3.8 itself wrote investigation-narrative prose directly into several docstrings
while diagnosing the kernel-anchoring bug against real data -- exactly the category
`docs/plans/2.13-comment-docstring-audit.md` already found and fixed once for the `2.x` family.

## Findings: flagged-but-not-actioned (checked against established precedent, found compliant)

- **`extract_trace_calltree.py`/`extract_wallclock_calltree.py` `HELP_BLURB` length**: one audit
  agent flagged these as too long (50 and 39 non-blank lines) against a baseline of the simplest
  existing tools (`extract_CPU_hotspots.py`=14, `extract_GPU_hotspots.py`=11). Checked directly
  against the actual closest precedent instead -- `extract_calltree.py`, the sample-pipeline
  calltree tool these two mirror -- and it's already 40 lines long itself, following the same
  house pattern: a short (7-10 line), jargon-free LEAD paragraph (confirmed for all three: 7-10
  lines each), followed by additional technical paragraphs for the caveats a calltree tool
  genuinely has more of than a flat hotspots table, ending with the required AMD-tool+link line.
  `CLAUDE.md`'s rule requires the *lead* to be short and jargon-free, not the whole blurb -- all
  three already satisfy that. No change needed.
- Likewise `extract_trace_hotspots.py`/`extract_trace_pop_metrics.py`'s total lengths (15 and 22
  lines, 4 paragraphs each) essentially match their own closest precedents
  (`extract_hotspots.py`: 16 lines/4 paragraphs; `extract_pop_metrics.py`: 20 lines/4 paragraphs)
  almost exactly. No change needed.

## Approach

### Comment/docstring fixes

For each finding in the table above: rewrite the flagged text in place, stating the current
standing fact/invariant/limitation directly, dropping the investigation-narrative or plan-pointer
language -- same discipline `docs/plans/2.13-comment-docstring-audit.md` already used, file-by-file
so each diff reviews as a coherent whole. Comment-only changes; no logic touched.

### README updates

- **`README.md`**: add a new "Trace-based tools" section (after the existing per-tool sections,
  before "Customizing noise filtering"), mirroring the established per-tool style (name, one
  paragraph description, usage code block, key caveats) for `extract_trace_hotspots.py`/
  `extract_trace_calltree.py`/`extract_trace_pop_metrics.py`, plus a short note that these read a
  trace-mode run already converted from its raw Perfetto `.proto` output to the flat CSV files
  these tools expect (a separate, user-run conversion step, out of scope for this project's own
  code) -- produced by *any* `rocprof-sys` trace-mode run (`ROCPROFSYS_TRACE=1`), not just this
  project's own `instrument_hotspots.sh trace` (one convenient way to get one, already documented
  above it, but not the only source) -- matching the wording `extract_trace_calltree.py`'s own
  module docstring already uses for this same point.
- **`postprocess/README.md`**: needs more than new bullets -- the `stage4` write-up has drifted
  out of date on the architecture itself, not just missing the trace pipeline. Confirmed by direct
  read: it still attributes `merge_rank_trees()`/`caller_chains_for_label()`/etc. to
  `stage4_rocprofsys_sample_tree.py`, but plan 3.5 already split those (plus `flatten_tree()`/
  `aggregate_node_stats()`/`make_node_values()`/`kernel_owner_label()`) out into
  `stage4_rocprofsys_common.py` specifically so both the sample and trace tree pipelines could
  share them -- the same common/format-specific split `stage3`'s write-up already documents
  correctly for `stage3_rocprofsys_common.py`, but `stage4`'s write-up never caught up to.
  - Fix the stale "9 CLI entry points" count to 12 in "Layout".
  - Rewrite the `stage4` subsection's opening framing to name the common/specific split explicitly
    (mirroring `stage3`'s own opening paragraph), add a `stage4_rocprofsys_common.py` bullet
    (the shared merge/flatten/stats engine + `kernel_owner_label()`, consumed by both
    `stage4_rocprofsys_sample_tree.py` and the new `stage4_rocprofsys_trace_aggregate.py`), and
    correct the existing `stage4_rocprofsys_sample_tree.py` bullet to only claim what it actually
    still owns (`load_rank_trees()`, `pair_gpu_per_rank()`, `attach_gpu_kernels()`/
    `attach_kernel_summaries()`) now that the generic engine has moved out.
  - Add the new trace-side modules to the `stage1`/`stage3`/`stage4`/`stage5` subsections:
    `stage1_rocprofsys_trace.py`, `stage3_rocprofsys_trace.py`,
    `stage4_rocprofsys_trace_aggregate.py`/`_flat.py`/`_tree.py`/`_ranks.py` (including the
    on-disk `.agg.json` per-rank cache, `get_rank_aggregate()`), and `stage5_trace_calltree_view.py`
    -- matching each subsection's existing per-module bullet style.
  - Fix the "stage4 → stage5 entry contract" section's "tree node" shape entry, which still says
    "Produced by `stage4_rocprofsys_sample_tree.merge_rank_trees()`" -- same stale attribution,
    now `stage4_rocprofsys_common.merge_rank_trees()`, shared by both pipelines.
  - Add a paragraph to "Kernel-to-CPU attachment" describing the trace pipeline's own mechanism
    (exact `corr_id` join, then owner-name-and-time reanchoring when that join lands on a shared
    generic entry point) right alongside the existing two-tier sample-pipeline description, for
    contrast -- referencing `_attach_kernels_by_corr_id()`/`_reanchor_kernels_by_owner_and_time()`
    in `stage4_rocprofsys_trace_aggregate.py`.

approved above (same violation category, or the same "stage4 architecture drifted out of date"
issue), just not individually itemized in the findings table:

- `stage4_rocprofsys_trace_ranks.py`'s own module docstring (lines 6-9, just above the flagged

  its flagged neighbor.

  re-anchoring as plain "name-based owner match," which undersold plan 3.8's actual mechanism
  (name match refined by the trace's own per-thread timestamps) -- corrected for accuracy while
  fixing the same paragraph's flagged history language.
- `postprocess/README.md`'s "flat entry" and "per-rank timing summary" shape-attribution bullets
  had the identical staleness as the flagged "tree node" bullet (missing the trace-pipeline
  producer entirely) -- fixed all three together rather than just the one named.
- `postprocess/README.md`'s "`tools/` — the CLI entry points" section had its own separate stale
  "9 files" count (distinct from the "Layout" one already flagged) -- fixed to 12, and a one-line
  note added to "Building a new tool" pointing at the trace pipeline's equivalent modules, since
  that section was written before the trace pipeline existed and never mentioned it at all.

None of these change the approach approved above -- they complete the same two fixes (the comment
audit, the stage4 architecture correction) more thoroughly than the itemized list alone would have.
