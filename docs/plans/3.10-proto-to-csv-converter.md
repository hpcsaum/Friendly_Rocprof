# Plan 3.10: rocprof-sys Perfetto `.proto` → trace-CSV converter

## Context

Every plan in the `3.x` trace-postprocessing family so far (3.1 through 3.9) has explicitly
deferred the `.proto`→CSV conversion step as "a separate, user-run tool, out of scope" — the
existing real trace data this project has tested against was converted by hand, with no repeatable
tool or documented process. This plan closes that gap: a new tool that converts a rocprof-sys
output directory's per-rank Perfetto `.proto` trace files into the flat CSV format
`postprocess/`'s trace pipeline already consumes, so the whole pipeline (plans 3.3–3.9) has a real,
repeatable first step instead of relying on however the existing test data happened to get made.

Design grounded in direct source reads, not documentation guesses: the actual Perfetto C++ source
(a full checkout exists locally at `/home/saumet/Documents/perfetto`) was read to confirm the exact
`trace_processor_shell` CLI contract and SQL schema, and the real production CSV files already in
`Heat_Convection_Solver/instrument_hotspots-trace-output-.../` were read to confirm the exact target
schema this tool must produce. A Plan agent cross-checked the design against this project's own
code and flagged one real gap (an operational note, folded in below) plus several concrete
implementation choices (also folded in). This surfaced one genuinely new, non-obvious correctness
risk (below) that a docs-only reading would have missed entirely.

**User's rules, as given, with one mid-design revision**:
1. Output must respect the format the current `postprocess/` workflow can directly consume.
2. Default run generates the three partitioned files (`-gpu`/`-mpi`/`-other`) — revised from an
   initial "default = unfiltered file" framing once research showed the real unfiltered file lacks
   `corr_id` and every GPU-arg column entirely, which would silently disable GPU-kernel-to-
   launch-site attachment if it were the default. The plain unfiltered file stays available as an
   opt-in extra (confirmed with the user) rather than being dropped.
3. The tool isn't responsible for obtaining/managing Perfetto's tooling itself — it locates an
   already-installed `trace_processor_shell` via a CLI argument and/or environment variable.
4. Input is a rocprof-sys directory with per-rank `.proto` files. A separate `merged.proto` (the
   whole-run merged trace) coexists in a real output directory and must be ignored entirely. No
   cross-rank coherence checking (missing files, mismatched runs) is performed.

## Verified technical design

### Target CSV schema (confirmed against real production files + this project's own parser)

Base 11 columns, always present, in this exact order:
`pid,process_name,tid,thread_name,slice_id,parent_slice_id,depth,name,category,ts,dur`.
`ts`/`dur` are nanoseconds; blank cells are empty CSV fields (`stage1_rocprofsys_trace.py`'s own
`v if v else None`). The real `-gpu.csv` partition additionally carries ~60 sparse, data-dependent
GPU-arg columns (`corr_id`, `blockDimX`, `grid_size`, ...) — confirmed by reading this project's own
stage1–4 code that only `corr_id` is ever read by name; everything else passes through unused. This
tool must emit whatever dynamic args a rank's data actually has, not a hardcoded ~60-key list, and
**computes each output file's arg-column header independently** (only `-gpu.csv` is expected to
have any in practice, but `-mpi.csv`/`-other.csv` get whatever's actually there, never an assumed
empty set).

Output file naming must satisfy `stage4_rocprofsys_trace_ranks._RANK_FILE_RE`
(`r"-(\d+)(?:-(gpu|mpi|other))?\.csv$"`): given input `perfetto-trace-<N>.proto`, write
`perfetto-trace-<N>.csv` (unfiltered, opt-in) and/or `perfetto-trace-<N>-{gpu,mpi,other}.csv`
(default). Category → partition-bin bucketing happens **in Python, via
`stage3_rocprofsys_trace.tag_for_category()`** (imported directly, not re-derived in SQL) — this
guarantees the three files' row counts always sum exactly to a full unfiltered fetch, the same
invariant `docs/DEVELOPMENT_HISTORY.md` already recorded as verified for the real data.

### `trace_processor_shell` invocation (confirmed from the actual C++ source)

`trace_processor_shell -Q "<SQL>" <proto_file>` — `-Q`/`--query-string` runs a query given directly
as a string (no temp file needed, simpler than `-q`/`--query-file`). Output is CSV to stdout:
quoted header, unquoted numbers, quoted strings. One subprocess invocation per (rank × query) —
confirmed better than one joined query, since joining the args table onto the base slice query
would multiply base rows once per arg (needing de-duplication anyway); two clean queries (base
slices, then args) with one pivot step in Python is simpler.

**Critical, easy-to-miss correctness detail** (found only by reading `shell/query.cc`'s
`ExtractQueryResult()` directly): a SQL `NULL` prints as the literal 7-character string `"[NULL]"`,
not an empty cell. Copied naively, every genuinely-NULL cell (e.g. `tid` on a GPU kernel-dispatch
slice with no owning thread) becomes the literal string `[NULL]` — truthy in Python, silently
breaking `stage1_rocprofsys_trace.py`'s blank-handling. This tool's CSV-parsing step must convert
any cell exactly equal to `[NULL]` back to an empty string before writing its own output.

### SQL query design (confirmed from the actual stdlib SQL source)

```sql
-- base slices (always run)
SELECT
  process.pid AS pid, process.name AS process_name,
  thread.tid AS tid, thread.name AS thread_name,
  slice.id AS slice_id, slice.parent_id AS parent_slice_id, slice.depth AS depth,
  slice.name AS name, slice.category AS category, slice.ts AS ts, slice.dur AS dur
FROM slice
LEFT JOIN thread_track ON slice.track_id = thread_track.id
LEFT JOIN thread ON thread_track.utid = thread.utid
LEFT JOIN process_track ON slice.track_id = process_track.id
LEFT JOIN process ON COALESCE(thread.upid, process_track.upid) = process.upid
ORDER BY slice.id;

-- args (only run when the caller wants the partitioned trio, i.e. by default)
SELECT slice.id AS slice_id, args.flat_key AS flat_key,
       args.int_value AS int_value, args.string_value AS string_value, args.real_value AS real_value
FROM slice JOIN args ON slice.arg_set_id = args.arg_set_id;
```

A slice's track is either a `thread_track` (→ `thread` → `process`) or a `process_track` (→
`process` directly, no thread) — **confirmed against real data**: GPU kernel-dispatch rows have
`pid`/`process_name` populated but blank `tid`/`thread_name`, so both track kinds must be
`LEFT JOIN`ed and coalesced on `process.upid`, never assuming every slice has an owning thread.
`args.flat_key` (not `key`, which can carry array-index suffixes) names each dynamic-arg column;
exactly one of `int_value`/`string_value`/`real_value` is non-null per row, picked in Python. A
`(slice_id, flat_key)` pair appearing more than once (an array-valued arg collapsing under one flat
key) resolves first-value-wins with one aggregate warning across the whole rank — mirroring
`_attach_kernels_by_corr_id()`'s own "more than one match, don't guess, warn once" convention.

### Locating `trace_processor_shell`

Mirrors `stage6_noise_config.py`'s existing `--extra-noise-config`/`$FRIENDLY_ROCPROF_NOISE_CONFIG`
override pattern (not the bare `command -v` pattern `scripts/*.sh` use for ROCm-module binaries,
since `trace_processor_shell` is a separately-obtained Perfetto tool, not something `module load
rocm` provides, and this project's real target — an HPC cluster — likely has no general internet
egress for the tool's own auto-download-on-first-run behavior). Precedence: `--trace-processor PATH`
CLI arg → `$FRIENDLY_ROCPROF_TRACE_PROCESSOR` env var → `shutil.which("trace_processor_shell")` →
`shutil.which("trace_processor")` (the Python wrapper script some installs use, which just
`execv`s straight to the real binary, so it takes identical arguments) → clear `SystemExit` with an
actionable message if none resolve, matching this project's own documented convention (`CLAUDE.md`:
"external tool dependencies explicit and checked at script startup, with a clear error if
missing").

### Input discovery

Generic `_PER_RANK_PROTO_RE = re.compile(r"-(\d+)\.proto$")` glob over the given directory (mirrors
`_RANK_FILE_RE`'s own "prefix isn't guaranteed, suffix is the convention" design) — this excludes
`merged.proto` for free (no trailing `-<N>`), plus one explicit, redundant
`if os.path.basename(path) == "merged.proto": continue` to document that the exclusion is
deliberate, not incidental. No coherence checking across ranks (per rule 4) — each matched file is
converted independently.

### Noted, not solved here

- Perfetto's own convention for a slice still open when trace capture ended is `dur == -1`; this
  whole codebase has no existing special-case for it anywhere (confirmed by search) — a
  pre-existing gap in the pipeline generally, not something specific to this tool. Passed through
  unchanged, with one comment acknowledging it.
- Choosing the default (partitioned trio) over the unfiltered file specifically preserves exact
  GPU-kernel-to-launch-site correlation out of the box — the tool's own `--help` text says this
  explicitly, so a user who only skims "partitions are the default, unfiltered is an extra" doesn't
  miss that the extra `--unfiltered` flag produces a file with reduced downstream fidelity, not just
  a smaller one.

**Confirmed with the user**: stays a Python tool under `postprocess/tools/` (not bash) —
category-partition logic reuses `stage3_rocprofsys_trace.py`'s `_CATEGORY_TAG_MAP` directly with no
duplication, and gets real unit tests with hand-crafted fixtures matching this project's existing
convention for data-transformation code, rather than the syntax-check-only convention bash scripts
get. Explicitly **out of scope for this plan**, noted for later: the user wants an eventual
`scripts/*.sh`-style launcher chaining the whole pipeline (rocprof-sys trace → this tool → one of
the `extract_trace_*.py` tools), mirroring how `instrument_hotspots.sh` already wraps its own
underlying tools — not part of this plan's work.

## Approach

### New: `postprocess/tools/convert_trace_to_csv.py`

Functions: `discover_proto_ranks(proto_dir)` (the input-side counterpart to `discover_ranks()`,
same shape: numeric sort, `SystemExit` on zero matches); `add_cli_argument(parser)` /
`resolve_trace_processor(args)` (the locate-the-binary logic above — local to this module, since no
other tool needs it); `_run_trace_processor(trace_processor_path, proto_path, sql)` (the one
subprocess-invoking function, and the one function tests mock); `_parse_trace_processor_csv(stdout_text)`
(pure parsing + the `"[NULL]"` fixup — the one function tests feed canned text into directly);
`write_unfiltered_csv(rows, dest)`; `write_partitioned_csvs(rows, args_by_slice_id, dest_dir, rank_stem)`
(buckets via `tag_for_category()`, per-file dynamic header, first-wins + warn on duplicate arg keys);
`convert_rank(proto_path, dest_dir, trace_processor_path, emit_unfiltered)`; `main()`. Follows this
project's established CLI shape (`stage6_cli_common` where applicable: `require_directory()`)
even though this tool doesn't build a stage6 report.

CLI: positional `proto_dir`; `-o`/`--output-dir` (default: same directory); `--unfiltered` (also
emit the plain combined file per rank); `--trace-processor PATH`. `-h`/`--help` follows `CLAUDE.md`'s
convention: jargon-free purpose+limitation lead, closing with the AMD/Perfetto tool name + doc link
(https://perfetto.dev/ for `trace_processor`, https://rocm.docs.amd.com/... for rocprof-sys itself).

## Divergences noted during implementation

- No separate `_fetch_base_rows()`/`_fetch_args_by_slice_id()` wrapper functions were added --
  `convert_rank()` calls `_run_trace_processor()` + `_parse_trace_processor_csv()` directly for
  each of the two queries; the extra indirection didn't earn its keep for two straight-line calls.
- `resolve_dest()`-style output handling wasn't reused as such, since `-o`/`--output-dir` names a
  directory this tool writes several files into, not one report file the way every other tool's
  `-o` does; `main()` just resolves it to `args.output_dir or args.proto_dir` and creates it if
  missing.

Neither changes anything about the approach approved above.
