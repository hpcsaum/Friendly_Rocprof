# Plan 2.11: §10 rule 6 — 120-column hard-wrap + `iter_table_rows()` reader (roadmap step 9, part 2 of 2)

## Context

Plan 2.10 applied `docs/plans/2.1-postprocess-consolidation-refactor.md` §10's report style guide
rules 1–5 and 7 across all 6 report tools, splitting out rule 6 (the 120-column hard-wrap for long
names, plus the `iter_table_rows()` reader it requires) into this follow-up, since it independently
touches two renderers and both `select_hotspot_*.py` re-parsers. Plan 2.10's own real-data
verification confirmed the problem is real and current: "Real HPC data's long C++ template names
visibly break table alignment in the calltree views" — a long, uncut label either drags every
other row's column alignment out of shape (tree view, where label width is shared across the whole
block) or runs past any reasonable terminal width unbroken (hotspots tables, where the trailing
label column is deliberately unpadded/untruncated today).

Rule 6 (`docs/plans/2.1-postprocess-consolidation-refactor.md` line 984) and its addendum (lines
987–1030) already specify the target design in detail, including a worked `iter_table_rows()`
sketch — this plan adapts that sketch to this codebase's actual module boundaries (the addendum's
`report_builder.py` split into `stage5_table_render.py`/`stage6_report_builder.py` back in plan
2.7; the addendum itself already anticipated this and named `stage5_table_render.py` as the
"module that will own the writing side of the same wrap").

## Approach

### 1. `stage5_table_render.py` — a standalone `wrap_trailing_label()`, reused by `render_table()`

Every stage-5 table module (`stage5_cpu_hotspots_table.py`, `stage5_gpu_hotspots_table.py`,
`stage5_fused_hotspots_table.py`, `stage5_load_imbalance_table.py`) ends its column spec in exactly
one unpadded `width: None` column (the function/kernel name) — confirmed by direct read of all
four. `stage5_pop_metrics_table.py`'s columns are all explicitly widthed (no `width: None` column
at all), so it's naturally unaffected by this change without any special-casing.

Per your request, the wrap/cap logic is its own standalone function next to `render_table()`, not
inlined inside it — so a future stage-5 table module with this same "fixed columns, then one
unpadded trailing label" shape can call it directly, without having to route through
`render_table()`'s own column-spec machinery at all:

```python
def wrap_trailing_label(prefix, label, width=120):
    """Formats one row whose line already begins with `prefix` (everything printed before the
    label -- e.g. "  1  12.340000  10.0  ...  ") and ends in an unpadded trailing label. Returns
    the row as a single string (1+ physical lines joined by "\\n"): unchanged
    (`prefix + label`) if it already fits in `width` columns; otherwise hard-wrapped -- a raw
    character-level cut, no word-boundary search, so concatenating every chunk back together
    reconstructs `label` exactly -- with each continuation line indented by len(prefix) spaces so
    it lines up exactly under where the label itself started (never flush-left). The 20-column
    floor on the available width guards against a pathological prefix that alone already exceeds
    `width` (none do today; a defensive minimum, not a real code path).
    """
    if len(prefix) + len(label) <= width:
        return prefix + label
    available = max(width - len(prefix), 20)
    chunks = [label[i:i + available] for i in range(0, len(label), available)]
    indent = " " * len(prefix)
    return "\n".join([prefix + chunks[0]] + [indent + c for c in chunks[1:]])
```

`render_table()` computes each row's own `prefix` exactly as it does today (indent + every column
before the last, joined the same way), then calls `wrap_trailing_label(prefix, label)` instead of
directly concatenating — for a label that fits, this is byte-identical to today's output (keeps
`test_width_none_column_is_unpadded_trailing` green unchanged).

### 2. `stage5_tree_render.py` — a standalone `wrap_leading_labels()`, reused by `format_aligned_rows()`

Here the label is the *leading* column (tree text + connector), with numeric columns following, and
`label_width` today is `max(len(text) for text, _values in data_rows)` — exactly the "one long
label drags every row's alignment" bug rule 6 names. Unlike the trailing-label case, capping this
width is inherently a whole-block decision (every row shares one `label_width`), not a per-row one
— so the reusable unit here is a function over the whole row set, extracted the same way, next to
`format_aligned_rows()`:

```python
def wrap_leading_labels(rows, suffix_width, width=120):
    """Caps and hard-wraps the leading label column for a block whose numeric columns come AFTER
    it (suffix_width = the fixed width of everything printed after the label, e.g.
    sum(2 + col_width for each numeric column)). Returns (label_width, wrapped_rows):
    label_width is the one column width every row's label is padded to -- the longest real label,
    capped so label + suffix_width never exceeds `width` columns, which is what stops a single
    pathologically long label from dragging every other row's alignment wider (the 20-column floor
    is the same defensive minimum as wrap_trailing_label()'s). wrapped_rows is `rows` with each
    (text, values) data row's text replaced by a list of 1+ label fragments -- a character-level
    cut, so concatenating every fragment in order reconstructs the original label exactly -- only
    the first of which carries `values`; marker rows (values is None) pass through untouched, and
    every row's tuple shape (chunks_or_text, values) is otherwise unchanged.
    """
    data_rows = [r for r in rows if r[1] is not None]
    available = max(width - suffix_width, 20)
    label_width = min(max((len(text) for text, _values in data_rows), default=0), available)
    wrapped = []
    for text, values in rows:
        if values is None or len(text) <= available:
            wrapped.append((text if values is None else [text], values))
            continue
        chunks = [text[i:i + available] for i in range(0, len(text), available)]
        wrapped.append((chunks, values))
    return label_width, wrapped
```

`format_aligned_rows()` calls `wrap_leading_labels(rows, numeric_suffix_width)` once up front
(`numeric_suffix_width = sum(2 + width for _name, width, _fmt in headers)`, the same expression it
already needs for the header line), uses the returned `label_width` for the header line and every
row's padding, and for each data row prints its first chunk (padded to `label_width`) with that
row's numeric cells, then any further chunks flush left with no numeric suffix — correct here
because this column already starts at column 0, so "flush left" and "aligned under where the label
started" are the same position (unlike `wrap_trailing_label()`'s case, where they're different).
For every row already under the cap, this is byte-identical to today's output (keeps
`format_aligned_rows()`'s existing tests green unchanged) — marker rows (e.g. "N more node(s)
hidden") pass through untouched, same as today.

Both functions get their own `width=120` default (no shared import between the two files) — same
"small constants duplicated across standalone/near-standalone modules" convention already used
elsewhere in this codebase (e.g. `SYNC_WAIT_LABELS`) rather than inventing a shared config module
for one integer.

No tree-output consumer exists to need a reader here: only `select_hotspot_functions.py`/
`select_hotspot_kernels.py` re-parse report text, and both read the *flat hotspot tables* (rendered
by `render_table()`), never calltree output — confirmed by reading both files. So this half of rule
6 needs a writer only, not a reader.

### 3. `stage5_table_render.py` — new `iter_table_rows(lines, num_columns)` reader

Placed next to `render_table()`, per the addendum's own note. Adapts the addendum's pseudocode,
parameterizing `NUM_COLUMNS` (the addendum's sketch hardcoded one; this codebase's two real
consumers need 7 and 6 respectively):

```python
def iter_table_rows(lines, num_columns):
    """Yields each logical row as a list of num_columns tokens, with a hard-wrapped trailing
    label already rejoined across any continuation lines render_table() introduced -- callers
    never see the physical line breaks. lines is the table's own row lines (header already
    skipped by the caller); stops at the first blank line, matching render_table()'s own
    "blank line ends the table" convention.

    Detection: a line is a continuation of the previous row, not a new row, iff its first
    whitespace-split token doesn't parse as a plain integer -- every real row's leading '#'
    column always is one; a continuation line (a raw fragment of a wrapped label) essentially
    never is. Reconstruction is direct concatenation, no separator inserted -- the wrap is a
    lossless character-level cut, so undoing it is just gluing the pieces back in order.
    """
    current = None
    for raw_line in lines:
        line = raw_line.rstrip("\n")
        if not line.strip():
            break
        first = line.split(maxsplit=1)[0] if line.split() else ""
        if first.lstrip("-").isdigit():
            if current is not None:
                yield current
            current = line.split(maxsplit=num_columns - 1)
        elif current is not None:
            current[-1] += line.strip()
    if current is not None:
        yield current
```

Known, accepted limitation carried over from the addendum unchanged: a wrap point landing exactly on
a digit run could leave a continuation line whose own first token is pure digits, misread as a new
row. Real C/C++/Fortran identifiers can't *start* with a digit, so this only bites mid-identifier at
an exact cut point — rare, and not fixed here (matches the addendum's own explicit deferral).

### 4. Update both `select_hotspot_*.py` re-parsers

`select_hotspot_functions.py::labels_from_report()` and `select_hotspot_kernels.py::labels_from_report()`
both currently do `line.split(maxsplit=N-1)` per physical line directly. Both switch to iterating
`iter_table_rows(lines[header + 1:], num_columns=7)` (CPU, columns: `# self(s) %total total(s) calls
%self function`) and `num_columns=6` (GPU: `# total(s) %total calls avg(us) kernel`) respectively —
same column counts already documented in each file's own comment today, just no longer hand-split
per physical line. Each row's per-column index use (`parts[6]`/`row[6]` for the CPU label,
`parts[3]`/`row[3]` for the GPU calls-count filter, `parts[5]`/`row[5]` for the GPU label) is
unchanged, since `iter_table_rows()` preserves the exact same token layout — only now spanning
1+ physical lines transparently. The existing `len(parts) < N: continue` malformed-row guard moves
to the call site unchanged (`iter_table_rows()` itself only handles wrap detection/reconstruction,
not row validation — keeps it single-purpose).

  wrap (e.g. a ~150-char synthetic C++ template name) splits into the expected number of
  continuation lines, each indented to exactly `len(prefix)` spaces, and concatenating all wrapped

  function — every label under the cap returns `label_width == max(len(text) for ...)` (today's

  one row) and that row's own chunks reconstruct the original label when joined; a marker row
  (`values is None`) passes through untouched. `FormatAlignedRowsTests` gains one end-to-end case
