# Plan 3.14: `profile_traced_hotspot_kernels.sh` — rocprof-compute deep-dive from an existing trace

## Context

Today, going deep on a hot GPU kernel with AMD's hardware-counter profiler (`rocprof-compute`)
means running `scripts/profile_hotspot_kernels.sh`, which does its own fresh `rocprofv3`
auto-profiling scan (via `profile_GPU_hotspots.sh`) just to find which kernels are hot before
handing them to `rocprof-compute`. If a user already has a `rocprof-sys` trace directory (from
`instrument_hotspots.sh trace` or `profile_traced_hotspots.sh`) — which already contains everything
needed to identify hot kernels — there's no way to reuse it; they'd pay for a second, redundant
profiling run just to re-discover kernel names `rocprof-compute` could otherwise be pointed at
directly. This plan adds a new script, `profile_traced_hotspot_kernels.sh`, that starts from an
existing trace directory instead: it extracts the kernels with the highest %runtime directly from
the trace's already-recorded data, then runs `rocprof-compute` on just those — combining
`profile_traced_hotspots.sh`'s "start from an existing trace" convention with
`profile_hotspot_kernels.sh`'s "resolve kernel names → run rocprof-compute → analyze" pipeline.

Researched by reading both parent scripts in full, the shared `postprocess/tools/select_hotspot_kernels.py`
kernel-name resolver and its `stage5_table_render.select_entries()` dependency, the trace-CSV
aggregation stack (`stage4_rocprofsys_trace_flat.py`, `stage4_rocprofsys_trace_ranks.py`,
`stage3_rocprofsys_trace.py`'s category-tag map), and validated end-to-end by a Plan agent that
re-checked every claim against the actual code and caught two real gaps (see Design notes below).
Key finding: `select_hotspot_kernels.py` currently only understands two kernel-name sources — a
`GPU_HOTSPOTS_COLUMNS`-format report (from `extract_GPU_hotspots.py`/`extract_hotspots.py`) or a raw
`rocprofv3` output directory — and **cannot** read a trace-based `hotspots.txt`
(`extract_trace_hotspots.py`'s output uses a different, CPU+GPU-fused column layout,
`FUSED_HOTSPOTS_COLUMNS`, with no per-section "GPU kernel hotspots" header the existing parser looks
for). So this plan's core new capability is a third source, `--trace-dir`, that reads kernel names
straight from the trace-CSV aggregation pipeline instead of any rendered report text.

## Confirmed decision (from the user)

`--time-range` support is in scope: `profile_traced_hotspot_kernels.sh` and
`select_hotspot_kernels.py --trace-dir` both get a `--time-range` flag, consistent with every other
trace-CSV tool (plan 3.13), so kernel selection can be scoped to e.g. a single steady-state
iteration instead of the whole run (including init/teardown) when the user wants that.

## Design

### 1. New `aggregate_gpu_kernels()` in `postprocess/stage4/stage4_rocprofsys_trace_flat.py`

The existing `aggregate(rank_inputs, cache_dir=None)` (line ~29) merges CPU functions and GPU
kernels/API/memcpy rows into one set of per-label entries tagged only with a coarse
`"domain"` (`"CPU"`/`"GPU"`) — `gpu_api` (e.g. `hipLaunchKernel`) and `gpu_kernel` rows both collapse
into `"GPU"`, so post-filtering its output by domain would wrongly include launch-call API frames,
not just actual kernel dispatches.

New `aggregate_gpu_kernels(rank_inputs, cache_dir=None)` mirrors `aggregate()`'s own loop structure
(same `_rank_rows(rank_inputs, cache_dir)` per-rank row helper the existing function already uses)
but filters each row to `"gpu_kernel" in row["tags"]` *before* accumulating into per-label
`count`/`sum`/`self_sum` — the same tag `gather_timing_summary_per_rank()` already filters on for
its own `gpu_busy_time` scalar (line ~108), sourced from `stage3_rocprofsys_trace.py`'s
`_CATEGORY_TAG_MAP` (`"rocm_kernel_dispatch"` / `"rocm_rccl"` → `"gpu_kernel"`). Returns
`(entries, total_kernel_time)`, where `pct_total` on each entry is computed against the *kernel-only*
total (matching how `stage4_rocprofv3.aggregate()` already ranks kernels against total kernel-dispatch
time for the rocprofv3 pipeline, not against total application runtime).

Because `--time-range` clipping (plan 3.13) happens inside `get_rank_aggregate()` itself, driven by
the process-wide `stage6_time_range_config` global, `aggregate_gpu_kernels()` needs no time-range
awareness of its own — it automatically respects whatever range is active, exactly like `aggregate()`
already does. The on-disk `.agg.json` cache is shared safely: every consumer (`aggregate()`,
`aggregate_per_rank()`, `gather_timing_summary_per_rank()`, and this new function) reads the same
cached full row set and applies its own in-memory filter afterward — no cache-format change needed.

### 2. New `--trace-dir` source in `postprocess/tools/select_hotspot_kernels.py`

New `labels_from_trace_dir(trace_dir, top=None, threshold=None, show_all=False,
require_multiple_calls=True, cache_dir=None)`:
- `stage6_cli_common.require_directory(trace_dir)` (matching the existing `--output-dir` path's own
  validation, line ~141)
- `rank_inputs = stage4_rocprofsys_trace_ranks.discover_ranks(trace_dir)`; `SystemExit` with a clear
  message if empty (mirroring the existing "no rocprofv3 kernel_stats.csv found" error at line ~54)
- `entries, _total = stage4_rocprofsys_trace_flat.aggregate_gpu_kernels(rank_inputs, cache_dir=cache_dir)`
- `selected, _desc = select_entries(entries, rank_field="sum", threshold_field="pct_total", top=top, threshold=threshold, show_all=show_all, threshold_unit="of total GPU kernel time")` — the exact same shared helper `labels_from_output_dir()` already uses (`stage5_table_render.py`), since `aggregate_gpu_kernels()`'s entries carry the same `"label"`/`"count"`/`"sum"`/`"pct_total"` fields it expects
- apply `require_multiple_calls` the same way (`e["count"] >= 2`) and return `sorted(set(labels))`

`main()` changes:
- `source = parser.add_mutually_exclusive_group()` gains a third member, `--trace-dir DIR`
- the "one of ... is required" check and its error message (line ~133-134) gets updated to mention
  all three sources
- `stage6_time_range_config.add_cli_argument(parser)` / `configure_from_args(args)`, added right
  after `parser.parse_args()` (same placement convention as `extract_trace_hotspots.py`/
  `extract_trace_calltree.py`) — this flag only has an effect when `--trace-dir` is the chosen
  source (the other two sources don't read raw `ts`/`dur` at all); document that in the flag's
  help text
- dispatch to `labels_from_trace_dir(args.trace_dir, top=args.top, threshold=args.threshold, show_all=args.show_all, require_multiple_calls=require_multiple_calls)` alongside the two existing branches

No change to `main()`'s final output convention: still one kernel name per line on stdout, nothing
else — so no `describe_time_range()` header note here (that's for human-readable reports; this
tool's stdout is machine-consumed directly into a bash array by the calling script).

### 3. New `scripts/profile_traced_hotspot_kernels.sh`

Mirrors `profile_hotspot_kernels.sh`'s structure and check ordering exactly (`set -euo pipefail`,
`SCRIPT_DIR`-relative tool paths, manual `while/case` arg loop, `usage()` heredoc, `--dry-run`
build-then-preview convention), with these changes:

```
Usage: profile_traced_hotspot_kernels.sh --trace-dir DIR [options] -- <executable> [args...]

  --trace-dir DIR          (required) rocprof-sys trace directory to select hotspot kernels from
                            (e.g. from instrument_hotspots.sh trace / profile_traced_hotspots.sh);
                            converted to CSVs first if not already
  -o, --output-dir DIR      rocprof-compute output/workload directory
                            (default: profile_traced_hotspot_kernels-workload-<timestamp>)
  --top N                   hotspot kernels to select (default: 20; last of --top/--threshold/--all wins)
  --threshold PCT           select kernels >= PCT% of total GPU kernel time
  --all                     select every kernel found, no truncation
  --all-dispatches          profile EVERY call of each kernel instead of just its 2nd (same
                            tradeoff/warning as profile_hotspot_kernels.sh)
  --time-range RANGE        only select kernels hot within this window of the trace (see
                            extract_trace_hotspots.py --help for the RANGE syntax)
  --no-summary               skip auto-running rocprof-compute analyze afterward
  --mpi "<launch cmd>"       MPI launch command, forwarded to rocprof-compute; same multi-rank
                            safety gate as profile_hotspot_kernels.sh
  --trace-processor PATH     forwarded to convert_trace_to_csv.py if the trace dir needs converting
  --dry-run
  -h, --help
```

Step ordering (matching `profile_hotspot_kernels.sh`'s own order): tool-existence checks
(`rocprof-compute`, `python3`) → MPI safety gate (verbatim reuse of
`profile_hotspot_kernels.sh:141-170`) → trace-dir CSV check/convert (verbatim reuse of
`profile_traced_hotspots.sh`'s `compgen -G "$DIR"/*-[0-9]*.csv` / `convert_trace_to_csv.py` pattern
— a conversion failure here is fatal, unlike that script's own non-fatal report steps, since kernel
selection cannot proceed without CSVs) → `select_hotspot_kernels.py --trace-dir "$TRACE_DIR"
[selection args] [--all-dispatches] [--time-range "$TIME_RANGE"]` → same "no kernel resolved, rerun
with --all-dispatches" hard error as `profile_hotspot_kernels.sh:211-214` → build/run
`rocprof-compute profile -n "$WORKLOAD_NAME" -p "$OUTPUT_DIR" -k "${KERNELS[@]}" [-d 2] --
"$@"` → `rocprof-compute analyze -p "$OUTPUT_DIR" | tee "$OUTPUT_DIR/analysis.txt"` unless
`--no-summary`, exiting with the profiled app's own exit code.

No bash-level directory-existence pre-check is added for `--trace-dir` — matching both parent
scripts' precedent of deferring that to Python (`require_directory()` inside
`convert_trace_to_csv.py`/`select_hotspot_kernels.py`), not re-implementing it in shell.
