# Plan 3.4: `stage3_rocprofsys_common.py` split + `stage3_rocprofsys_trace.py` category tagger

## Context

Roadmap step 3 of `docs/plans/3.1-trace-postprocessing-family.md` (depends on 3.2's renames). This
is the trace pipeline's equivalent of the sample pipeline's noise-tagging engine
(`stage3_rocprofsys_sample.py`, designed in `docs/plans/2.5-stage3-noise-engine.md`) — it turns the
ancestry-linked rows `stage1_rocprofsys_trace.py` produces into a per-row set of **tags**, and
nothing else. Same governing principle as 2.5, restated for this session: **classification and
action stay separate — a tag is a fact about a row, what a tool does with that fact (drop it,
splice it out, collapse its children, route it to a different table) is decided by the calling
tool, never by this module.** The same set of action primitives the sample engine already exposes
(`remove_tagged_subtrees`, `splice_by_tag`, `make_collapses_children`, `make_is_pruned`) must work
on trace rows too, unchanged.

Unlike the sample/text-table pipeline — where a row's only signal is a label string, and
substring/prefix/suffix pattern-matching is the *only* way to guess what a row represents — a trace
row already carries an exact, ground-truth `category` per event (confirmed against real Perfetto
data this session: `rocm_hip_api`, `rocm_kernel_dispatch`, `mpi`, `ompt`, `host`, `numa`,
`pthread`). AMD's `categories.h` documents the full enum this session found via ROCm doxygen docs:
`NONE, PYTHON, USER, HOST, ROCM, ROCM_HIP_API, ROCM_HSA_API, ROCM_KERNEL_DISPATCH,
ROCM_MEMORY_COPY, ROCM_SCRATCH_MEMORY, ROCM_PAGE_MIGRATION, ROCM_COUNTER_COLLECTION,
ROCM_MARKER_API, ROCM_ROCDECODE_API, ROCM_ROCJPEG_API, ROCM_RCCL_API, ROCM_RCCL, SAMPLING, PTHREAD,
KOKKOS, MPI, OMPT`, plus several `AMD_SMI_*` variants and system-monitoring categories not
enumerated exhaustively. So the primary classification here is a direct `{category: tag}` lookup,
not pattern-matching — a genuine simplification the trace format affords over the sample pipeline,
worth stating plainly rather than re-deriving the sample engine's heuristics for a problem this
data doesn't have.

That said, two of the sample engine's five tags — `wrapper_noise` (rocprofsys/gotcha
instrumentation overhead) and `compiler_runtime_noise` (malloc-internals noise) — classify by
*name*, not by any category a text table has, because they're about *who's calling*, not *what
kind of call it is*. A trace's CPU-side rows (`host`, `ompt`, `pthread`, `sampling`, ...) carry
plain function names in the same `name` field the sample engine's `label` matches against, so the
exact same risk exists: rocprofsys's own instrumentation wrapper frames or libc allocator internals
can show up as ordinary-looking rows in a trace too. Re-implementing that pattern logic a second
time would duplicate real domain knowledge (the actual substring lists in
`default_noise_patterns.json`) for no reason — this plan reuses it directly instead, which is the
main "common element to mutualize" this design turns on.

**Two directed design changes made explicit here** (both confirmed directly, not this plan's own
first draft): reading `stage3_rocprofsys_sample.py`'s actual source line-by-line for this plan
turned up that *nothing* in it is sample-specific — `tag_rows()`, the sibling/ancestor propagation,
and all four tree-surgery primitives already key only on `label`/`parent`/`is_thread_root`/
`tags`/`structural_drop_tags`/`self_sum`/`sum`, none of which are unique to the text-table format.
Its `_sample` suffix (from plan 3.2's mechanical batch rename) turns out to have been premature —
given trace-side reuse is now real, not hypothetical, the file itself should move to a shared
`stage3_rocprofsys_common.py`, with both pipelines as declared consumers, rather than having the
trace side quietly depend on a module named for the other pipeline.

Separately (**corrected from this plan's first draft**, which proposed aliasing a trace row's
`name` into a `label` key inside stage1 — rejected directly): the engine shouldn't be hardcoded to
the string `"label"` at all. `stage1_rocprofsys_sample.py`'s rows happen to use `label`;
`stage1_rocprofsys_trace.py`'s rows use `name`; a future format's stage1 might use something else
again. The one line in `stage3_rocprofsys_common.tag_rows()` that reads a row's display name
(`_label_matches(row["label"], td)`) takes which key to read as a parameter instead, defaulting to
`"label"` (so every existing caller is unaffected), and each stage1 module is the single declared
source of truth for its own rows' key name — `stage1_rocprofsys_trace.py` exports it as a
`LABEL_KEY` constant, threaded down through the pipeline by whichever stage3-family module consumes
that stage1's rows, rather than mutating row data to fit the engine's assumption.

## Approach

### `stage3_rocprofsys_common.tag_rows()` gains a `label_key` parameter

Signature becomes `tag_rows(rows, tag_defs=None, filename=None, label_key="label")`. The single
line that reads `row["label"]` becomes `row[label_key]`; nothing else in the function (or in the
other three primitives, which never read a row's display-name field at all) changes. Default value
`"label"` means every existing sample-pipeline caller
(`stage4_rocprofsys_sample_tree.py`/`stage4_rocprofsys_sample_flat.py`) needs zero changes beyond
the import-path rename — confirmed no other behavior difference, since passing `label_key="label"`
explicitly vs. omitting it are identical.

### Stage1 addition: `LABEL_KEY` constant

`stage1_rocprofsys_trace.py` gains one module-level constant, `LABEL_KEY = "name"`, documented in
its docstring as "the column this module's rows use as their human-readable display name, for
callers threading it into `stage3_rocprofsys_common.tag_rows()`'s `label_key` parameter." No row
data changes at all — `stage1_rocprofsys_trace.py`'s existing "preserve every column, no
interpretive shaping" scope (plan 3.3) stays fully intact, no divergence to record there.
`test_stage1_rocprofsys_trace.py` gets one new, small assertion: `stage1.LABEL_KEY == "name"`.

### Category → tag map

A plain Python dict constant in the new module (not a JSON file, unlike the sample engine's
patterns) — deliberate divergence, with rationale: `default_noise_patterns.json` exists so an
*app-specific* substring pattern can be tuned without a code change, because label text is
inherently open-ended. A `category` value is a closed, ROCm-defined enum, not free text tunable
per-app — there's nothing here for a user to configure, only new ROCm releases occasionally adding
enum members, which already need a code change to `categories.h` itself upstream. The explicit
fallback bucket (below) is what actually gives this forward-compatibility, not a config file.

| Categories | Tag | Rationale |
|---|---|---|
| `rocm_hip_api`, `rocm_hsa_api`, `rocm_marker_api`, `rocm_rocdecode_api`, `rocm_rocjpeg_api`, `rocm_rccl_api`, `rocm_counter_collection` | `gpu_api` | Host-side API-call overhead — same name and meaning as the sample engine's `gpu_api`, just derived from an exact category instead of a name substring. |
| `rocm_kernel_dispatch`, `rocm_rccl` | `gpu_kernel` | **New tag** — actual device execution time. The sample/text pipeline has no row-level visibility into this at all (kernel timing there comes from a separately-joined GPU CSV at stage4 tree, not a row tag), so there's no existing name to reuse; `gpu_kernel` names the specific case a `--show-gpu-api`-style flag would want to treat differently (device execution vs. host-side launch overhead). |
| `rocm_memory_copy`, `rocm_scratch_memory`, `rocm_page_migration` | `gpu_memcpy` | **New tag** — device memory movement. Plan 3.1 explicitly flagged `ROCM_MEMORY_COPY` as belonging to neither the CPU nor GPU-kernel domain cleanly; giving it (and the two scratch/page-migration categories whose names describe the same kind of activity) an explicit third bucket resolves that rather than forcing a wrong choice. |
| `mpi` | `mpi_territory` | Same name and meaning as the sample engine's tag. |
| `numa`, `rocm` (the bare/generic category), `amd_smi_*` (prefix match) | `other` | These are real, ROCm-documented categories (`numa`/`pthread` were both actually observed in this session's real trace), but their row-level semantics (is `numa` a hierarchical call-tree row or a side-channel monitoring event? are `amd_smi_*` rows nested in the tree at all?) are genuinely unknown without real data to inspect — routing them to the explicit fallback flags them as "not a normal app-code row" without guessing a taxonomy this session has no evidence for. Not set in stone; revisit once real trace data exercises them. |
| anything else not listed above (a category from a ROCm version newer than this tool knows about) | `other` | The roadmap's required "explicit fallback bucket for unmapped categories." |
| `host`, `ompt`, `pthread`, `sampling`, `python`, `user`, `kokkos`, `none` | *(no category tag)* | "CPU-ish, nameable" categories — plausible homes for real app/OpenMP/Kokkos code, but also exactly where `wrapper_noise`/`compiler_runtime_noise` need to look (see below). Left untagged by the category map itself, same as the sample engine leaves ordinary app-code rows untagged. |

This gives all five sample-engine tags a direct trace-pipeline equivalent (`gpu_api`,
`mpi_territory` by category; `wrapper_noise`, `compiler_runtime_noise`, `wrapper_branch_noise` by
the reuse below) plus `other`, exactly matching the "5 + others" shape — with two genuinely new
tags (`gpu_kernel`, `gpu_memcpy`) the trace format newly makes possible. `tag_for_category(category)`
is exposed as its own small function (lowercased exact lookup, then `amd_smi` prefix check, then
membership in the documented CPU-ish set → `None`, else `"other"`) so the fallback path has an
isolated unit test, per the roadmap's explicit call for one.

### Reusing `wrapper_noise` / `compiler_runtime_noise` / `wrapper_branch_noise` directly

Checked directly against the source: none of `wrapper_noise`, `compiler_runtime_noise`, or the
derived `wrapper_branch_noise` use `ancestor_for_thread_roots` or `first_real_descendant_skip_tag`
in `default_noise_patterns.json` today — those only decorate `gpu_api`/`mpi_territory`, which this
plan already classifies by exact category instead. So calling `tag_rows()` restricted to just those
three tag defs needs no `is_thread_root` handling at all, and (now that `tag_rows()` takes
`label_key` as a parameter) no row mutation either — this module imports
`stage1_rocprofsys_trace.LABEL_KEY` and passes it straight through.

Call order in this module's `tag_rows(rows)`:
1. Delegate to `stage3_rocprofsys_common.tag_rows(rows, tag_defs=restricted_defs,
   label_key=stage1_rocprofsys_trace.LABEL_KEY)`, where `restricted_defs` is
   `stage6_noise_config.tag_defs()` filtered down to just `{"wrapper_noise",
   "compiler_runtime_noise", "wrapper_branch_noise"}`. This sets
   `row["tags"]`/`row["self_tags"]`/`row["structural_drop_tags"]` from those three patterns alone
   — deliberately excluding `gpu_api`/`mpi_territory` from this call, since those are already
   exact from the category map and re-running their name patterns against, say, a `host`-category
   helper function would risk a spurious match no exact category lookup would ever produce.
   A real, useful emergent property: a user's `--extra-noise-config` additions to `wrapper_noise`/
   `compiler_runtime_noise` (already meant to be app-specific) apply to trace-based tools for free,
   with no separate config path to maintain.
2. For every row, add its `tag_for_category(row["category"])` result (if not `None`) into the
   *already-set* `row["tags"]` — must happen after step 1, since `stage3_rocprofsys_common.tag_rows`
   assigns (not unions) `row["tags"]`.
3. Return `None` (mutates in place), matching `stage3_rocprofsys_common.tag_rows`'s own signature
   exactly, not `stage1_rocprofsys_trace.attach_ancestry`'s "returns rows" convention — this module
   is the closer analog.

### Re-exporting the action primitives

`remove_tagged_subtrees`, `splice_by_tag`, `make_collapses_children`, `make_is_pruned` are
imported from `stage3_rocprofsys_common` and re-exported unchanged (a one-line import, documented
in the module docstring as "see there for semantics") — matching plan 3.1's roadmap wording exactly
and letting a caller depend on this single module for everything the trace-tagging step needs.
None of these four read `row["label"]` or anything category-specific — confirmed directly from
source (they key only on `tags`/`structural_drop_tags`/`parent`/`self_sum`/`sum`) — so they work on
tagged trace rows with zero modification. `splice_by_tag(fold=True)`'s self-time folding is a
no-op until a later stage populates `self_sum`/`sum` (stage4's job, per plan 3.3) — actions get
wired up against the aggregated tree in a later stage5/6-equivalent plan, exactly mirroring how the
sample pipeline's tools call these primitives against stage4 output today, not raw stage1/2 rows.

### Module: `postprocess/stage3/stage3_rocprofsys_trace.py`

Docstring covers: scope (turns ancestry-linked trace rows into `tags`, nothing else), the
category-map rationale (closed enum vs. open-ended label patterns → why this one isn't JSON-backed
like the sample engine's), the explicit reuse of `wrapper_noise`/`compiler_runtime_noise`/
`wrapper_branch_noise` via delegation (and why `is_thread_root` needs no handling here), and that
`gpu_api`/`mpi_territory`/`gpu_kernel`/`gpu_memcpy`/`other` all come from `tag_for_category()`
alone. States explicitly out of scope: cross-rank merging, `corr_id`-based kernel/launch
correlation, count/self_sum computation, any tool-level action wiring.

Functions: `tag_for_category(category)`, `tag_rows(rows)`, plus the four re-exported primitives.

### Tests — `postprocess/tests/stage3/test_stage3_rocprofsys_trace.py`

Same `importlib.util.spec_from_file_location` convention as every other stage test file.

- `TagForCategoryTests`: one case per map row above (`rocm_hip_api` → `gpu_api`, `rocm_rccl` →
  `gpu_kernel`, `rocm_memory_copy` → `gpu_memcpy`, `mpi` → `mpi_territory`, `numa` → `other`, an
  `amd_smi_something` prefix case → `other`, each CPU-ish category → `None`, and a wholly
  made-up, never-seen category string → `other`, exercising the explicit fallback the roadmap calls
  for).
- `TagRowsTests`: built on small synthetic row lists (reusing the existing trace fixtures under
  `postprocess/tests/fixtures/trace_single_rank/` where they already fit, plus new synthetic rows
  where they don't) covering:
  - A `rocm_hip_api` row gets `gpu_api` in `tags`; a `mpi` row gets `mpi_territory`; a
    `rocm_kernel_dispatch` row gets `gpu_kernel`; a `rocm_memory_copy` row gets `gpu_memcpy`.
  - A `host`-category row named to match an existing `wrapper_noise` substring (e.g. containing
    `"gotcha"`) gets tagged `wrapper_noise`, proving the delegated call fires on trace rows.
  - A `host`-category row with two children, one of whose whole subtree matches `wrapper_noise`
    and a clean sibling, produces `wrapper_branch_noise` in `structural_drop_tags` on the
    contaminated sibling — proving the sibling-group derivation still works unmodified.
  - A `host`-category row with an ordinary app-looking name gets no tag at all (no false positive).
  - A `numa`-category row gets `other`; an unmapped/future category string gets `other`.
  - A row matching both an exact category tag and a `wrapper_noise`/`compiler_runtime_noise`
    pattern by name (constructed deliberately, even if unlikely in real data) ends up with **both**
    tags in `tags` — proving step 3's union doesn't clobber step 2's result.
- `ReexportedPrimitivesTests`: a short smoke test that `remove_tagged_subtrees`/`splice_by_tag`/
  `make_collapses_children`/`make_is_pruned` imported from this module are the *same* functions as
  `stage3_rocprofsys_sample`'s (identity check), not reimplementations — guards against silent drift
  between the two if someone "fixes" one copy later without noticing the re-export.

No new fixture *files* needed beyond what plan 3.3 already created — synthetic row dicts built
directly in the test file cover the category/name combinations the existing CSV fixtures don't
already carry (unmapped category, `wrapper_noise`-matching name under `host`, memcpy/rccl
categories).

### Explicitly out of scope for this plan

Any tool-level `{tag: action}` wiring (that's a later stage5/6-equivalent plan, roadmap step 6);
`corr_id`-based kernel/launch-site correlation; cross-rank merging; count/self_sum computation
(stage4's job). The `numa`/`rocm`(generic)/`amd_smi_*` → `other` routing is a deliberate,
documented placeholder pending real trace data — not treated as a final taxonomy decision.
