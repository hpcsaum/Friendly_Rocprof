# Fourth tool: selective instrumentation helper

## Context

Tools 1-3 (`profile_CPU_hotspots.sh`, `profile_GPU_hotspots.sh`, `profile_hotspots.sh`) all answer "where does the time go" using non-invasive techniques (CPU sampling, GPU kernel tracing) — no rebuild needed. This fourth tool is different in kind: it uses AMD's binary-rewriting instrumentation (`rocprof-sys-instrument`) to build a new copy of the target binary that only instruments the specific functions the first three tools already identified as hotspots, then optionally runs that binary to produce a full trace. The point is overhead reduction: instrumenting every function in a binary is slow and self-distorting; instrumenting only the ~top 1% (the functions that already showed up as hotspots) is not — this is the intended next step after a user has already run `profile_hotspots.sh` and knows where to look.

Requirements as given by the user: the script either runs `profile_hotspots.sh` itself with a 1% threshold, or takes an existing `hotspots.txt` as an optional argument; it then runs `rocprof-sys-instrument` to build an experiment that traces only the hotspot functions; and it has two modes — "instrument" (build only) and "trace" (build, then run to produce a full trace).

Facts below were confirmed directly from AMD's ROCm 7.0.2 docs and from `rocprofiler-systems`' own source (`module_function.cpp`, `details.cpp`, `function_signature.cpp`), not invented, since incorrect instrumentation-tool flags would be a much worse failure mode here than in the read-only tools 1-3.

## Confirmed facts about `rocprof-sys-instrument`

1. **Binary rewrite** (`rocprof-sys-instrument <opts> -o <new-exe> -- <exe>`) is lower-overhead than **runtime/dynamic mode** (`rocprof-sys-instrument <opts> -- <exe> [args]`, the default when neither `-p` nor `-o` is given), and is the documented/recommended mode for MPI apps specifically — the docs state runtime mode's fork+ptrace is "generally incompatible with how MPI applications spawn processes." Recommended flow: rewrite once, then run the resulting `.inst` binary (optionally under `mpirun`) via `rocprof-sys-run -- ./myexe.inst`.
2. **Function selection**: `-R/--function-restrict <regex...>` is an exclusive allow-list — only matches survive, i.e. exactly "instrument only these functions." `-I/--function-include` force-includes without excluding others; `-E/--function-exclude` always wins over both. Multiple values on one flag are ORed. Matching runs (source-confirmed) against the **demangled** function name and a demangled signature string, via `std::regex_search` (unanchored, ECMAScript grammar) — so function names need only their regex metacharacters escaped, not full-signature exact matching.
3. No built-in "auto-select functions from a prior profiling run" feature exists in `rocprof-sys-instrument` — a wrapper that builds `-R` regexes from our own hotspots data is genuinely necessary, not redundant.
4. **Instrument-only vs. full trace is the same instrumented binary, different runtime env vars**, not a different rewrite invocation: `ROCPROFSYS_TRACE=1` enables the full perfetto-trace backend; `ROCPROFSYS_PROFILE=1` enables the lighter timemory backend. Both "instrument" and "trace" mode below use the identical `.inst` binary built once by the rewrite step.
5. MPI: avoid runtime-instrumentation mode entirely; rewrite once (single process, not under `mpirun`), then `mpirun -n N rocprof-sys-run -- ./myexe.inst` to run the pre-built binary per rank.
6. **Runtime API-tracing toggles, orthogonal to Dyninst instrumentation** — these are separate runtime interceptors (GOTCHA/OMPT/ROCprofiler-SDK callbacks) loaded by the rocprof-sys runtime library itself, available regardless of whether the binary was Dyninst-rewritten, confirmed in source (`config.cpp`, tag `rocm-7.0.2`) and `configuring-runtime-options.html`:
   - `ROCPROFSYS_USE_ROCM` — "Enable ROCm API and kernel tracing", **default `true`**.
   - `ROCPROFSYS_USE_OMPT` — "Enable support for OpenMP-Tools", **default `false`** — requires the target program's OpenMP runtime to actually support/expose OMPT callbacks to capture anything (not guaranteed for every OpenMP runtime; not independently confirmed by AMD docs, but architecturally required by how OMPT works).
   - `ROCPROFSYS_USE_MPIP` — "Enable support for MPI functions" (GOTCHA-based interposition, no relinking needed), **default `true` in source, but silently force-reset to `false` if the installed rocprofiler-systems build wasn't compiled with MPI support** — whether this actually captures anything on the target system depends on how that system's ROCm/rocprofiler-systems package was built. No AMD-documented way to reliably detect this from a wrapper script, so this is a documented caveat, not something we auto-detect.
   - No AMD-documented single "bundle" flag combines these three; each is independent. The user directed setting all three explicitly for `trace` mode regardless of their defaults (belt-and-suspenders against a site-level config file overriding a default), on the basis that these are lightweight API-boundary interceptors rather than full per-function Dyninst instrumentation — that overhead characterization is the user's own domain call, not an AMD-doc-confirmed claim, and is stated as such rather than attributed to AMD's docs.
7. **The rewrite step unconditionally writes `instrumented.json`/`.txt`** listing exactly the post-filter set of functions that got instrumented (confirmed in `rocprof-sys-instrument.cpp`/`module_function.hpp`, tag `rocm-7.0.2`) — `--print-dir <path>` controls where; each entry has a `function` field (demangled) and a `signature.name` field (also demangled, may include params/templates). This is the authoritative source this plan uses to detect "requested hotspot functions that didn't actually get instrumented," rather than an independent heuristic.

Sources (to cite in `-h`/`--help` text and code comments): https://rocm.docs.amd.com/projects/rocprofiler-systems/en/docs-7.0.2/how-to/instrumenting-rewriting-binary-application.html and https://rocm.docs.amd.com/projects/rocprofiler-systems/en/docs-7.0.2/how-to/configuring-runtime-options.html

## Design

### Core decision: one script, two modes, MPI launch driven by the script itself — not by wrapping it externally

Tools 1-3's convention is "`mpirun` wraps the whole script, once per rank, and the script self-detects its rank via env vars." That convention doesn't fit this tool: the binary rewrite must happen exactly once, full stop, never once-per-rank — and on a real HPC system this tool runs once per job step, inside an existing SLURM/PBS allocation or interactive session, not itself re-launched by `mpirun`/`srun` N times. Instead (per the user's explicit direction, citing the pattern used by HPE's `gbb4hpc`-style tools): **this script takes the MPI launch command as data, via `--mpi "<launch command and rank count>"`** (e.g. `--mpi "mpirun -np 4"` or `--mpi "srun -n 4"`), and decides internally where that prefix does or doesn't apply — rather than the script being invoked N times and figuring out its own rank. `--mpi` is optional; omitting it runs everything as a plain single process (a serial app). The value is split on whitespace (simple `read -ra`, no nested-quoting support — consistent with this project's established GIGO/beginner-scope simplicity, same spirit as tools 1-3 not validating cross-tool input).

This is a deliberate, scoped exception to tools 1-3's own convention, not a proposal to change theirs — it exists here because this tool has a genuine once-only build step that the wrap-the-whole-script pattern can't express cleanly, and because on a real HPC system a single top-level script invocation (not one per rank) matches how the target environment actually works. Worth one sentence in `docs/DEVELOPMENT_HISTORY.md`'s narrative for this tool so it doesn't read as an inconsistency later.

**`trace` mode runs every step `instrument` mode runs, then continues one step further** — it is not a separate pipeline that consumes some other invocation's output. The two modes share one pipeline; only the last step differs (`instrument` stops after the build and prints a summary, `trace` immediately also runs the freshly-built binary to produce the actual trace). This was the main point of ambiguity to resolve: there is exactly one script invocation per use, never a required "run `instrument` first, then separately run `trace`" two-invocation workflow (a user *can* still call `instrument` alone if they only want to inspect what would be instrumented without running anything, then later call `trace` — reusing the same `--report`, if they saved one — but `trace` never assumes a `.inst` binary already exists; it always builds its own).

For usability, **both modes end by printing a ready-to-paste command line**, not just `instrument`: `instrument` prints the exact `trace` invocation that would generate a trace from what it just built (same `--report`/`--mpi`/binary path, prefixed "to generate the trace, run:"); `trace` prints the exact `trace` invocation it itself just ran, verbatim (prefixed "to regenerate this trace, run:") — so either mode always leaves the user with a concrete, reusable command for producing/reproducing a trace, whether or not that's the mode they happened to run.

Concrete walkthrough (example: an MPI+HIP app `./myapp --iters 100`, launched via `mpirun -np 4`, run once from inside an existing SLURM/PBS allocation — the script itself is invoked exactly once, not per rank):

**Shared steps, run by BOTH modes, in this order:**
1. **(only if `--report` was NOT given)** run the full N-rank job once, to measure it: `mpirun -np 4 scripts/profile_hotspots.sh --threshold 1 -o rocprof-sys-instrument-scan -- ./myapp --iters 100` — a completely normal use of the existing tool 3, with the given `--mpi` value placed in front of it exactly the way that tool's own docs already say to (`mpirun`/`srun` before the script). All 4 ranks run through it together, same as if the user had typed that command by hand. Skipped entirely if `--report FILE` was given.
2. Read the resulting `rocprof-sys-instrument-scan/rocprof-sys/` directory (or the given `--report` file) and resolve it to a list of hotspot function names, once.
3. Run the binary rewrite **once, with no `mpirun`/`srun` in front of it at all, regardless of what `--mpi` was**: `rocprof-sys-instrument -R "<regex1>" -R "<regex2>" ... -o ./myapp.inst -- ./myapp` — a single Dyninst pass over the binary file on disk. This step never executes `./myapp` and has nothing to do with ranks; running it 4 times (once per MPI rank) would just rebuild the identical `./myapp.inst` four times for no benefit, which is exactly what step 1's "run the whole script once, not per rank" already avoids.
4. Print `./myapp.inst`'s path.

**Then each mode does its own final step:**
- **`instrument` mode** stops here: prints "to generate the trace, run:" followed by the exact `scripts/instrument_hotspots.sh trace ...` command line that would do so (reusing the same `--report`/`--mpi`/binary path), and exits 0. Nothing is ever executed using `./myapp.inst` in this mode.
- **`trace` mode** continues immediately, in the same invocation: exports the trace-related env vars (`ROCPROFSYS_TRACE=1`, `ROCPROFSYS_USE_ROCM=1`, `ROCPROFSYS_USE_OMPT=1`, `ROCPROFSYS_USE_MPIP=1`, `ROCPROFSYS_OUTPUT_PATH=<trace output dir>`), then runs `mpirun -np 4 rocprof-sys-run -- ./myapp.inst --iters 100` (the same `--mpi` value from step 1 placed in front of `rocprof-sys-run`, or plain if `--mpi` was omitted) — all 4 ranks run the just-built instrumented binary together, each producing its own trace file under the trace output directory. On success, prints "to regenerate this trace, run:" followed by the exact `scripts/instrument_hotspots.sh trace ...` command line just executed, verbatim.

Naming (per `CLAUDE.md`'s convention): `scripts/instrument_hotspots.sh` (names the action, not the AMD tool). Python helper: `postprocess/select_hotspot_functions.py` — it *consumes* a report to *select* functions, which doesn't fit the existing `extract_<what>` pattern (those produce a report from raw AMD output); `select_<what>` describes what this one actually does.

### Obtaining hotspot function names

Two sources, resolved to the same shape (a deduped, sorted list of clean function labels):

1. **`--report FILE`**: parse specifically the `"=== 2. CPU compute hotspots ..."` table (works identically for a combined `extract_hotspots.py` report or a solo `extract_CPU_hotspots.py` report — same `format_table()` output either way). Never table 1 (fused) or table 3 (GPU kernels) — GPU-domain rows are kernel names, not something `-R`'s function-name matching can select; kernel instrumentation is an unrelated mechanism. Locate the header line ending in `function`, then take column 5 (`line.split(maxsplit=5)[5]`) of each following row until a blank line.
2. **No `--report`** (default): run `profile_hotspots.sh $SELECTION_ARGS -o "$OUTPUT_DIR" -- "$@"` as a normal full run (not `--no-summary`, so the user also keeps a normal reusable `hotspots.txt`), then read `$OUTPUT_DIR/rocprof-sys` directly via `extract_CPU_hotspots.aggregate()` + `select_entries(..., top=..., threshold=..., show_all=...)` — reusing tool 1's existing, already-tested functions instead of re-parsing our own pretty-printed text when we don't have to. For consistency, `instrument` mode exposes the **same full selection option set as `profile_hotspots.sh`/`profile_CPU_hotspots.sh`** — `-o/--output-dir DIR`, `--top N`, `--threshold PCT`, `--all`, `--no-summary` — not just a bare `--threshold`. `$SELECTION_ARGS` is built with the same shell-level "last of `--top`/`--threshold`/`--all` wins" convention already used by tools 1-3, **but defaults to `--threshold 1`** (per the user's original 1% requirement) rather than tools 1-3's own default of top-20, since nothing has been explicitly chosen otherwise. The exact same `$SELECTION_ARGS` value is forwarded to both the `profile_hotspots.sh` call (for the human-readable report) and the `select_hotspot_functions.py --output-dir` call (for the actual regex list) — one selection choice, applied consistently to both.

### Regex-escaping strategy

`-R` matches via `std::regex_search` (ECMAScript grammar), so each label becomes an **unanchored substring regex**, escaping only real ECMAScript metacharacters (`.^$*+?()[]{}|\`) — not Python's `re.escape()`, which over-escapes characters that aren't metacharacters in this grammar. `<`, `>`, `~`, `::` (common in C++ signatures, even though no current fixture has one) are left untouched since they're literal in this grammar. Multiple `-R` values are ORed by the tool itself, so one `-R <regex>` per hotspot label, no per-label anchoring.

### Lost-function detection (after the rewrite, using rocprof-sys-instrument's own output — not a heuristic)

Source-confirmed (`rocprof-sys-instrument.cpp`, `module_function.hpp`, tag `rocm-7.0.2`): the rewrite step **unconditionally** writes an `instrumented.json` (and `.txt`) file listing the exact post-filter set of functions that actually got instrumented — populated after all `-R`/`-I`/`-E` regex filtering and heuristics are applied. This is the authoritative answer to "did my requested function actually make it in," so this plan uses it directly instead of a separate heuristic (e.g. `nm`) that could disagree with the tool's own result. Each JSON entry has a `function` field (demangled name, via `Dyninst::getDemangledName()`) and a `signature` object with a `name` field (also demangled, via the tool's own `demangle()`) — likely including parameters/templates/namespaces, so matching against our plain labels (e.g. `compute_stencil`) must be substring, not exact-equality (same reasoning as the `-R` regex itself).

Mechanics: the rewrite command in step 6 always passes `--print-dir "$OUT_BINARY.rocprof-sys-info"` (an explicit, predictable location — rather than relying on the tool's own default `rocprof-sys-<basename>-output/` naming convention, which is harder to predict programmatically when `$OUT_BINARY` includes a directory). Immediately after a successful rewrite, run `printf '%s\n' "${LABELS[@]}" | python3 "$SELECTOR" --check-instrumented "$OUT_BINARY.rocprof-sys-info/instrumented.json"` — reads the requested labels from stdin, parses `instrumented.json`, and for each requested label with no substring match among any entry's `function`/`signature.name`, prints one stderr warning ("hotspot function '<label>' wasn't found in the instrumented binary -- it may be inlined, optimized out, or use a name rocprof-sys-instrument didn't match; this doesn't stop anything, but that function won't show up in the trace"). **Always exits 0** regardless of findings — per the user's explicit direction, a lost function is a warning, never something that stops the trace experiment. If `instrumented.json` itself is missing or unparseable (shouldn't happen given it's written unconditionally, but defensively handled rather than crashing the whole script over a transparency nicety), skip the check with a single one-line note instead. A genuinely empty *requested* label list (zero hotspots resolved at all, before the rewrite is even attempted) remains a separate, unambiguous hard error — a completely different failure mode from "some already-resolved labels didn't make it into the binary."

### `postprocess/select_hotspot_functions.py` — functions

- `escape_for_instrument_regex(name)` — escapes only `.^$*+?()[]{}|\`.
- `labels_from_output_dir(rocprof_sys_dir, top=None, threshold=None, show_all=False)` — `cpu_entries, _, scanned, total = extract_CPU_hotspots.aggregate(...)`; `SystemExit` if nothing scanned; `select_entries(cpu_entries, total, top=top, threshold=threshold, show_all=show_all)` (identical tri-state signature to `extract_CPU_hotspots.select_entries` itself, reused directly rather than narrowed to threshold-only); returns sorted deduped labels.
- `labels_from_report(report_path)` — finds the "CPU compute hotspots" section, parses its rows per the format above (rows are taken as-is, whatever selection produced the report is trusted — `--top`/`--threshold`/`--all` on this script have no effect on this path, noted in `--help`); `SystemExit` if no such section/rows found.
- `find_lost_functions(instrumented_json_path, requested_labels)` — loads the JSON array, builds one flat set of every entry's `function` + `signature.name` strings, returns the subset of `requested_labels` with no substring match in that set; raises a distinct, caught-by-the-caller exception (not `SystemExit` — this path must never abort the script) if the file is missing/unparseable, so `main()` can print a one-line skip note instead.
- `main(argv=None)` — two mutually-exclusive top-level modes, checked manually (not an argparse group, since the two modes take entirely different flag sets): **(a) resolve mode** (default): mutually-exclusive `--report FILE` / `--output-dir DIR`, plus a second mutually-exclusive selection group mirroring `extract_CPU_hotspots.py`'s own CLI exactly — `-n/--top N` / `--threshold PCT` (**default `1.0`, not tools 1-3's own default of 20** — this script's whole premise is "only the ~top 1%") / `--all` — meaningful only with `--output-dir`; prints `label<TAB>regex` pairs to stdout for the bash launcher to consume; exits 1 with a clear message on an empty resolved label list. **(b) `--check-instrumented FILE` mode**: reads requested labels one-per-line from stdin, calls `find_lost_functions`, prints one stderr warning per lost label (or a one-line skip note if the file couldn't be read); **always exits 0**, regardless of findings — a lost function is a warning, never a failure. Same `HELP_BLURB`/`RawDescriptionHelpFormatter` convention as the other three Python tools, ending in the AMD-tool-name + doc-link line.

### `scripts/instrument_hotspots.sh` — control flow

Shared preamble: `SCRIPT_DIR`, `HOTSPOTS_LAUNCHER="$SCRIPT_DIR/profile_hotspots.sh"`, `SELECTOR="$SCRIPT_DIR/../postprocess/select_hotspot_functions.py"`. Dispatches on a required leading mode argument (`instrument`/`trace`; bare `-h`/`--help` or anything else shows a short top-level usage and exits). **Both modes share the exact same option set and the exact same steps 1-6 below** — `trace` simply continues into step 7, `instrument` stops after step 6.

1. Options: `-o/--output-dir DIR` (default `rocprof-sys-instrument-scan`; base dir for the auto-profile run, split into `DIR/rocprof-sys`/`DIR/rocprofv3` by `profile_hotspots.sh` itself exactly as it already does), `--top N` / `--threshold PCT` / `--all` (mutually exclusive, shell-level "last one wins" like tools 1-3, but **defaulting to `--threshold 1`** rather than tools 1-3's own top-20 default), `--no-summary` (forwarded to `profile_hotspots.sh`; skips writing its `hotspots.txt`, but the underlying `$OUTPUT_DIR/rocprof-sys` data this tool actually reads is unaffected either way), `--report FILE` (skips auto-profiling entirely; ignores `-o`/selection flags, `--help` says so), `--mpi "<launch command>"` (optional, e.g. `"mpirun -np 4"`; reused for both the auto-profile call in step 3 and, in `trace` mode only, the final run in step 7 — it's the same job), `--out-binary PATH` (default `$BINARY.inst`; deliberately not reusing `-o`, which already means "output directory" here, and would be a footgun since this is a binary file path), `--trace-output-dir DIR` (default `rocprof-sys-instrumented-trace-output`; **`trace` mode only** — where the actual trace files land in step 7; unused/ignored by `instrument` mode), `--dry-run`, `-h/--help`. Require `--`, require ≥1 token after it; `BINARY="$1"`, keep full `"$@"` for reuse as `APP_ARGS`. If `--mpi` given, `read -ra MPI_ARR <<< "$MPI_STR"`; else `MPI_ARR=()`.
2. `command -v rocprof-sys-instrument` and `command -v python3` always hard-required (both modes; no fallback path, unlike tools 1-3's optional post-processing). `trace` mode additionally requires `command -v rocprof-sys-run` at this same point, before doing any of the (possibly slow) work below — fail fast rather than discovering a missing dependency only after the build has already run.
3. If `--report` given: skip straight to step 5 — no execution happens for this path, so `--mpi`/`-o`/selection flags are irrelevant/ignored here (a note in `--help` says so).
4. If no `--report`: run `"${MPI_ARR[@]}" "$HOTSPOTS_LAUNCHER" "${SELECTION_ARGS[@]}" -o "$OUTPUT_DIR" -- "${APP_ARGS[@]}"` (`${SELECTION_ARGS[@]}` defaulting to `(--threshold 1)`, overridden by whichever of `--top`/`--threshold`/`--all` was actually given) — the one place `--mpi` matters in the shared steps, since reaching representative code paths of an MPI-dependent app may require its real rank count. `profile_hotspots.sh` is invoked exactly as its own documented convention already expects (mpirun/launch command placed before it) — no changes needed to that script.
5. Resolve `label<TAB>regex` pairs via one call to the selector: `--report "$REPORT"` or `--output-dir "$OUTPUT_DIR/rocprof-sys" "${SELECTION_ARGS[@]}"` (the exact same `SELECTION_ARGS` used in step 4, so the report and the actual instrumented set always agree); non-zero selector exit aborts with its own message (empty label list).
6. Print the selected labels for transparency; build `rocprof-sys-instrument -R "${REGEXES[@]}" --print-dir "$OUT_BINARY.rocprof-sys-info" -o "$OUT_BINARY" -- "$BINARY"` — **always run un-prefixed, ignoring `MPI_ARR` entirely**, even if `--mpi` was given: binary rewriting is a single, one-time step that has nothing to do with a running MPI job. On success, run `printf '%s\n' "${LABELS[@]}" | python3 "$SELECTOR" --check-instrumented "$OUT_BINARY.rocprof-sys-info/instrumented.json"` (see "Lost-function detection" above) — its warnings, if any, land on stderr; it always exits 0 and never affects this script's own control flow. `--dry-run` prints, up to this point, the pairs + `printf '%q '` of the (if applicable) step-4 profiling command and the step-6 rewrite command; it does not run the lost-function check at all (nothing was actually built to check against).
   - **`instrument` mode stops here** (or, under `--dry-run`, prints what's above and exits 0 without running anything): on success, print the out-binary path, then "to generate the trace, run:" followed by the exact `scripts/instrument_hotspots.sh trace ...` command line reusing `--report`/`--mpi`/the binary path (built via `printf '%q '` over the equivalent invocation, so it's directly copy-pasteable).
7. **`trace` mode only, same invocation, immediately after step 6**: export `ROCPROFSYS_OUTPUT_PATH="$TRACE_OUTPUT_DIR"`, `ROCPROFSYS_TRACE=1`, and, so the trace actually shows kernels and MPI communication instead of only the selectively-instrumented hotspot functions: `ROCPROFSYS_USE_ROCM=1` (HIP API + kernel-dispatch + memcpy tracing), `ROCPROFSYS_USE_OMPT=1` (OpenMP region tracing, needs an OMPT-capable OpenMP runtime), `ROCPROFSYS_USE_MPIP=1` (MPI call tracing via runtime symbol interposition, no relinking needed — silently captures nothing if the installed rocprof-sys build lacks MPI support, a documented caveat rather than something this script detects); set explicitly regardless of each var's own default, both for transparency in `--dry-run` output and as a guard against a site config file overriding a default. Build `RUN_CMD=("${MPI_ARR[@]}" rocprof-sys-run -- "$OUT_BINARY" "${APP_ARGS[@]}")` — reusing the same `MPI_ARR` from step 4, since this is the same job/rank count. `--dry-run` additionally prints the exported vars + `printf '%q '` of `RUN_CMD`, exits 0; otherwise runs it (`set +e`/capture/`set -e`), prints a closing note that the trace is a Perfetto file under `$TRACE_OUTPUT_DIR` (viewable at ui.perfetto.dev; not parsed by any tool in this project — same honesty as `extract_CPU_hotspots.py`'s handling of `.proto` files it finds but doesn't parse), then "to regenerate this trace, run:" followed by the exact `scripts/instrument_hotspots.sh trace ...` invocation just executed (the original CLI arguments this script itself was called with, echoed back via `printf '%q '`), `exit "$APP_EXIT"`.

### Help text

Top-level usage (shown for a bad/missing mode or bare `-h`): ~12-line jargon-free explanation of the overhead problem this solves, stating plainly that **`trace` does everything `instrument` does and then also runs the result** (not two independent modes to be chained by hand), one line per mode, a pointer to each mode's own `-h`, and the closing AMD-tool-name + doc-link line. Each mode's own usage independently satisfies the same convention (blurb → doc-link line → options table). `trace` mode's usage additionally notes in plain language that the trace also captures GPU kernel launches/copies, OpenMP regions, and MPI calls automatically (not just the selected hotspot functions), with a one-line caveat that OpenMP tracing needs an OMPT-capable OpenMP runtime and MPI tracing needs a rocprof-sys build with MPI support — so a trace missing one of those isn't necessarily a bug in this script.
