# Plan 3.2: rename existing rocprof-sys modules, fix the stage4/5 boundary, document the stage4→5 contract (roadmap step 1)

> **Note (plan 3.4):** the `_sample` suffix this plan gave `stage3_rocprofsys.py` turned out to be
> premature — its actual content (the tag engine and tree-surgery primitives) is format-agnostic
> and is shared by the trace pipeline too. Plan 3.4 renames it again, to `stage3_rocprofsys_common.py`.
> See that plan for details; this file is left as originally approved.

## Context

`docs/plans/3.1-trace-postprocessing-family.md`'s implementation roadmap makes this step 3.2 — the
first, foundational step before any new trace-CSV code lands, with no dependency on anything else
in that roadmap. Three things, merged into one plan/diff because they're all preparatory
groundwork for the same reason: none of the new trace-CSV modules can be built cleanly without
them settled first, and none of them individually justifies its own plan.

1. **Rename the existing `*_rocprofsys*` modules.** They only ever handle rocprof-sys's timemory
   text-table/sampling output, never Perfetto trace data — plan 3.1 needs a new, parallel
   `*_rocprofsys_trace_*` family, and leaving the existing modules unqualified would make "trace"
   alone ambiguous about *whose* trace format. Symmetric fix: existing modules become
   `*_rocprofsys_sample_*`.
2. **Fix a pre-existing stage4/5 boundary gap**, found while designing 3.1: the flat-hotspots side
   already separates stage4 (gather/merge) from stage5 (rank/render) cleanly; the tree side never
   did — `stage5_tree_render.py` mixed genuinely generic rendering with rocprof-sys-specific rank
   loading and GPU-kernel-attachment orchestration, and `stage5_pop_metrics_table.py`'s
   `compute_run_metrics()` similarly welded per-rank data gathering to the LB/CommE/PE arithmetic.
   Both block a new backend from reusing the existing stage5 view code — the actual mechanism
   behind 3.1's "reuse stage5" claim — so both get fixed here, before anything reuses them.
3. **Document the stage4→5 entry contract** in `postprocess/README.md`, once the two fixes above
   settle what the canonical shapes actually are, so a future backend author has a written
   contract to target instead of re-deriving it by reading source.

## Approach

The tool rename (`extract_calltree_traced.py` → `extract_wallclock_calltree.py`) is a necessary
side effect, not part of the original ask: "traced" there has always meant "built from
`wall_clock-*.txt` timemory data," a different sense of "trace" than the new Perfetto-trace-CSV
tools — keeping it name-adjacent to a future `extract_trace_calltree.py` would recreate the exact
ambiguity this rename removes elsewhere. Every import site across `stage5_tree_render.py`,
`stage5_calltree_view.py`, `stage5_wallclock_calltree_view.py`, `stage5_fused_hotspots_table.py`,
`extract_hotspot_callers.py`, and `postprocess/README.md`/top-level `README.md` updates to match.

**Found during implementation, applied for full consistency**: `extract_wallclock_calltree.py`'s
own default output filename was still `calltree_traced.txt` — the same stale "traced" ambiguity
the tool rename exists to remove, just one level down. Renamed to `wallclock_calltree.txt`,
matching `extract_calltree.py` → `calltree.txt`'s existing convention. A real, user-visible
default-output-name change (unlike everything else in this plan), called out explicitly rather
than folded silently into the "mechanical rename" bucket above.

### Stage4/5 boundary fix #1 — calltree loader/attachment relocation

Move `load_rank_trees()`, `kernel_totals_with_counts()`, `pair_gpu_per_rank()` out of
`stage5_tree_render.py` into the renamed `stage4_rocprofsys_sample_tree.py` — pure relocation.

**Found during implementation**: the old `attach_and_render_gpu_kernels()` wasn't a pure
relocation candidate — it mixed stage4-shaped work (mutating the tree, re-deriving per-rank kernel
counts) with stage5-shaped work (rendering the "no anchor" fallback table via `format_aligned_rows`/
`REPORT_HEADERS`, both genuinely stage5 primitives). Moving it wholesale would have made stage4
import from stage5, inverting the intended dependency direction. Split instead:
- `stage4_rocprofsys_sample_tree.attach_gpu_kernels(flat, gpu_per_rank, gpu_dir, rank_keys, is_pruned, collect_into=None)`
  — attachment only, returns `(unattached, gpu_kernel_by_rank)`.
- `stage5_tree_render.render_gpu_kernel_fallback(unattached, gpu_kernel_by_rank, node_values)` —
  rendering only, replaces the old function's fallback-table half.

All three call sites (`stage5_calltree_view.py`, `stage5_wallclock_calltree_view.py`,
`extract_hotspot_callers.py`) updated to call both in sequence. `stage5_tree_render.py` loses its
`glob`/`os`/`stage1_rocprofsys_sample`/`stage1_rocprofv3`/`stage2_rocprofsys_sample`/
`stage3_rocprofsys_sample`/`stage4_rocprofv3` imports entirely — nothing left in that file needs
them once the moved functions are gone.

### Stage4/5 boundary fix #2 — `compute_run_metrics()` split

`stage5_pop_metrics_table.compute_run_metrics()` welded per-rank data gathering (calling
`stage4_rocprofsys_sample_flat`/`stage4_rocprofv3` by name) to the Load Balance/Communication
Efficiency/Parallel Efficiency arithmetic. Split into:
- `gather_timing_summary_per_rank(run_dir)` → `(per_rank, cpu_dir, gpu_dir, rank_keys)`, where
  `per_rank` is `[{rank_key, total_time, comm_time, useful_compute, cpu_only_time, gpu_busy_time}]`
  — the new **per-rank timing summary** shape. Kept in `stage5_pop_metrics_table.py` rather than
  moved to a stage4 module, matching `stage5_fused_hotspots_table.build_combined_view()`'s already-
  established precedent: a stage5 backend that gathers from stage4 modules and does per-run
  correction arithmetic is this codebase's accepted shape for this kind of work, not something
  stage4 itself owns.
- `compute_metrics_from_per_rank(per_rank)` → the LB/CommE/PE/GPU-Util/GPU-Off/GPU-LB dict, reading
  only the `per_rank` list — no stage4 imports, no opinion on where the numbers came from.
- `compute_run_metrics(run_dir)` kept as a thin wrapper (`gather` then `compute`, merged with
  `run_dir`/`cpu_dir`/`gpu_dir`/`num_ranks`) for existing callers (`extract_pop_metrics.py`) —
  byte-identical return shape and values.

### Documented contract

New `postprocess/README.md` section, "The stage4 → stage5 entry contract," naming the four
canonical shapes now in use (flat entry, tree node, per-rank label→value, per-rank timing summary)
and the rule: a new backend for an *existing* report kind targets one of these shapes to inherit
its stage5 view; a genuinely new report kind gets its own shape and its own view file. Also
corrected two now-stale mentions of `load_rank_trees()`/`attach_and_render_gpu_kernels()` still
living in `stage5_tree_render.py`, elsewhere in the same doc (the `stage4/`, `stage5/`, and
"Building a new tool" sections).
