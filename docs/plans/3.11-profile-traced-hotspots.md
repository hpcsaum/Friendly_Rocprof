# Plan 3.11: `profile_traced_hotspots.sh` — chaining trace → CSV → hotspots/calltree reports

## Context

Plans 3.7–3.10 built every individual piece of the trace pipeline: `instrument_hotspots.sh trace`
produces a raw per-rank Perfetto `.proto` trace; `convert_trace_to_csv.py` (plan 3.10) converts it
to trace-CSV; `extract_trace_hotspots.py`/`extract_trace_calltree.py` (plan 3.7) build reports from
it. Nothing chains these together yet — a user who wants a full trace-based hotspots/calltree
report has to run all four steps by hand. This plan adds that chain as one new script.

`instrument_hotspots.sh` itself stays exactly as it is for its own purpose (users who just want the
raw trace, e.g. to inspect in Perfetto's own UI) — except for one real bug, in scope for this plan
(found by the user, not deferred): it builds the instrumented binary (`rocprof-sys-instrument`'s
rewrite output) but never copies it into its own output directory, only leaving it next to the
original executable. Confirmed directly by reading the script (lines 253–255, 346, 359–373): `
OUT_BINARY` defaults to `"$BINARY.inst"`, and nothing after the rewrite (`"${REWRITE_CMD[@]}"`)
copies it anywhere else.

**Explicitly deferred, not part of this plan** (the user's own words: "this probably deserves a
dedicated plan"): CPU callers (and possibly MPI callers) of a GPU kernel that made it into the
hotspot table need to be instrumented too, independent of their own hotspot status — otherwise the
kernel-owner-reanchoring work from plan 3.8 has no real CPU frame to attach to, the same gap plan
3.8's own MPI-ancestry finding already surfaced. This is a real selection-logic change to
`instrument_hotspots.sh`/`select_hotspot_functions.py`, noted here as a forward pointer for a
future plan (tentatively 3.12) — not designed or touched in this plan.

## Decisions confirmed with the user

1. **Name**: `profile_traced_hotspots.sh` — not the user's initial "extract_and_trace_hotspots"
   suggestion, which mixed the `scripts/profile_<what>.sh` and `postprocess/tools/extract_<what>.py`
   verb conventions this project otherwise keeps separate. This script orchestrates other
   tools/scripts (like `profile_hotspots.sh` already does), it doesn't do its own data
   transformation, so it belongs in the `profile_` family.
2. **Binary-copy fix destination**: `$OUTPUT_DIR` (the scan directory) — present and meaningful in
   both `instrument` and `trace` modes, so one copy step covers both, unlike `$TRACE_OUTPUT_DIR`
   which only exists in `trace` mode.
3. **`convert_trace_to_csv.py`'s own `--unfiltered`** (emit the plain, non-partitioned CSV) is not
   exposed through the new script at all — it always requests just the default `-gpu`/`-mpi`/`-other`
   trio, which is also what every downstream tool actually needs (exact GPU-kernel correlation).
4. **Selection-flag namespace, split in two** (this resolves a real collision found while designing
   this — `instrument_hotspots.sh`'s `--top`/`--threshold`/`--all`/`--unfiltered` select which
   functions get *instrumented*; `extract_trace_hotspots.py`'s flags of the same names select which
   entries appear in the *final report* — two independent concerns that happen to share names):
   bare `--top`/`--threshold`/`--all`/`--unfiltered` control the **final report**
   (forwarded to `extract_trace_hotspots.py`); `--instrument-top`/`--instrument-threshold`/
   `--instrument-all`/`--instrument-unfiltered` control **instrumentation selection** (forwarded to
   `instrument_hotspots.sh`'s own same-named flags), for expert users who want to diverge from the
   default — when none of the `--instrument-*` flags are given, `instrument_hotspots.sh`'s own
   existing default (≥1% threshold) applies unchanged.
5. **Two resume/shortcut entry points**, mirroring `instrument_hotspots.sh`'s own `--report`
   shortcut but each skipping progressively more of the pipeline:
   - `--report FILE` — same meaning as `instrument_hotspots.sh`'s own flag (reuse an existing
     `hotspots.txt` instead of auto-profiling to select which functions to instrument), passed
     straight through unchanged. Scan is skipped; instrumentation + trace + convert + report still
     run.
   - **New**: `--trace-report DIR` — skips scan, instrumentation, AND the trace run entirely,
     starting straight from an existing trace directory `DIR` (from a previous run of this script,
     a raw `instrument_hotspots.sh trace` run, or any other source). Checks whether `DIR` already
     has trace-CSV files matching this project's naming convention — if so, skips
     `convert_trace_to_csv.py` too and goes straight to the two `extract_trace_*.py` report tools;
     if `DIR` only has raw `.proto` files, runs `convert_trace_to_csv.py` on it first. No `--
     <executable>` is needed in this mode (nothing gets built or run) — mutually exclusive with
     `--report`/`--instrument-top`/`--instrument-threshold`/`--instrument-all`/
     `--instrument-unfiltered`/`--mpi`/`--out-binary` (all configure a step that won't run when
     `--trace-report` is given), each rejected with a clear error if combined, matching this
     project's existing "fail clearly, don't guess" convention for conflicting flags (e.g.
     `select_hotspot_functions.py`'s own `--report`/`--extra-noise-config` mutual exclusion).

## Design details

### Bug fix: `instrument_hotspots.sh` — save the instrumented binary

Exact location: the successful (non-`--dry-run`) rewrite branch, right after `"${REWRITE_CMD[@]}"`
runs and the non-fatal `--check-instrumented` lost-function check completes (current lines 359–364).
Add one copy step there: `$OUT_BINARY` and its `$OUT_BINARY.rocprof-sys-info` sidecar directory
into `$OUTPUT_DIR` (e.g. `cp "$OUT_BINARY" "$OUTPUT_DIR/$(basename "$OUT_BINARY")"` plus a matching
sidecar copy). Update both success messages ("wrote instrumented binary: $OUT_BINARY" in `instrument`
mode, the final trace-mode summary) to also name the copy's location. The original `$OUT_BINARY`
path keeps being what actually executes in `trace` mode (line 384) — only the copy is new, nothing
about execution changes.

### Selection-flag namespace (the real design work in this plan)

| Bare flag (final report) | Forwards to | `--instrument-*` flag (instrumentation selection) | Forwards to |
|---|---|---|---|
| `--top`/`--threshold`/`--all` | `extract_trace_hotspots.py`'s own `--top`/`--threshold`/`--all` | `--instrument-top`/`--instrument-threshold`/`--instrument-all` | `instrument_hotspots.sh`'s own `--top`/`--threshold`/`--all` |
| `--unfiltered` | `extract_trace_hotspots.py`'s own `--unfiltered` | `--instrument-unfiltered` | `instrument_hotspots.sh`'s own `--unfiltered` |

Calltree-noise flags (`--max-depth`, `--show-gpu-api`, `--show-rocprofsys-internals`,
`--show-mpi-internals`, `--show-compiler-runtime`, `--show-all-internals`) have no such collision —
reused as-is for BOTH `instrument_hotspots.sh`'s own auto-profiling-scan calltree AND the final
`extract_trace_calltree.py` calltree, since they mean exactly the same thing (noise visibility) in
both places; no reason to make a user set the same preference twice.

Passed straight through, unprefixed, no collision: `--mpi`, `--report`, `--out-binary`,
`--no-summary`, `--dry-run`, plus one new flag this script introduces: `--trace-processor PATH`
(forwarded to `convert_trace_to_csv.py`, same name/meaning as that tool's own flag).

### Output directory layout

One `-o`/`--output-dir DIR` (default `profile_hotspots_trace-output-<timestamp>`), split into two
subdirectories — mirrors `profile_hotspots.sh`'s own `$OUTPUT_DIR/rocprof-sys`/`$OUTPUT_DIR/rocprofv3`
pattern:
- `$OUTPUT_DIR/scan` — passed as `instrument_hotspots.sh`'s own `-o` (the auto-profiling-scan
  directory; the fixed instrumented-binary copy lands here too).
- `$OUTPUT_DIR/trace` — passed as `instrument_hotspots.sh`'s own `--trace-output-dir`. The CSV
  files (`convert_trace_to_csv.py`), `hotspots.txt` (`extract_trace_hotspots.py`), and
  `calltree.txt` (`extract_trace_calltree.py`) are all written into this SAME directory — none of
  their own `-o`/output-dir flags are overridden, since each tool's own default is "write next to
  the input directory," which already is `$OUTPUT_DIR/trace` — so the whole trace-derived artifact
  set stays self-contained in one directory without this script needing to compute individual
  destination paths for each.

### `--trace-report DIR`: resuming from an existing trace

When given, this branch replaces the entire scan→instrument→trace sequence -- `instrument_hotspots.sh`
is never invoked at all, and `-- <executable> [args...]` is not required (any leftover positional
args are simply unused, not an error, matching how easy it is to leave a stale `-- ./app args...`
tail on a copy-pasted command). Existing-CSV detection: a plain glob check for at least one file
matching this project's trace-CSV naming convention directly under `DIR` (e.g.
`compgen -G "$DIR"/*-[0-9]*.csv`) -- good enough to distinguish "already converted" from "raw
`.proto` only" without needing bash to replicate `stage4_rocprofsys_trace_ranks._RANK_FILE_RE`'s
full regex precision; a false negative here just costs one redundant (idempotent) conversion run,
never wrong output. If no CSVs are found, runs `convert_trace_to_csv.py "$DIR"` (writing the CSVs
directly into `DIR`, in place) before continuing to the two `extract_trace_*.py` calls, same as the
normal path's `convert` step. Both `extract_trace_hotspots.py`/`extract_trace_calltree.py` then run
against `DIR` directly (no separate `$OUTPUT_DIR/scan`/`$OUTPUT_DIR/trace` split in this mode --
there was never a scan or a fresh trace to keep separate from).

### Composition mechanism

Subprocess invocation, not `source` — the exact mechanism `profile_hotspots.sh` already uses for
`profile_CPU_hotspots.sh`/`profile_GPU_hotspots.sh`. `profile_traced_hotspots.sh` calls
`instrument_hotspots.sh trace ...` once; then, non-fatal (`|| echo "warning: ..." >&2`, matching
`profile_hotspots.sh`'s own precedent for its post-processing steps — the expensive trace has
already been produced by this point, a post-processing failure shouldn't look like the whole run
failed), calls `convert_trace_to_csv.py`; then — only if that succeeded, since the two extract
tools have nothing to read otherwise — `extract_trace_hotspots.py` and `extract_trace_calltree.py`,
each independently non-fatal.

`--no-summary` additionally gates whether these three post-`instrument_hotspots.sh` steps run at
all (skip straight to "just get me the raw trace + binary" if given) — generalizing `--no-summary`'s
existing meaning ("skip auto-generated reports") from the scan-level report to the trace-level ones
too. `--dry-run` propagates through the whole chain, printing every step's command via the same
`printf '  %q ' ...` pattern every other script here already uses, without executing anything.

## Verification

No real ROCm/rocprof-sys/Perfetto tooling is available in this dev sandbox (standing project
constraint) — verification here is necessarily: `bash -n` on both scripts (syntax); manual
`--dry-run` invocations against a small placeholder executable exercising every new
flag-forwarding path (`--instrument-top` reaching `instrument_hotspots.sh`'s `--top`, bare `--top`
reaching the final report's own selection, `--trace-processor` reaching the converter,
`--no-summary` skipping all three post-processing steps, `--mpi` forwarding through) and confirming
the printed command lines are exactly right; `-h`/`--help` read-through against `CLAUDE.md`'s
conventions. `--trace-report DIR` specifically: a directory with only a placeholder `.proto` file
present (confirms the conversion step is included) and a second directory with a placeholder
`*-0.csv` file already present (confirms the conversion step is correctly skipped), plus one case
combining `--trace-report` with a clearly-conflicting flag (e.g. `--mpi`) to confirm the mutual-
exclusion error fires. Real end-to-end validation (an actual instrumented trace run) is the user's
own job on real hardware, same as every other script in this project.

## Divergences noted during implementation

- The normal (non-`--trace-report`) path's `--dry-run` output delegates to
  `instrument_hotspots.sh`'s own `--dry-run` (it's already in `INSTRUMENT_CMD` when `DRY_RUN=1`,
  so the script just runs it for real) instead of flattening the composed command into one
  `printf '%q '` line as originally sketched -- this mirrors `profile_hotspots.sh`'s own existing
  precedent (it does the same delegation to its two sub-launchers) and gives a far more detailed,
  accurate preview (the real `rocprof-sys-instrument`/`rocprof-sys-run` invocations, MPI expansion,
  etc.) than this script could reconstruct on its own.
- Testing surfaced a real bug in a helper this plan didn't anticipate needing: a `print_args`
  function guarding against `printf`'s own "%q still runs once on an empty array, printing a
  spurious `''`" quirk was itself written as `[[ $# -gt 0 ]] && printf ...`, which returns false
  (and, under this script's own `set -e`, silently kills the whole script) when called with zero
  arguments -- exactly the case it exists to guard. Fixed to always `return 0`. Caught by manual
  `--dry-run` testing with an empty selection-args array, exactly the scenario the plan's own
  Verification section called for.

Neither changes anything about the approach approved above.
