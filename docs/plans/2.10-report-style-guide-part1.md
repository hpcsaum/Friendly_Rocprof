# Plan 2.10: §10 report style guide, rules 1–5 & 7 (roadmap step 9, part 1 of 2)

> **As-built divergence:** a pre-commit review round changed several details from this plan's
> original design -- `standard_header()`'s signature became `(tool_name, description, runs)` (the
> `generated_line()`/`command_header()` two-line header collapsed into one first-line sentence, and
> the command line moved to the end of the footer instead); each `runs` entry's `directory` became
> a `directories` list, so one run can show a CPU+GPU directory pair under one shared metadata
> block; the single-titled-section case kept `=== Title ===` bracketing instead of going bare; a
> blank line was added between a table and its bulleted notes; and `extract_hotspots.py`'s
> CPU+GPU-pairing directory handling was unified with both calltree tools via a new
> `resolve_two_dirs()` helper, which this plan's original design didn't cover. See
> [docs/DEVELOPMENT_HISTORY.md](../DEVELOPMENT_HISTORY.md)'s Plan 2.10 section for the full
> as-built design.

## Context

Roadmap step 9 applies `docs/plans/2.1-postprocess-consolidation-refactor.md` §10's 7-rule report
style guide uniformly across all 6 report-writing tools — the first step where real report output
is *intentionally* allowed to change everywhere. Rule 6 (120-column hard-wrap + a new
`iter_table_rows()` reader, needed by `select_hotspot_functions.py`/`select_hotspot_kernels.py`'s
re-parsers) is split into its own follow-up, **Plan 2.11**, since it independently touches two
separate renderers (`stage5_table_render.py` and `stage5_tree_render.py`) plus both re-parsing
consumers — large and self-contained enough to review on its own. This plan covers rules 1–5 and 7.

**Two real gaps surfaced before drafting this plan, not in §10 itself, both about report content
living in the wrong place** — the same problem §10 exists to solve, just not named there:

1. **Table-owned prose scattered and duplicated across tools.** Several pieces of "footer"/
   "header" text currently hand-typed in a tool's `write_report()` actually explain what a
   *stage-5 table module* renders, not tool-specific business logic. Confirmed cases (direct
   comparison of all 6 tools' current `write_report()` bodies against every stage5 table module):
   - **Load-imbalance legend** — "Each function's/kernel's own [inclusive/self/total] time on each
     rank..." hand-typed at 4 call sites (`extract_CPU_hotspots.py`, `extract_GPU_hotspots.py`,
     twice in `extract_hotspots.py`) — all describing `stage5_load_imbalance_table.py`'s semantics.
   - **POP metrics "Metric explanation:" legend** — hand-written in `extract_pop_metrics.py`,
     branching on 4 booleans `stage5_pop_metrics_table.py`'s `pop_metrics_columns()` already
     computes for the same purpose (its own docstring already says so).
   - **Calltree aggregation legend** — *word-for-word identical* between `extract_calltree.py` and
     `extract_calltree_traced.py`'s footers, describing `stage5_tree_render.py`'s own
     `REPORT_HEADERS` convention.
   - **`%total`-meaning sentences** — not word-for-word duplicates (CPU hotspots, GPU hotspots, and
     `extract_hotspots.py`'s 4 tables each describe a genuinely different denominator), but still
     table-owned: `%total` is `select_entries()`'s own `threshold_field`/`threshold_unit`
     mechanism, and every sentence reduces to "`%total` is each X's share `{threshold_unit}`" with
     the same string already passed to `select_entries()`. Today each tool hand-types its own,
     so the two can (and already have) drift apart.
   - **Ranking-mode note** ("Ranked by self time.../inclusive time...") — same shape as the
     `%total` case: explains `select_entries()`'s `rank_field` choice, hand-typed independently in
     CPU hotspots and `extract_hotspots.py`.
   - **Calltree's noise-tier/max-depth/rank-list summary** ("Showing: GPU-API/runtime noise...
     hidden...", "max depth: N", "ranks aggregated: N (rank keys: ...)") — describes how *this
     tool's one tree/table* was filtered and assembled; belongs beside `stage5_tree_render.py`'s
     other per-report explanatory text, not hand-typed per calltree tool.
2. **Metadata/header consolidation Plan 2.8 flagged and deferred here.** Plan 2.8 kept
   `gather_run_info()`'s *content* (which keys/constants each tool guesses from) tool-owned, but
   flagged its *presentation* — each tool hand-building its own header block — as a step-9 item.
   On review, this generalizes further than "CPU/GPU hotspots share a block": **every tool's
   header reduces to the same handful of facts** — which tool wrote it, its own invocation, one or
   more source directories each with an optional executable/runtime/rank-count/scanned-files, and
   (automatically, from the section list) which tables the report contains. One shared function
   renders all 6 tools' headers; each tool just describes its own facts.

## Approach

### 0. The standard header — one function for all 6 tools

New function in `stage6_report_builder.py` (alongside the new `generated_line()`/
`command_header()`/`help_redirect()` helpers from rules 5/7 below):
```python
def standard_header(tool_name, command_line, runs):
    """The metadata block every report shares: which tool wrote it (tool_name, e.g.
    "extract_CPU_hotspots.py"), when (generated_line()), its own invocation (command_line, from
    command_header() -- "" if a tool has none to give), and one or more runs it read data from.

    Each entry in runs is a dict: {"label", "directory", "executable", "run_datetime", "runtime",
    "num_ranks", "scanned_files", "extra_lines"}. Only "label" and "directory" are required --
    every other field is optional and prints blank/omitted when absent, the same "never error on
    missing metadata" convention gather_run_info() already follows. "scanned_files" (a list of
    paths, or omit the key entirely for a tool with no such list) renders as an indented bullet
    list, paths relative to that run's own directory. "extra_lines" (a list of pre-formatted,
    already-indented strings, or omit) is an escape hatch for the rare fact that doesn't fit this
    shape at all (e.g. a calltree tool's separately-resolved CPU/GPU data subdirectories).

    One run for CPU/GPU hotspots and both calltree tools; two for the combined hotspots tool (CPU
    + GPU sides); 1+N for extract_pop_metrics.py (reference + any scaling-study directories). 2+
    runs automatically get one trailing caveat noting they aren't cross-checked against each other
    -- true whenever multiple independent directories feed one report, regardless of which tool,
    so it's generated here once instead of hand-typed by whichever tool happens to need it today.
    """
    parts = [f"tool: {tool_name}\n", generated_line()]
    if command_line:
        parts.append(command_line)
    for run in runs:
        parts.append(f"{run['label']}: {os.path.abspath(run['directory'])}\n")
        parts.append(f"  executable: {run.get('executable') or ''}\n")
        parts.append(f"  run date/time: {run.get('run_datetime') or ''}\n")
        parts.append(f"  runtime: {run.get('runtime') or ''}\n")
        parts.append(f"  MPI ranks: {run['num_ranks'] if run.get('num_ranks') is not None else ''}\n")
        if "scanned_files" in run:
            parts.append("  files scanned:\n")
            parts.extend(f"    - {os.path.relpath(f, run['directory'])}\n" for f in run["scanned_files"])
        parts.extend(run.get("extra_lines") or [])
    if len(runs) > 1:
        parts.append(
            f"note: the {len(runs)} directories above are not checked against each other "
            "(same executable/test case/run) -- that's the caller's responsibility.\n"
        )
    parts.append("\n")
    return "".join(parts)
```
This **replaces** every tool's current hand-built header string entirely (the old descriptive
title sentences like `"rocprof-sys hotspots report (CPU-side only)"` are dropped in favor of the
plain `"tool: extract_CPU_hotspots.py"` line — `--help` already covers what the tool does, per
rule 5's philosophy of pushing descriptive prose out of the report). Worked examples:

- `extract_CPU_hotspots.py`: one run — `runs = [{"label": "source directory", "directory":
  output_dir, "executable": run_info["executable"], "run_datetime": run_info["run_datetime"],
  "runtime": run_info["total_runtime"], "num_ranks": run_info["num_ranks"], "scanned_files":
  scanned_files}]`. (This also fixes a latent inconsistency in passing: today's CPU hotspots shows
  bare basenames in "files scanned:", silently dropping nested-subdirectory info a real scan can
  have — see the `mpi_2rank_dated_subdir` fixture — while GPU hotspots already shows the more
  informative relative path; the shared function adopts the relative-path form for both.)
- `extract_hotspots.py`: two runs (CPU side, GPU side), each with its own executable/run_datetime/
  runtime/num_ranks — no `scanned_files` key for either (unchanged, it never had one). The 2-run
  case's automatic cross-check caveat replaces today's hand-typed "the two directories above are
  not checked against each other" sentence exactly.
- `extract_pop_metrics.py`: 1+N runs (reference + any scaling-study directories), each with just
  `num_ranks` (no per-run executable/runtime metadata today — those keys are simply omitted,
  printing blank, same convention as everywhere else). The auto-generated 2+-run caveat is new
  information for this tool (true today, just never stated) — a genuine, welcome side effect of
  unifying rather than scope creep.
- `extract_calltree.py`/`extract_calltree_traced.py`: one run — `{"label": "source directory",
  "directory": run_dir, "num_ranks": len(rank_keys), "extra_lines": [f"  CPU data:
  {os.path.abspath(cpu_dir)}\n", f"  GPU data: {os.path.abspath(gpu_dir) if view['gpu_paired']
  else '(none)'}\n"]}` — no executable/runtime (these tools never guess them; the fields simply
  print blank). `extra_lines` is exactly the "fact that doesn't fit the fixed shape" this field
  exists for: the two already-resolved subdirectory paths, distinct from a second independent run.

**Auto-generated "tables:" listing.** `render_report()` (rule 2/3/4 section below) already knows
every section's plain-text title once rules 2–4 land; it lists them right after `header`, before
the first section body, generated once instead of any tool separately maintaining a summary:
```python
titled_titles = [title.rstrip("\n") for title, _body in sections if title]
if titled_titles:
    parts.append("tables:\n" + "".join(f"  - {t}\n" for t in titled_titles) + "\n")
```
(0 titled sections — both calltree tools' untitled tree/fallback blocks — means no "tables:" line
at all, which is honest: a call tree isn't really a list of named tables.)

### 2. Relocate table-owned prose into its owning stage5 module

**`stage5_table_render.py`** — two new functions, next to `select_entries()`/`render_table()`:
```python
def pct_total_note(entry_noun, threshold_unit):
    """Bulleted note explaining what this table's %total column means -- threshold_unit is the
    exact same string already given to select_entries() (its "showing top N ... {threshold_unit}"
    line and this note now share one source, so they can't drift the way this codebase's 4
    hand-typed %total sentences already have -- e.g. extract_hotspots.py's 4 tables all pass
    select_entries() the same generic threshold_unit="of total runtime" today despite each table
    meaning a genuinely different denominator)."""
    return f"  - '%total' is each {entry_noun}'s share {threshold_unit}.\n"

def ranking_note(unfiltered, extra_clause=""):
    """Bulleted note explaining which time basis (self vs. inclusive) ranked this table --
    extra_clause lets a caller append one more tool-specific sentence (e.g. extract_hotspots.py
    noting GPU kernels are unaffected, already leaf events)."""
    basis = (
        "inclusive (total) time -- a function that just calls other functions can still rank high"
        if unfiltered else
        "self time -- each function's own work, not counting time spent in whatever it calls, so "
        "pass-through functions fall out of the ranking on their own"
    )
    return f"  - Ranked by {basis}.{extra_clause}\n"
```
Each tool tightens its own `select_entries()` calls' `threshold_unit` to the real, accurate
denominator description for that table (a genuine content correction, not just a refactor —
today's generic `"of total runtime"` is actively wrong for 3 of `extract_hotspots.py`'s 4 tables),
then reuses that exact string in `pct_total_note()`. Representative values: CPU/GPU hotspots' own
tools keep `"of total measured [GPU] time (summed across all scanned files)"`;
`extract_hotspots.py`'s 4 tables become `"of the combined pool above (double-counting-corrected)"`
(table 1), `"of the CPU run's own total (not the combined pool)"` (tables 2 and 4), `"of the GPU
run's own total (not the combined pool)"` (table 3). `ranking_note()` is called once per table that
`select_entries()` ranked by self/inclusive time — CPU hotspots' 2 tables (each gets its own bullet
copy, same one-liner) and `extract_hotspots.py`'s table 2 (with `extra_clause=" GPU kernels are
unaffected (already leaf events)."` on its own fused-table note, if still needed once table 1's
wording is reviewed against this). Any further tool-specific clarification (CPU/GPU hotspots'
"won't add to 100% across both tables" / "if a --threshold/--top cut entries"; table 4's "only 2 of
these calls are subtracted from table 1's pool" nuance; table 1's Combined-pool arithmetic
breakdown) becomes its own additional bulleted line(s) after these, per rule 4's "a table can have
several bullets under it" — no information lost by splitting the generic, parameter-driven
sentence from tool-specific extra content.

**`stage5_load_imbalance_table.py`** — new function, placed next to `load_imbalance_columns()`:
```python
_VERB_BY_LABEL = {"function": "called", "kernel": "launched"}

def imbalance_note(item_label, time_kind):
    """Bulleted note explaining this table's per-rank convention -- item_label is "function" or
    "kernel" (matches load_imbalance_columns()'s own item_label), time_kind is "self"/"inclusive"
    (CPU tool, selected by --unfiltered) or "total" (GPU tool, no self/inclusive split since a
    kernel has no callees)."""
    verb = _VERB_BY_LABEL[item_label]
    return (
        f"  - Each {item_label}'s own {time_kind} time on each rank, compared across ranks -- a "
        f"rank that never {verb} a {item_label} counts as 0.0 for that rank, not omitted.\n"
    )
```
Called as `imbalance_note("function", "inclusive" if unfiltered else "self")` (CPU hotspots, both
its own tool and `extract_hotspots.py`'s CPU section) and `imbalance_note("kernel", "total")` (GPU
hotspots, both its own tool and `extract_hotspots.py`'s GPU section) — 4 call sites, one function.

**`stage5_pop_metrics_table.py`** — new function `metrics_legend(show_gpu_cols, show_gpu_eff,
multi_run, scaling)`, inserted between `pop_metrics_columns()` and `format_metrics_table()`.
Body is `extract_pop_metrics.py`'s current "Metric explanation:" block moved verbatim (same
bullets, same branching on the same 4 inputs) — a pure relocation, no wording change. The tool
calls it with the exact `show_gpu_cols`/`show_gpu_eff` `format_metrics_table()` already returns,
plus its own `multi_run`/`scaling` it already computes.

**`stage5_tree_render.py`** — two new functions:
```python
def aggregation_note():
    """Bulleted note explaining the per-rank aggregation convention every rendered tree in this
    codebase shares -- identical for both calltree tools."""
    return (
        "  - Every row is aggregated across all ranks (not one call tree per rank): calls and\n"
        "    total-avg(s) are plain averages; self gets a full avg/std_dev/min/max load-balance\n"
        "    breakdown, the same convention this codebase's other load-imbalance tables use -- a\n"
        "    rank that never reached a given node counts as 0 there, not omitted, so real\n"
        "    imbalance (e.g. a function only some ranks call) isn't hidden by averaging.\n"
    )

def tree_view_note(rank_keys, max_depth, show_gpu_api, show_rocprofsys_internals=None,
                    show_mpi_internals=None, show_compiler_runtime=None):
    """Bulleted note summarizing how this specific tree was filtered/truncated -- the 3
    internals flags default to None (omitted from the summary) for extract_calltree_traced.py,
    which only has show_gpu_api; extract_calltree.py passes all 4."""
```
(column names in `aggregation_note()` lowercased per rule 1, since this text is new). `rank_keys`'s
listing (today's "(rank keys: ...)" aside) and the noise-tier/max-depth summary (today's
"Showing: ..."/"max depth: N" lines) both move into `tree_view_note()`, called once each by
`extract_calltree.py` (all args) and `extract_calltree_traced.py` (only `show_gpu_api`).

### 3. Rules 2+3+4 — dynamic section numbering, and notes move after the table

**The core mechanism change** is in `stage6_report_builder.py`'s `render_report()`. Today a
section's `title` is a fully pre-decorated string (some tools hand-write `"=== N. ... ===\n"`,
others a bare sentence) and any table note gets wedged wherever the tool's code happens to
`parts.append()` it — sometimes before the table (rule 3 violation). Going forward, `title` is
**plain, undecorated text** (a bare sentence, still ending in `\n`, no `===`, no number), and
`render_report()` decides the decoration itself, once, for the whole report:

```python
def render_report(header, sections, footer=""):
    titled = [(title, body) for title, body in sections if title]
    parts = [header]
    if titled:
        parts.append("tables:\n" + "".join(f"  - {t.rstrip(chr(10))}\n" for t, _b in titled) + "\n")
    numbered = 0
    for title, body in sections:
        if title:
            if len(titled) >= 2:
                numbered += 1
                parts.append(f"=== {numbered}. {title}")
            else:
                parts.append(title)
        parts.append(body)
        parts.append("\n")
    if footer:
        parts.append(footer)
    return parts
```
(`title` strings drop their own trailing `" ===\n"`/`"\n"` in favor of one shared spot — exact
string-building detail to finalize during implementation, not a design question.) This gives:
- 0 titled sections in the list (e.g. calltree's untitled tree/fallback blocks) → no `tables:`
  line, no numbering, behavior unchanged for those sections.
- exactly 1 titled section → bare sentence, no `===` (fixes pop_metrics' single
  over-bracketed "=== Metrics ===" section — see below — and matches CPU/GPU hotspots' *single*-
  titled-section case, e.g. GPU hotspots when its imbalance section has no title).
- 2+ titled sections → each gets `=== N. Title ===`, numbered by its position among *titled*
  sections only (untitled prose in between, e.g. CPU hotspots' GPU-timing note, doesn't consume a
  number) — this is what makes the numbering genuinely dynamic instead of hand-typed, closing the
  exact gap rule 2 calls out ("computed dynamically per report, not hardcoded").

**Skip-message sections change shape to fit this.** Today's skip case (e.g. "only 1 rank/file
found") sets `title=None` and folds the whole message into `body` — which worked before but can't
participate in dynamic numbering. Going forward the skip message becomes the section's real,
countable title with an empty body:
```python
if len(imbalance_scanned) < 2:
    imbalance_title = f"CPU load imbalance across ranks -- skipped: only {len(imbalance_scanned)} rank/file found, need at least 2 to compare\n"
    imbalance_body = ""
```
`render_report()`'s existing per-section shape (title, blank-line-producing body, blank line)
degrades cleanly to just "title line, one blank line" when body is `""`.

**Rule 3+4 together**: any note currently wedged between a section's title and its table moves to
*after* the table, converted to a `"  - "`-bulleted line (or lines) — the relocated legends above
already return their bulleted form ready to append. Fully worked example,
`extract_CPU_hotspots.py`'s section 2 (today: title, then a bare wedged sentence, then the table):
```python
(
    "GPU API / launch overhead -- showing {gpu_desc}\n",
    render_table(CPU_HOTSPOTS_COLUMNS, gpu_selected)
    + "  - host-side call overhead only -- NOT device kernel execution time\n"
    + ranking_note(unfiltered)
    + pct_total_note("function", threshold_unit)
),
```
Its section-4 (imbalance) note becomes `render_table(...) + imbalance_note("function", ...)`
appended the same way, dropping the old wedged sentence entirely. `extract_hotspots.py`'s table 1
additionally appends its "Combined-pool arithmetic" breakdown (unique to that tool, stays as its
own tool-owned bulleted block, just repositioned after the table instead of living in the header).
The same table→then→bulleted-notes reshuffle applies to `extract_GPU_hotspots.py`'s single wedged
note and the rest of `extract_hotspots.py`'s wedged sentences. `pop_metrics_table.py`'s
`format_metrics_table()` drops its self-drawn `"=== Metrics"`/`"==="` wrapping (now redundant with
rule 2's single-section bare-sentence case) in favor of a bare `f"Metrics{scaling_suffix}\n"` title
string, still returned pre-baked inside `table_text` exactly as today (an opaque, always-one-
section block, per Plan 2.8's existing precedent — it never goes through `render_report()`'s
numbering/`tables:`-listing logic at all, since it's structurally incapable of having a 2nd
section). Calltree tools' `tree_view_note()`/`aggregation_note()` output is appended after the
tree section's body the same way (title stays `None` — a tree isn't a titled table — so this note
sits inside an untitled section's body, not under a `=== N. ===` header).

- **`extract_CPU_hotspots.py` / `extract_GPU_hotspots.py` / `extract_hotspots.py`**: confirmed no
  redirect-eligible content — none has a labeled general-methodology footer today; their remaining
  post-relocation footer text (proto/db file listings, the GPU-hotspots-tool pointer) is per-run
  data or already a cross-tool pointer, not something `--help` could say instead. No change here.

### 5. Rule 7 — a `command:` header line

New function in `stage6_report_builder.py`:
```python
def command_header(argv0, tokens, width=100):
    """Builds the report's 'command:' line: sys.executable + this script's own absolute path,
    followed by tokens -- CLI arguments the tool itself already assembled from its parsed
    argparse Namespace (never raw sys.argv, which can't tell a user-typed relative path from a
    coincidentally-identical option value elsewhere in the command). Wraps onto one continuation
    line, indented to align under the first token, once the line would exceed width columns."""
```
Each tool's `main()` builds its own small `tokens` list right after `parser.parse_args(argv)` —
this is the "small per-tool list" §10 already calls for, just generalized from path-only to every
argument, since reconstructing a runnable command line needs the non-path flags too (e.g.
`--top 10`), and un-parsing an arbitrary `argparse.ArgumentParser` generically (positionals vs.
flags vs. `nargs="*"` vs. mutually-exclusive groups) is far riskier than each tool listing its own
handful of fixed, known arguments explicitly. Worked example, `extract_CPU_hotspots.py::main()`:
```python
tokens = [os.path.abspath(args.output_dir)]
if args.dest:
    tokens += ["-o", os.path.abspath(args.dest)]
if args.top is not None:
    tokens += ["--top", str(args.top)]
elif args.threshold is not None:
    tokens += ["--threshold", str(args.threshold)]
elif args.show_all:
    tokens += ["--all"]
if args.unfiltered:
    tokens += ["--unfiltered"]
command_line = command_header(sys.argv[0], tokens)
write_report(args.output_dir, dest, top=args.top, threshold=args.threshold, show_all=args.show_all,
             unfiltered=args.unfiltered, command_line=command_line)
```
`write_report()` passes `command_line` straight into `standard_header(tool_name, command_line,
runs)` above — no separate threading needed, it's already one of that function's 3 parameters.
Every tool defaults `command_line=""` when not supplied, so existing programmatic/test callers
