# Plan 3.5+3.6 (merged): the canonical per-rank trace aggregate, its on-disk cache, and thin flat/tree consumers

> **Divergence found during implementation**: this plan says `stage4_rocprofsys_common.merge_rank_trees()`
> is "imported unchanged" — that turned out to be impossible as written. The function hardcodes
> `row["label"]`, but trace rows are keyed by `"name"` (per the earlier, deliberate decision *not*
> to alias/mutate trace rows into a `label` key — see plan 3.4). Resolved the same way plan 3.4
> resolved the identical tension for `tag_rows()`: `merge_rank_trees()` gained a `label_key="label"`
> parameter (default preserves every existing sample-pipeline caller unchanged;
> `stage4_rocprofsys_trace_aggregate.py` passes `label_key=stage1_rocprofsys_trace.LABEL_KEY`).
> Recorded in `docs/DEVELOPMENT_HISTORY.md`.

> **Second divergence, found while testing plan 3.7**: `build_rank_aggregate()`'s ordering
> (`tag_rows()` before the `corr_id` join) had a real bug — an untethered kernel-dispatch row is a
> "root" until the join reparents it, and `tag_rows()`'s own sibling-group derivation compares
> every root at the top level as siblings, wrongly flagging a real CPU thread root's entire subtree
> as `wrapper_branch_noise`-contaminated whenever one existed alongside it. Fixed by moving
> `tag_rows()` to run *after* the join; the join itself uses `tag_for_category()` directly (a
> stateless per-row lookup) instead of needing `row["tags"]` already populated. Recorded in
> `docs/DEVELOPMENT_HISTORY.md`.

## Context

Roadmap steps 3.5 ("stage4-equivalent: flat + tree") and 3.6 ("on-disk aggregate cache") from
`docs/plans/3.1-trace-postprocessing-family.md` were sequenced as two separate plans, one after the
other. Re-reading that doc surfaces a real internal inconsistency between two of its own sections:
the module breakdown (§"Proposed new modules") describes `stage4_rocprofsys_trace_flat.py` as its
own independent by-label accumulator "fed by the trace reader" directly — i.e., re-parsing/
re-deriving from raw rows on its own — while the caching design (§"Caching design") says "**both**
the calltree tool and hotspots tool read the *same* cache file... rather than maintaining two
separate aggregate formats for the same underlying data." Those two sections don't actually agree:
if flat has its own independent accumulation path, either it duplicates the expensive parse+merge
work the tree path already paid for, or the caching design's "same cache file" claim was aspirational
and never actually wired up. Sequencing 3.6 (caching) *after* 3.5 (build flat+tree against raw data)
makes this worse, not better — caching would be bolted onto whatever functions 3.5 already built,
rather than the cached shape being designed first and everything else built to consume it.

Directed correction for this plan: **the aggregated table must be tool-independent — no filtering,
no dropped rows, no tool-specific renaming — and stage4's own later derivation steps (flat entries,
per-rank breakdowns, the cross-rank merged tree, POP-metrics timing summaries) must be able to read
it directly as input, instead of a still-unaggregated trace.** Concretely: there is exactly **one**
expensive step (parsing a 10GB+ CSV, tagging, and merging repeated same-position calls within a
rank), and everything downstream of it — for every report kind — is a cheap, pure derivation from
its output, never a second pass over raw rows.

**A real, relevant precedent found while researching this, deliberately not followed here**:
`stage4_rocprofsys_sample_flat.scan_ranks()` (the *existing*, already-shipped sample-pipeline
equivalent) bakes noise-tag filtering directly into its per-rank scan — it drops
`wrapper_noise`/`compiler_runtime_noise`/`other`/ancestor-only-`mpi_territory` rows before any tool
ever sees them (`stage4_rocprofsys_sample_flat.py:65-75,106-117`). That's exactly the anti-pattern
this plan avoids: the new trace aggregate keeps every row and every tag, unfiltered, for every
consumer — which tags a given tool hides/splices/collapses stays a stage5/6 decision, same
separation `stage3_rocprofsys_trace.py` already established for classification vs. action.
Refactoring `scan_ranks()` itself to match is a real, separate follow-up, deferred out of this plan
by direct instruction — its own filtering-vs-classification split touches the existing, shipped
CPU-hotspots/load-imbalance/POP-metrics tools and deserves its own plan, not a rider on this one.

**Second directed correction, also folded in here**: every generic function this new pipeline
calls from `stage4_rocprofsys_sample_tree.py` should move to a shared common module first — the
same move already made for stage3 (`stage3_rocprofsys_sample.py` → `stage3_rocprofsys_common.py` in
plan 3.4) — rather than having the trace pipeline import from a module named for the other
pipeline. See "`stage4_rocprofsys_common.py` split" below.

## Approach

### The canonical per-rank aggregate = the already-documented "tree node" shape, flattened

`postprocess/README.md`'s stage4→5 contract (written in plan 3.2) already names the canonical
tree-node shape: `{label, parent, children, per_rank, tags, structural_drop_tags, static_children}`
— exactly `stage4_rocprofsys_sample_tree.merge_rank_trees()`'s own native output. This plan's
cached artifact is that same shape, for **one rank**, flattened back into a parent-linked list
(top-level `count`/`self_sum`/`sum` instead of nested `per_rank[rank_key]`) — both because it's the
one shape every downstream need (cross-rank tree merge, flat-by-label grouping, per-rank
label→value, per-rank timing summary) can be cheaply derived from, and because a flat list is the
natural shape to serialize.

Explicit scope of "no filtering/dropping/renaming": every tag (including noise tags) stays on every
row; nothing is excluded because some particular tool won't want it. The one legitimate reshape that
does happen — the raw CSV's display-name column (`stage1_rocprofsys_trace.LABEL_KEY`, i.e. `"name"`)
becoming the canonical `"label"` key — is not a loss, it's the one universal rename *every* consumer
needs, landing exactly where plan 3.3 already said this kind of decision belongs (a later stage4
module, not the parser). GPU-dispatch-detail columns (`grid_size`, `workgroup_size`, ...)
deliberately do **not** survive the intra-rank merge: once N raw launches at one call site collapse
into a single count, there's no one meaningful "the" grid size to keep, and no current stage5 view
consumes these anyway — an explicit, stated scope boundary, not an oversight, revisited if/when a
GPU-detail view is ever designed.

### Prerequisite refactor: `stage4_rocprofsys_common.py` split

Mirrors plan 3.4's `stage3_rocprofsys_sample.py` → `stage3_rocprofsys_common.py` move exactly, for
the same reason: verified directly against `stage4_rocprofsys_sample_tree.py`'s source, five of its
functions are already fully generic (no sample/rocprofv3-format coupling) and are exactly the ones
this new pipeline needs — `merge_rank_trees()`, `flatten_tree()`, `caller_chains_for_label()`,
`aggregate_node_stats()`, `make_node_values()`. The rest of that file
(`load_rank_trees()`/`kernel_totals_with_counts()`/`pair_gpu_per_rank()`/`attach_gpu_kernels()`/
`attach_kernel_summaries()`/`kernel_owner_label()`/`find_kernel_anchors()`/`_attach_kernel_group()`/
`unattached_kernel_per_rank()`/`is_kernel_launch()`/`KERNEL_LAUNCH_LABEL_SUBSTRINGS`/
`make_kernel_node()`/`nearest_visible_ancestor()`) is genuinely sample/rocprofv3-specific — the
heuristic kernel-to-launch-site attachment machinery this plan's exact `corr_id` join replaces
entirely — and stays where it is, unmoved.

`git mv` is not applicable here (only part of a file moves) — instead: create
`postprocess/stage4/stage4_rocprofsys_common.py` with the five functions relocated verbatim (byte-
identical bodies), a docstring naming both `stage4_rocprofsys_sample_tree.py` and this plan's new
trace modules as consumers, and update every real import site (confirmed exhaustive via direct
grep — comment-only mentions of `stage4_rocprofsys_sample_tree.merge_rank_trees()` etc. elsewhere
are left as accurate history, same treatment plan 3.4 gave old comment references):
- `postprocess/stage5/stage5_calltree_view.py` — its `from stage4_rocprofsys_sample_tree import
  (...)` block splits: `attach_gpu_kernels`/`load_rank_trees`/`pair_gpu_per_rank` stay imported from
  `stage4_rocprofsys_sample_tree`; `flatten_tree`/`make_node_values`/`merge_rank_trees` move to a new
  `from stage4_rocprofsys_common import (...)`.
- `postprocess/stage5/stage5_wallclock_calltree_view.py` — same split (no
  `caller_chains_for_label` import here).
- `postprocess/tools/extract_hotspot_callers.py` — same split, plus `caller_chains_for_label` also
  moves to the new `stage4_rocprofsys_common` import.
- `stage4_rocprofsys_sample_tree.py`'s own docstring/function list updated to drop the five moved
  functions and note it now imports them back from `stage4_rocprofsys_common` for its own use
  (`load_rank_trees()` still calls into structures those functions build).

Verification for this sub-step alone: existing
`postprocess/tests/stage4/test_stage4_rocprofsys_sample_tree.py` splits the same way
`test_stage3_rocprofsys_common.py` did — the five moved functions' tests relocate to a new
`test_stage4_rocprofsys_common.py`, the rest stay — full suite must stay green immediately after
this move, before any new trace code is written, same discipline as every other pure-relocation
step in this project.

### New module: `postprocess/stage4/stage4_rocprofsys_trace_aggregate.py`

**`build_rank_aggregate(csv_paths, rank_key)`** — the one expensive path, in order (order matters,
see step 3):
1. `stage1_rocprofsys_trace.parse_trace_csv()` + `attach_ancestry()` — unchanged.
2. `stage3_rocprofsys_trace.tag_rows()` — unchanged.
3. Per-row `self_sum`/`count`/`sum` synthesis: `count = 1`, `sum = dur`, `self_sum = dur` minus the
   sum of *structural* children's `dur` (children as Perfetto/stage1 already resolved them, via
   `parent_slice_id`) — the shape plan 3.3 explicitly deferred to "a later stage4 module." **Must
   run before step 4**: a `rocm_kernel_dispatch` row about to be reparented onto its launch site
   (step 4) isn't nested in wall-clock time the way a true structural child is (the GPU dispatch
   typically executes concurrently with, not strictly inside, the host launch call) — computing
   `self_sum` afterward would wrongly subtract a concurrently-running kernel's duration from its
   launcher's own self time.
4. corr_id-based kernel attachment: for every untethered (parent is `None`) `gpu_kernel`-tagged row
   with a non-`None` `corr_id`, find the row(s) tagged `gpu_api` sharing that same `corr_id`. Exactly
   one match → reparent the kernel-dispatch row onto it directly (`row["parent"] = match`) — a real
   structural edit, simpler than the existing sample-pipeline's `attach_gpu_kernels()`/
   `attach_kernel_summaries()` machinery (which grafts a *synthetic* `static_children` subtree
   precisely because rocprofv3's `kernel_stats.csv` carries no real tree position at all — `corr_id`
   gives trace data an exact one, so the dispatch row just becomes a normal child; no proportional
   weight-splitting needed). Zero matches → leave it as its own root, no guessing, matching
   `stage1_rocprofsys_trace.attach_ancestry()`'s existing "don't guess a parent" precedent. More than
   one match → warn once per rank (count-based, matching that same module's warning style) and leave
   unattached — guessing would defeat the entire point of an *exact* join.
5. Recompute `roots = [r for r in rows if r["parent"] is None]` — **after** step 4's reparenting,
   not reused from before it, since reparenting removes affected rows from the root set.
6. `stage4_rocprofsys_common.merge_rank_trees([(rank_key, rows, roots)])` (see the common-module
   split above), imported **unchanged**. Confirmed directly against its source: its loop body has no
   special-casing for `len(ranks) > 1` — feeding it one rank's tuple performs exactly the same
   by-`id(parent)`+`label` merge it already does across ranks, collapsing repeated same-position
   calls within that one rank (the "500 identical `hipLaunchKernel` siblings become one merged node"
   case plan 3.1 already flagged, now placed concretely rather than just asserted).
7. New (~15 lines) reshape function — call it `_flatten_rank_merge(merged_roots, rank_key)` — calls
   `stage4_rocprofsys_common.flatten_tree()` (unchanged) on the single-rank merged tree and pulls
   each node's one `per_rank[rank_key]` entry back out to top-level `count`/`self_sum`/`sum`,
   producing a flat, parent-linked row list. This is the concrete design for the "new glue function"
   plan 3.1 already flagged as the one real gap in "stage4 is reusable as-is" (a reshape between two
   `merge_rank_trees()` calls, since its input shape and output shape differ). **This flat list is
   the cached aggregate.**

**`get_rank_aggregate(csv_paths, rank_key, cache_dir=None)`** — the cache-aware wrapper every other
new module calls instead of `build_rank_aggregate()` directly:
- `cache_dir` defaults to the directory of the first `csv_paths` entry (cached alongside the raw
  CSV, per plan 3.1's decision).
- Cache file: `<cache_dir>/<rank_key>.agg.json` — keyed on `rank_key`, not source filename(s), since
  one rank's input can be a single file or a category-partitioned set (plan 3.1's "gpu/mpi/other"
  split), and `rank_key` is the one identity stable across either shape.
- Valid cache (exists, mtime ≥ every `csv_paths` entry's mtime) → decode and return. Missing or
  stale → `build_rank_aggregate()`, write the cache, return the fresh rows.
- Encode/decode boundary (genuinely new — confirmed by direct search that no set-to-JSON or
  cache-file convention exists anywhere in this codebase today): `tags`/`structural_drop_tags` sets
  → sorted lists on write, `set(...)` on read; `parent` object references → each row's own position
  (integer index) in the flat list on write, resolved back to real dict references on a two-pass
  read (build every row dict first, then wire `"parent"` by index) — the same index/lookup
  indirection `stage1_rocprofsys_trace.py` already uses for `slice_id`, just a fresh index since
  `slice_id` doesn't survive the merge.
- Any read failure (corrupt JSON, unexpected schema) → fall back to a fresh build rather than raise,
  matching `stage6_run_metadata.load_json_file()`'s "best-effort, never raises" convention — the one
  prior-art style worth carrying over, even with no cache-specific code in this repo to copy.

### Cross-rank consumers become genuinely thin

**`postprocess/stage4/stage4_rocprofsys_trace_tree.py`** *(new)*: given N per-rank aggregates (each
via `get_rank_aggregate()` — fresh or cached, indistinguishable to this code), recomputes each rank's
`roots` and calls `stage4_rocprofsys_common.merge_rank_trees()` a **second** time, across ranks — the
same function, unchanged, now merging already-deduped per-rank rows instead of raw ones. No
kernel-attachment step of its own needed here at all: `corr_id` joining already happened per-rank
inside `build_rank_aggregate()`, so by the time this runs, kernel-dispatch nodes are already ordinary
children. Feeds the **unchanged** `stage5_tree_render.py` rendering functions directly.

**`postprocess/stage4/stage4_rocprofsys_trace_flat.py`** *(new)*: given the same N per-rank
aggregates, three pure reductions — no re-parsing, no re-tagging:
- a global flat-entry list (group by `label` across every rank) — the flat-entry canonical shape.
- a per-rank `{label: value}` breakdown, one dict per rank — the per-rank-label→value shape, feeding
  `stage5_load_imbalance_table.compute_load_imbalance()` **unchanged**.
- a per-rank timing-summary list (`{rank_key, total_time, comm_time, gpu_busy_time, ...}` —
  `comm_time` from summed `self_sum` of `mpi_territory`-tagged rows, `gpu_busy_time` from
  `gpu_kernel`-tagged rows, `total_time` from each rank's root `sum`) — feeding
  `stage5_pop_metrics_table.compute_metrics_from_per_rank()` **unchanged**, already generalized for
  exactly this shape by plan 3.2.

This is the actual resolution of the original tangle: there is exactly one place the expensive work
happens (`stage4_rocprofsys_trace_aggregate.py`), and both consumer files are cheap, tool-independent
derivations from its output — matching the "later stage4 steps read the table directly" requirement
literally, not just in spirit.

### Explicitly out of scope for this plan

Multi-rank file discovery/glob conventions for a real trace-CSV output directory — no real multi-rank
trace data exists yet to confirm an actual naming scheme against (unlike the sample pipeline's
`PID_SUFFIX_RE`, built against real rocprof-sys output). `get_rank_aggregate()` takes explicit file
path(s) plus a caller-supplied `rank_key`; wiring a real directory scan into per-rank groupings is
deferred to roadmap step 3.7 (stage5/6 composition), which needs that wiring anyway to build the
actual CLI tools. GPU-dispatch-detail preservation through the merge (see above). Any `{tag: action}`
wiring — still stage5/6's job, unchanged principle from plan 3.4. Refactoring
`stage4_rocprofsys_sample_flat.scan_ranks()` to drop its own baked-in noise filtering — deferred by
direct instruction to its own future plan.

### Tests

New fixtures under `postprocess/tests/fixtures/` (small, hand-crafted trace-CSVs, extending the
`trace_single_rank`-style convention from plan 3.3):
- A multi-instance fixture: the same call site (e.g. `jacobi_sweep` → `hipLaunchKernel`) repeated
  several times with distinct `slice_id`s/timestamps, to exercise the intra-rank collapse (one
  merged node, `count` > 1, `self_sum`/`sum` summed).
- A `corr_id`-linked HIP-launch/kernel-dispatch pair (exact match — one candidate), a kernel
  dispatch row with a `corr_id` matching *no* `gpu_api` row (exercises the "leave as root" path), and
  a deliberately ambiguous case (two `gpu_api` rows sharing one `corr_id`, exercises the warn-and-skip
  path).
- Two small per-rank fixtures for the cross-rank merge/flat/timing-summary tests.

Unit tests (mirroring `postprocess/tests/stage4/`), beyond the common-module-split verification
already covered above, for: `build_rank_aggregate()`'s self_sum correctness and corr_id-join
behavior (all three cases above); `get_rank_aggregate()`'s cache hit/miss/stale-invalidation
behavior (a hit must not re-invoke `build_rank_aggregate()` — verified via a monkeypatch/counter,
not just "returns the right data," since the whole point is skipping the expensive path); the
encode/decode round-trip (sets, parent-by-index) preserving every field exactly;
`stage4_rocprofsys_trace_tree.py`'s cross-rank merge output shape checked against the documented
tree-node contract field-by-field; `stage4_rocprofsys_trace_flat.py`'s three derivations checked
against their respective documented shapes, and against
`compute_load_imbalance()`/`compute_metrics_from_per_rank()` actually accepting their output without
modification.

## Verification

`python3 -m unittest discover -s tests` from `postprocess/`: existing suite stays green (no existing
file touched — this plan is new modules only, same discipline as plans 3.3/3.4), plus every new test
above passing. No real multi-gigabyte trace exists on this CPU-only dev machine — verification is
fixture-based only, per `CLAUDE.md`'s testing philosophy; the cache-hit-skips-recompute behavior is
specifically worth asserting via a call-counter/monkeypatch rather than trusting output equality
alone, since a bug that silently always rebuilds would still produce correct data, just none of the
intended performance benefit.
