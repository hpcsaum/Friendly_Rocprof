# Roadmap: `postprocess/tests/` maintainability cleanup

## Context

A full audit (6 parallel deep-reads, one per stage/tool group) of `postprocess/tests/` found 750
`unittest` tests across 45 files with zero shared helpers, zero docstrings, and heavy copy-paste:
the same `importlib.util` module-loading dance repeated in ~35 files, at least 4 incompatible
`make_row`/`make_raw_row`-family helpers sharing confusingly similar names, several "same test
shape run once per input variant" clusters that amount to manual parametrization, and a few tests
that check trivial implementation details rather than behavior. The goal of this work is to make
the suite navigable and extensible by a human without reducing behavioral coverage — this is a
structure/readability pass, not a coverage-adding or coverage-cutting pass (any test removed must
be genuinely redundant with another, not just similarly-named).

Two decisions were made before planning this out (see conversation): stay on plain `unittest` +
`subTest()` rather than adopt pytest — this matches the project's own documented policy
(`docs/plans/1.11-pop-metrics-tool.md:53`: *"Tests use plain unittest... no pytest/CI config"*) and
needs zero new dependencies, which matters for HPC/offline environments. And the new test comment
policy will extend `postprocess/README.md`'s existing "Tests" section rather than living in a new
file — that section already documents the two module-loading styles and the noise-config global
state hazard, so it's the natural home for a testing-specific comment policy too.

**Baseline** (confirmed by actually running the suite): from `postprocess/`,
`python3 -m unittest discover -s tests -t .` → `Ran 750 tests ... OK`. This exact command is the
regression check after every phase below — test *count* will drop as duplication is consolidated,
but the result must stay `OK` and no fixture/scenario coverage should silently disappear (verify by
checking that a consolidated `subTest` loop still iterates every case the separate tests used to
cover, not a subset).

**Process note that applies to every phase**: per `CLAUDE.md`, update
`docs/DEVELOPMENT_HISTORY.md` (timeline row + narrative) and regenerate
`docs/DEVELOPMENT_HISTORY.docx` via the documented `pandoc` command before each commit. Each phase
below should land as its own commit, so this happens once per phase, not once at the end.

## Phase 0 — Write the test comment policy

Extend `postprocess/README.md`'s existing "## Tests" section (currently ends after the
`stage6_noise_config`/`stage6_time_range_config` module-loading-hazard paragraph) with a new
subsection covering comments specifically, built directly from `CLAUDE.md`'s existing "Code
comments" policy applied to test files:

- Every test file gets a short top-of-file docstring: which module/tool it tests and the
  functional scope it covers — not a list of every test in the file (that's what the file itself
  is for).
- An inline comment on an individual test is warranted only when the test's purpose, or the shape
  of its fixture data, is genuinely non-obvious from the test name and assertions alone — a hidden
  invariant, a documented known-limitation, or why a scenario needs its own test rather than being
  folded into another. Restating what the assertions already show is not a comment worth having.
  Same "current behavior, not history" rule as `CLAUDE.md`: no "added during test cleanup", no
  "see prior audit", no narrating this project.
- Every hard-coded value in a test (a magic number, a specific string, a threshold) needs its
  significance made clear one way or the other: either it's arbitrary (any value would exercise
  the same code path — say so, or better, name the variable/constant so that's obvious without a
  comment) or it's significant (it must match something real — a documented rocprof output field,
  a constant defined in the module under test, a specific fixture file's actual content) and the
  comment should say what it's tied to. A reader should never have to guess whether changing a
  number in a test would break something real or just be cosmetic.
- Point at the best examples the audit already found as the calibration bar rather than inventing
  new prose: `test_stage3_rocprofsys_common.py`'s known-limitation comments,
  `test_stage4_rocprofsys_trace_aggregate.py`'s ordering-invariant comment, and
  `test_stage5_pop_metrics_table.py`'s hand-traced arithmetic comments are all worth naming
  directly as the target style.

This lands first (own small commit) because every later phase's new/touched code should already
follow it — there's no separate "finalize the policy" step at the end, only the "apply it
everywhere it doesn't already comply" pass in Phase 6.

## Phase 1 — Shared test helper module (mechanical, low-risk)

New file: `postprocess/tests/_test_helpers.py` (plain module, imported normally — no `conftest.py`,
since that's pytest-only and wouldn't be picked up by `unittest`). Contents:

- A `load_module_by_path(name, file_path)` helper wrapping the `importlib.util.spec_from_file_location`
  dance currently copy-pasted in ~35 files (all of `tools/`'s tests, plus the stage tests that
  specifically want a fresh isolated module instance per `postprocess/README.md`'s existing
  explanation). Preserve `stage6_noise_config`'s test-specific `sys.modules` save/restore — that one
  needs an extra step the helper should support via a parameter or a second function, not silently
  drop.
- Do **not** try to unify this with the plain-`import` style most stage tests use — README already
  documents that split as intentional (tools need `importlib.util` because they're meant to run as
  scripts, not be imported), so the helper only targets the mechanical boilerplate, not the choice
  of style itself.

Representative files to migrate onto the helper: `tests/tools/test_extract_calltree.py`,
`tests/stage4/test_stage4_rocprofsys_common.py`, `tests/stage6/test_stage6_noise_config.py` — same
pattern applies to the rest of the ~35 files using this dance.

Also in this phase (same theme — mechanical, no behavior change):
- Rename the colliding `make_row`/`make_raw_row`/`make_merge_row` helpers to purpose-specific names
  per file (e.g. `make_label_parent_row`, `make_merged_tree_node`, `make_raw_trace_row`) so the same
  name never means two different shapes across files. Concretely affects
  `tests/stage4/test_stage4_rocprofsys_common.py`, `tests/stage4/test_stage4_rocprofsys_sample_tree.py`,
  `tests/stage4/test_stage4_rocprofsys_trace_aggregate.py`, and the two `stage5` files with their own
  `make_row`.
- Fix `tests/stage4/test_stage4_rocprofsys_trace_tree.py`'s local `flatten()` — it reimplements what
  `stage4_rocprofsys_common.flatten_tree()` already provides (already imported directly by
  `test_stage4_rocprofsys_sample_tree.py`) — switch to the real import instead.

**Verify**: full suite still `Ran 750 tests ... OK` (no test count change expected in this phase —
it only relocates helper code, doesn't consolidate tests yet).

## Phase 2 — `select_hotspot_kernels` / `select_instrumented_functions` consolidation

The single biggest test-count win identified. Both `tests/tools/test_select_hotspot_kernels.py`
and `tests/tools/test_select_instrumented_functions.py` re-run the same 5-shape pattern
(default-exclude / include-all / top-N / threshold / no-data-raises) once per loader function
(`labels_from_output_dir` / `labels_from_report` / `labels_from_trace_dir`). Replace each such
cluster with one `subTest`-driven test iterating `(loader_fn, fixture_dir, kwargs, expected)`
tuples, preserving every currently-covered combination.

Separately: the `iter_table_rows`/`wrap_trailing_label` edge-case tests (malformed text, missing
file, wrapped-label reconstruction across physical lines) are duplicated near-verbatim in both
files because both tools call the same shared `stage5_table_render` utility. Move that coverage
once into `tests/stage5/test_stage5_table_render.py` (where the utility actually lives) and drop
the per-tool duplicates — this is a real "test the shared thing once" fix, not just deduplication
for its own sake.

**Verify**: `Ran <N> tests ... OK` where `<N> < 750`; spot-check that the subTest loop's tuple list
covers every fixture directory + kwargs combination the deleted tests used to hit individually
(diff the old vs new test bodies to confirm no fixture/scenario silently dropped).

## Phase 4 — Test-scope audit (every file, explicitly)

Separate pass, after duplication is already cleaned up so what's left in each file is the real
signal. Go through **all 45 test files, one by one — no file skipped** — and classify every test in
it as one of:

- **Genuine unit coverage of that stage/tool's own logic** — leave as-is.
- **A pure re-test of a shared/common function's behavior**, already covered at that function's own
  test file, with nothing stage-specific added — drop it.
- **A legitimate integration/wiring check** (confirms this module correctly calls into a shared
  function, not that the shared function itself is correct) — keep, but make it clearly
  distinguishable as that (a class name like `...WiringTests`, or a one-line comment per the Phase 0
  policy) so a reader doesn't mistake it for redundant duplicate coverage.
- **Misplaced**: tests real behavior that belongs to a different module/stage than the file it's
  currently sitting in — relocate to the correct test file. (A stage legitimately testing its own
  use of an earlier stage's output shape, e.g. stage4 consuming a stage1-parsed row, is not this
  case — that's normal integration, not misplacement.)

Known instances already spotted by the audit, as a starting point — confirm these and then continue
past them, since the audit was not exhaustive on this specific question:
`ReexportedPrimitivesTests` in `test_stage3_rocprofsys_trace.py` (object-identity check on functions
re-exported unchanged from `stage3_rocprofsys_common` — already tested where implemented);
`test_wrapper_branch_noise_sibling_derivation_still_works` in the same file (re-exercises
`stage3_rocprofsys_common`'s sibling-group logic, already covered there); the `*ColumnsTests`
classes consolidated in Phase 3 (re-verify `test_stage5_table_render.py`'s behavior through a thin
column-spec wrapper — decide during Phase 3's consolidation whether any of the consolidated version
still needs to exist at all, or whether it fully collapses into "does this COLUMNS constant have the
right keys," a one-liner, once the render behavior itself isn't in question).

## Phase 5 — Trivial-test cleanup (drop or loosen, not consolidate)

Small, judgment-based pass — each item independently confirmed against the original audit note
before touching it:

- Drop tests checking a trivial implementation detail with no real behavioral value (e.g.
  `LabelKeyTests.test_label_key_names_the_name_column` in `test_stage1_rocprofsys_trace.py` — just
  asserts a string constant equals itself) unless it turns out something external actually depends
  on that constant, in which case keep it but add the one-line comment explaining why (per Phase 0
  policy) instead of dropping it.
- Loosen `test_stage5_table_render.py`'s exact-whitespace/exact-indent-width assertions
  (`test_left_aligned_column`, `test_continuation_lines_indented_to_exact_prefix_width`) to
  relational checks (e.g. `len(line) - len(line.lstrip()) == len(prefix)`) instead of literal string
  matches, so a deliberate padding-width tweak doesn't spuriously break several tests at once.
- Merge the handful of flagged "identical setup, redundant subset assertion" pairs found per-group
  (e.g. `test_stage2_rocprofsys_sample.py`'s two same-row-data tests; the parent-chain vs.
  sub-check pair in `test_stage1_rocprofsys_trace.py`) into single tests with multiple assertions.

**Verify**: full suite `OK`; test count drops further.

## Phase 6 — Final comments pass

Apply the Phase 0 policy suite-wide, now that the file layout has settled from Phases 1-5 (doing
this last avoids writing docstrings for helper code that then gets moved/renamed, or for tests that
Phase 4/5 end up dropping):

- Add a top-of-file docstring to all 45 test files (scope + what this file covers), matching the
  style `CLAUDE.md` already mandates for source modules.
- Add short "why" comments only where a test's purpose is genuinely non-obvious after the
  consolidation/audit work — the good existing examples named in Phase 0 stay as-is (don't rewrite
  working comments for the sake of it).
- Leave everything else uncommented — per policy, a comment restating what the assertions already
  show is not worth having.

**Verify**: full suite `OK`; spot-check a handful of docstrings against the actual file contents
for accuracy (the docstring should describe what's really there, not an idealized version).

## Phase 7 — Post-refactor coverage check against the real codebase

Everything through Phase 6 only ever removes or reshapes existing tests — it can't surface coverage
gaps that were already there before this cleanup started, and consolidation (Phases 2-3) creates a
small risk of a case being dropped by mistake despite the per-phase diff checks. This phase closes
the loop: for each `stageN/*.py` and `tools/*.py` source module, cross-check its exposed
functions/CLI flags/branches against what the (now cleaned-up) test file for it actually exercises,
and write new tests for anything genuinely uncovered.

- Go module by module (same grouping as Phase 4) — list each module's public functions and, for
  `tools/`, its CLI flags — and confirm each one has at least one test that would fail if its
  behavior broke. No new dependency for this (no `coverage.py` in the repo, and introducing one
  would cut against the zero-dependency approach chosen for Phase 0-6) — a manual function-inventory
  cross-check, or the stdlib `trace` module (`python3 -m trace --count`) if a quantitative pass is
  wanted, both work without adding anything to install.
- One concrete gap already known from the original audit: no test file anywhere in the suite checks
  `-h`/`--help` output content, despite `CLAUDE.md`'s mandate that every tool's `--help` lead with a
  specific jargon-free explanation and a link to the underlying AMD tool's docs. Confirm this gap
  still exists post-cleanup and add coverage for it (per tool, or via a shared helper in
  `_test_helpers.py` if the check is generic enough to run once per tool).
- For any new test added here that exercises a real fixture scenario not currently represented under
  `tests/fixtures/`, follow `CLAUDE.md`'s existing fixture policy (hand-crafted, documented-schema
  data) — and where the new coverage concerns something real profiling output already demonstrates
  under the sibling `Heat_Convection_Solver/` tree, include a real-data verification pass against
  that, not fixture-testing alone, per `CLAUDE.md`'s "Test" section.

**Verify**: full suite `OK`; new test count only ever goes up in this phase (the only phase where
it's expected to), and every newly-added test is tied to a specific, named gap (not added
speculatively) so the running note from Phase 4 stays accurate about why the suite looks the way it
does.
