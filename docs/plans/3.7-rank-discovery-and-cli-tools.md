# Plan 3.7: rank discovery + the 3 new trace CLI tools (stage5/6 composition)

> **Divergence found during the real-data smoke test**: this plan has `discover_ranks()` prefer
> the single unfiltered file over the category-partitioned trio when both exist for a rank,
> reasoning that they're "overlapping supersets." Running the new tools against this project's own
> real trace-CSV export (the only real multi-rank data available) showed that reasoning was
> incomplete: that export's unfiltered file carries a narrower column set than its partitioned
> files (missing `corr_id` and the other wide GPU-arg columns entirely), so preferring it silently
> disabled every `corr_id` join. Fixed by reversing the precedence — the partitioned set wins when
> present (confirmed, for that same real export, to be an exact row-for-row partition of the
> unfiltered file, so no data is lost either way); the unfiltered file is used only when no
> partitioned set exists. Recorded in `docs/DEVELOPMENT_HISTORY.md`.

## Context

The final step of plan 3.1's roadmap sequence (depends on 3.2, 3.4, 3.5+3.6). Two things this step
was explicitly built to defer now have real answers:

- **Multi-rank file discovery**: `stage4_rocprofsys_trace_aggregate.get_rank_aggregate()`/
  `stage4_rocprofsys_trace_tree.merge_ranks()`/`stage4_rocprofsys_trace_flat.*()` all take an
  explicit, caller-supplied `rank_inputs` list — deliberately, since no real multi-rank trace data
  existed yet to confirm a naming convention. It does now: the real
  `Heat_Convection_Solver/instrument_hotspots-trace-output-.../2026-08-10_12.59/` directory this
  project's own manual conversion work produced contains exactly `perfetto-trace-<N>.csv` (one per
  rank, N=0..3, a bare digit) plus the category-partitioned trio
  `perfetto-trace-<N>-{gpu,mpi,other}.csv` for each rank — both the unfiltered file *and* the
  partitioned set exist side by side for every rank (overlapping supersets, not a choice already
  made for us), so discovery has to prefer one over the other, not just glob everything.
- **`{tag: action}` wiring for the new trace tools**: turns out to need almost no new design at
  all. `stage3_rocprofsys_trace.py` deliberately reused the sample pipeline's exact tag names for
  `gpu_api`, `mpi_territory`, `wrapper_noise`, `compiler_runtime_noise`, and `wrapper_branch_noise`
  — so `stage6_cli_common.NOISE_TIER_FLAGS`/`add_noise_tier_args()` apply to the new calltree tool
  **completely unchanged**, verbatim the same call `extract_calltree.py` already makes. Only two
  tags have no sample-pipeline equivalent at all: `gpu_kernel` and `gpu_memcpy` (real device
  execution/memory-movement time the trace format newly makes visible, not noise) — decided:
  always shown, no flag, since there's no existing precedent or real-data reason to hide them.

Two small, well-justified additions surfaced only now, during actual composition, not anticipated
by the 3.5+3.6 design in detail (though both fit inside decisions that plan already made room for):
`stage4_rocprofsys_trace_flat.aggregate()`'s entries need a `"domain"` field — the *optional* field
plan 3.1's own documented flat-entry canonical shape already named
(`{label, count, sum, self_sum, pct_self, pct_total} (+ optional domain)`), just never populated
until a fused hotspots table needed it; and `stage4_rocprofsys_trace_tree.merge_ranks()` needs an
optional per-rank `postprocess` hook (mirroring `stage4_rocprofsys_sample_tree.load_rank_trees()`'s
identical existing contract) so the calltree tool's tag-driven splice/prune can run **before** the
cross-rank merge, while `get_rank_aggregate()`'s own cached output stays exactly as
tool-independent as plan 3.5+3.6 established — action-wiring still never touches the cache.

## Approach

### File discovery: `postprocess/stage4/stage4_rocprofsys_trace_ranks.py`

`discover_ranks(trace_dir)` → a list of `(rank_key, csv_paths)` tuples, sorted by numeric rank —
exactly the `rank_inputs` shape `merge_ranks()`/`aggregate()`/`aggregate_per_rank()`/
`gather_timing_summary_per_rank()` already expect, so nothing about those functions changes.

- Regex: `-(\d+)(?:-(gpu|mpi|other))?\.csv$`, matched against each file's basename after a
  recursive `glob` for `*.csv` under `trace_dir`. Deliberately not anchored to the literal
  `perfetto-trace-` prefix this session's own ad hoc conversion happened to produce — that prefix
  is this project's own naming, not something any upstream tool guarantees, and the deferred
  `.proto`→CSV conversion tool (still out of scope) doesn't exist yet to lock a prefix in. The
  trailing `-<digit>[-category].csv` shape is the one part actually evidenced by real data.
- Per rank digit: if the single unfiltered file (no category suffix) exists, use only that one;
  otherwise use whichever of the `-gpu`/`-mpi`/`-other` files exist as the partitioned set. Never
  both — the real directory has both forms for every rank, and they're overlapping supersets, not
  a partition of each other; mixing them would double-count every row.
- No file matches anything → `raise SystemExit` naming the expected pattern, mirroring
  `extract_CPU_hotspots.py`'s existing "no scanned_files" precedent.
- Documented explicitly as *this project's own* assumed convention (the one real evidence
  supports), not an AMD-tool guarantee — a user with differently-named CSVs renames them; a future
  `.proto`→CSV conversion tool this project eventually builds should produce names matching this
  convention by construction.

### Two small stage4 additions

- `stage4_rocprofsys_trace_flat.aggregate()`: each entry gains `"domain"` — `"GPU"` if any of
  `gpu_api`/`gpu_kernel`/`gpu_memcpy` is in the row's tags, else `"CPU"`.
- `stage4_rocprofsys_trace_flat.aggregate_per_rank()`: stays domain-agnostic, unlike the sample
  pipeline's own `aggregate_per_rank()` (which excludes GPU rows via `if row["gpu"]: continue`).
  That exclusion is a consequence of rocprofv3's own data being *already aggregated* per rank with
  no compatible per-rank breakdown to fold in there — not a general principle that GPU work
  shouldn't appear in a load-imbalance view. Trace data gives real, exact per-rank `gpu_kernel`
  timing, so GPU load imbalance is now genuinely available and belongs in the same table, not
  excluded to match an older data source's limitation.
- `stage4_rocprofsys_trace_tree.merge_ranks()`: gains an optional `postprocess=None` parameter,
  applied to each rank's rows right after `get_rank_aggregate()` returns them and before that
  rank's `roots` are recomputed — the exact same contract shape
  `stage4_rocprofsys_sample_tree.load_rank_trees()`'s own `postprocess` parameter already has.

### `{tag: action}` wiring

| Tag | Default | Flag |
|---|---|---|
| `gpu_api` | hidden (`make_is_pruned`) | `--show-gpu-api` |
| `wrapper_noise` | spliced out, `fold=False` | `--show-rocprofsys-internals` |
| `compiler_runtime_noise` | hidden (`make_is_pruned`) | `--show-compiler-runtime` |
| `mpi_territory` | first frame shown, its subtree collapsed | `--show-mpi-internals` |
| `wrapper_branch_noise` | always removed (`remove_tagged_subtrees`) | none, same as the sample pipeline |
| `other` | always spliced, `fold=True` | none, same as the sample pipeline |
| `gpu_kernel`, `gpu_memcpy` | always shown | none — real device time, not noise |

Since these are the exact tag names `stage3_rocprofsys_trace.py` already reuses,
`stage6_cli_common.add_noise_tier_args(parser, ["gpu_api", "rocprofsys_internals", "mpi_internals",
"compiler_runtime"], all_shorthand=True)` is called **verbatim**, identical to
`extract_calltree.py`'s own call — no new flag dict, no changes to `stage6_cli_common.py` at all.

### New module: `postprocess/stage5/stage5_trace_calltree_view.py`

`build_calltree_view(rank_inputs, cache_dir=None, max_depth=None, show_gpu_api=False,
show_rocprofsys_internals=False, show_mpi_internals=False, show_compiler_runtime=False)`:
1. A per-rank postprocess closure: `remove_tagged_subtrees` for `wrapper_branch_noise` (always),
   `splice_by_tag(..., fold=False)` for `wrapper_noise` unless `show_rocprofsys_internals`,
   `splice_by_tag(..., fold=True)` for `other` (always) — the same primitives
   `stage5_calltree_view.strip_wrapper_noise()` already uses, re-exported unchanged from
   `stage3_rocprofsys_trace.py`.
2. `merge_ranks(rank_inputs, cache_dir=cache_dir, postprocess=<that closure>)` → `merged_roots`.
3. `flatten_tree(merged_roots)` (from `stage4_rocprofsys_common`) → `flat`.
4. `is_pruned = make_is_pruned(tags)` where `tags` is `{"gpu_api"}` unless `show_gpu_api`, unioned
   with `{"compiler_runtime_noise"}` unless `show_compiler_runtime`; `collapses_children =
   make_collapses_children(set() if show_mpi_internals else {"mpi_territory"})`.
5. `node_values = make_node_values(rank_keys)` (from `stage4_rocprofsys_common`).
6. `stage5_tree_render.render_calltree_text(...)` — **unchanged**, same call shape the sample
   pipeline's own view already uses.
7. Returns `{"tree_text", "rank_keys"}` — genuinely simpler than
   `stage5_calltree_view.build_calltree_view()`: no `"fallback_text"`/unattached-kernel section at
   all, since the `corr_id` join already placed every kernel dispatch exactly, with no ambiguity
   left needing a fallback. A real simplification the trace format affords, not a missing feature.

### `postprocess/tools/extract_trace_hotspots.py`

One positional `trace_dir`; `-o/--output`; `stage6_cli_common.add_selection_args(...)` (same
wording convention as `extract_CPU_hotspots.py`); `stage6_noise_config.add_cli_argument(...)`
(unchanged — still gives a user's `--extra-noise-config` free effect on `wrapper_noise`/
`compiler_runtime_noise`, per plan 3.4).

`write_report()`: `discover_ranks(trace_dir)` → `aggregate(rank_inputs)` → **one**
`FUSED_HOTSPOTS_COLUMNS`-shaped table (confirmed by direct read of
`stage5_fused_hotspots_table.py`: it only ever needs `{label, self_sum, pct_total, sum, domain,
count}`, all present once `"domain"` is added) via the unchanged `select_entries()`/
`render_table()`; `aggregate_per_rank(rank_inputs)` → the unchanged `compute_load_imbalance()` for
a second, load-imbalance section — the same two-section structure `extract_CPU_hotspots.py` already
has, except this one covers CPU functions *and* GPU kernels together in the same table (see the
`aggregate_per_rank()` change above) — a real capability gain trace data affords over the sample
pipeline's CPU-only load-imbalance view, not something to leave out for parity with it.
**Deliberate simplification** from plan 3.1's original phrasing ("reusing
`FUSED_HOTSPOTS_COLUMNS`/`CPU_HOTSPOTS_COLUMNS`/`GPU_HOTSPOTS_COLUMNS`"): one fused table, not
three — trace data is a single, already-unified CPU+GPU source, unlike the sample+rocprofv3 pairing
`FUSED_HOTSPOTS_COLUMNS` was built to reconcile, so there's no separate-collection-tools reason to
keep CPU-only/GPU-only tables split. Stated explicitly here and in the tool's own report footer.
No sync-wait double-counting correction is needed either (confirmed by reading
`build_combined_view()`'s own docstring: that correction exists specifically because rocprof-sys's
and rocprofv3's totals are independently collected and can overlap; trace data's `self_sum` per
node is already disjoint by construction, `corr_id`-joined structurally).

### `postprocess/tools/extract_trace_calltree.py`

One positional `trace_dir`; `-o/--output`; `stage6_cli_common.add_max_depth_arg(...)` (unchanged);
`add_noise_tier_args(...)` (unchanged, verbatim, see table above); `stage6_noise_config
.add_cli_argument(...)` (unchanged). `write_report()`: `discover_ranks(trace_dir)` →
`stage5_trace_calltree_view.build_calltree_view(...)` → the unchanged `aggregation_note()`/
`tree_view_note()` for the trailing notes — same composition shape as `extract_calltree.py`, minus
the GPU-kernel-fallback section (see above).

### `postprocess/tools/extract_trace_pop_metrics.py`

Positional `reference_dir` + `scaled_dirs` (`nargs="*"`); `--scaling {strong,weak}`; `-o/--output`;
`stage6_noise_config.add_cli_argument(...)` — the same flag set as `extract_pop_metrics.py` (which
has neither ranked-truncation nor tree flags, confirmed by direct read).

A small per-directory composer, inline in this tool's own `write_report()` (not a
`stage5_trace_pop_metrics_view.py` — `extract_pop_metrics.py` itself has no separate view file
either; its `write_report()` calls stage4/stage5 functions directly, and this tool follows the same
precedent): for each directory, `discover_ranks()` → the unchanged
`gather_timing_summary_per_rank()` (already generalized for exactly this in plan 3.5+3.6) → the
unchanged `compute_metrics_from_per_rank()` → a metrics dict shaped like `compute_run_metrics()`'s
own return, minus `"cpu_dir"`/`"gpu_dir"` (trace data has no such pairing concept — always both
domains from one source). `format_metrics_table()`/`metrics_legend()`/`pop_metrics_columns()` (all
unchanged) never read `"gpu_dir"` themselves — only `extract_pop_metrics.py`'s own `write_report()`
does, for its `"pool: CPU+GPU combined / CPU-only"` `extra_lines` note; this tool's `write_report()`
builds its own note instead (e.g. "pool: CPU+GPU, single unified trace source"), not reusing that
exact line.

### Explicitly out of scope

A `--cache-dir` flag (`get_rank_aggregate()`'s existing default — alongside each raw CSV — is used
as-is; a separately-justified future addition if a real workflow needs otherwise). The
`.proto`→CSV conversion tool itself (still deferred, per plan 3.1's original scope decision). Any
change to the existing sample-pipeline tools or flags.

### Tests

- `discover_ranks()`: unfiltered-file wins over the partitioned set when both exist for a rank;
  the partitioned set is used when no unfiltered file exists; numeric (not string) sort order for
  10+ ranks; no match anywhere raises with the expected message. New small fixture directory with
  a mix of both forms across a few ranks.
- `aggregate()`'s new `"domain"` field, and `aggregate_per_rank()` staying domain-agnostic (no GPU
  exclusion, per the correction above): extend the existing `trace_two_rank` fixture-based tests.
- `merge_ranks()`'s new `postprocess` hook: a synthetic per-rank drop function changes the merged
  tree, mirroring `load_rank_trees()`'s own existing postprocess-hook test.
- `stage5_trace_calltree_view.build_calltree_view()`: each `--show-*` flag's default-hidden/shown
  behavior, against a fixture carrying a `wrapper_noise`-matching name and an `other`-mapped
  category.
- CLI tools: argparse-level smoke tests mirroring `test_extract_CPU_hotspots.py`/
  `test_extract_calltree.py`/`test_extract_pop_metrics.py`'s own convention, plus a manual smoke
  test against the real `Heat_Convection_Solver` rank CSVs — report *structure* (section layout,
  column headers) compared against the equivalent existing tool's output, explicitly **not**
  byte-identical (a genuinely different, richer data source), with that caveat stated in each new
  tool's own report footer — per plan 3.1's own verification note for this step.
