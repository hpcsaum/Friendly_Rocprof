# Plan 2.8: stage-6 composition — stage6_report_builder.py, stage6_run_metadata.py (roadmap step 7)

## Context

Plans 2.2–2.7 already pulled stages 1–5 out into shared modules, leaving the 6 report-writing
tools (`extract_CPU_hotspots.py`, `extract_GPU_hotspots.py`, `extract_hotspots.py`,
`extract_pop_metrics.py`, `extract_calltree.py`, `extract_calltree_traced.py`) thin-ish already —
but two pieces of real, confirmed duplication are still inline in every one of them: the
`parts = [] ... report = "".join(parts) ... write to dest_path ... return report` assembly
boilerplate, and (in the two hotspots tools only) the run-metadata-guessing helpers
(`find_first_key`/`guess_executable`/`guess_run_datetime`/`guess_total_runtime`/`guess_num_ranks`/
`gather_run_info`). Roadmap step 7 (§12 of `docs/plans/2.1-postprocess-consolidation-refactor.md`)
calls for extracting both into `report_builder.py`/`run_metadata.py` (renamed
`stage6_report_builder.py`/`stage6_run_metadata.py` here — see decision 4), finishing what step 6
started. The tool files themselves (`extract_*.py`, `select_hotspot_*.py`) keep their existing
names, unprefixed — the `stage*_` prefix marks internal shared modules, never the user-facing CLI
tools.

**Confirmed via full fresh reads of all 6 tools, plus the master plan's own §10/§12 text:**

1. **The join/write/return tail is byte-for-byte identical across all 6 tools** — same 3 lines,
   same variable names, no per-tool variation at all.
2. **A genuinely generic report-assembly backend is achievable, not just a thin `section()`
   helper** — every tool's `write_report()` is really three phases done in sequence: compute data
   (calls into stage4/5), build report text from that data, write it out. The middle phase itself
   splits cleanly into **header** (metadata/run-info lines — genuinely tool-specific, stays a
   plain string each tool builds itself), **sections** (a title + a body, repeated N times — CPU
   hotspots has 4, `extract_hotspots.py` has 6, `extract_pop_metrics.py` has 1, GPU hotspots has 2),
   and **footer** (closing notes/redirects — tool-specific prose). The section shape itself (title
   line, body, one blank line) *is* uniform across every table-shaped tool today, even before §10's
   later formatting pass makes the *wording* uniform too — the structural repetition was already
   there, just spelled out by hand in every tool. This lets `stage6_report_builder.py` own the "for
   each section: title, body, blank line" loop generically, while each tool keeps full control of
   what its own header/sections/footer actually say.
3. **The two calltree tools fit the same section shape too, once `stage5_tree_render.py`'s two
   render functions stop self-terminating with a blank line.** `render_calltree_text()`/
   `attach_and_render_gpu_kernels()` currently each append their own trailing `"\n"` (a plan-2.7
   design choice, so `build_calltree_view()`'s `tree_text`/`fallback_text` could be concatenated
   directly by their two callers). Every other stage-5 render function (`render_table()`, and now
   `render_report()`'s own section loop) puts that blank line at the *assembly* layer instead, never
   inside the leaf renderer — `stage5_tree_render.py`'s two functions were the one exception. Fixing
   that (dropping each function's own trailing `+ "\n"`, so both end exactly like
   `format_aligned_rows()`/`render_table()` already do: one newline from the table itself, no more)
   removes the only real blocker, so `render_report()` itself stays the plain, uniform `(title,
   body)` shape below — no extra flag needed — and both calltree tools adopt it in this same plan
   instead of needing a special case. The only thing that moves is *where* the blank line comes
   from: `extract_calltree.py`/`extract_calltree_traced.py`'s own `write_report()` used to get it
   for free from the two stage-5 functions; now `render_report()` supplies it, the same way it does
   for every other tool's sections. Real report output is unaffected either way (still
   byte-identical) — only `stage5_tree_render.py`'s own unit tests, which assert on the old
   trailing-blank-line behavior directly, need updating to match.
4. **New shared modules get the `stage6_` prefix, matching the `stage1_`–`stage5_` convention** —
   `report_builder.py` → `stage6_report_builder.py`, `run_metadata.py` → `stage6_run_metadata.py`.
   The tool files (`extract_CPU_hotspots.py`, etc.) are the user-facing CLI surface and keep their
   existing, unprefixed names — the prefix marks an internal shared module, not a rule about
   "everything touched in stage 6."
5. **`stage6_run_metadata.py`'s functions split into "real shared primitive" vs "keep separate."**
   Diffed every CPU/GPU pair function-by-function:
   - `find_first_key()` — code is byte-identical between the two (CPU's copy just has a docstring
     GPU's lacks) → one shared function.
   - `load_metadata()`/`load_config_json()` — identical control flow, differ only in the glob
     pattern literal (`"metadata.json"` vs `"*_config.json"`) → one shared `load_json_file(output_dir,
     glob_pattern)`.
   - `guess_executable()` — identical logic, differs only in which keys-list constant is passed →
     one shared function taking `keys` as a parameter; each tool keeps its own keys constant
     (`EXECUTABLE_KEYS` vs `CONFIG_EXECUTABLE_KEYS` — genuinely different lists, not a coincidence to
     collapse).
   - `guess_total_runtime()` — same shape as `guess_executable()`; its two keys-list constants
     (`TOTAL_RUNTIME_KEYS`/`CONFIG_RUNTIME_KEYS`) happen to hold identical contents today, but they're
     independent guesses against two different, undocumented JSON schemas — kept as two separate
     tool-owned constants rather than merged into one, so one schema's guess list can evolve without
     silently changing the other's.
   - `guess_run_datetime()` and `guess_num_ranks()` — genuinely different logic (CPU has extra
     fallback branches GPU doesn't have at all: a `TIME_OUTPUT_DIR_RE`-based directory-name fallback
     for datetime, a `NUM_RANKS_KEYS` metadata lookup before PID-counting for ranks). These become one
     shared function each with the extra behavior gated behind an optional parameter that defaults to
     "skip it" — the same "generic function, optional no-op-by-default hook" shape plan 2.7 already
     established for `select_entries()`'s `prepare` and `load_rank_trees()`'s `postprocess`.
   - `find_extra_artifacts()` (CPU-only, Perfetto/rocpd file discovery for its own footer note) has
     no GPU equivalent and isn't "metadata guessing" in the same sense — stays in
     `extract_CPU_hotspots.py`, not moved.
   - `gather_run_info()` itself stays as each tool's own small function (not moved into
     `stage6_run_metadata.py` as one mega-parameterized function) — it's just a 4-line dict-builder
     calling the now-shared primitives with that tool's own constants; forcing it into one shared
     function with 7+ keyword parameters would be a worse trade than two 4-line functions.
   - **A further metadata consolidation is real but deferred to step 9, not attempted here.** This
     step only extracts the *mechanism* (the primitives above) byte-identically; it deliberately
     does not touch the *content* questions those two near-duplicate key-list pairs raise — should
     `EXECUTABLE_KEYS`/`CONFIG_EXECUTABLE_KEYS` genuinely be reconciled into one guess order the way
     `TOTAL_RUNTIME_KEYS`/`CONFIG_RUNTIME_KEYS` already coincidentally match, should `gather_run_info()`
     itself end up as one shared shape once both tools' headers are uniform, should `PID_SUFFIX_RE`
     (same name, two different regexes) get distinguished names now that they're both parameters to
     the same shared function. Those are report-*content* decisions belonging with §10's uniform
     metadata presentation (step 9), not a structural-extraction step — bundling them in here would
     risk the "byte-identical output" invariant this step is verified against for no real gain.
     Flagged explicitly so step 9 doesn't have to rediscover it.
6. **"All 8 tools" in the roadmap's step-7 description means the whole tool suite ends up
   appropriately thin, not that `select_hotspot_functions.py`/`select_hotspot_kernels.py` need the
   same treatment.** Confirmed by reading both fully: neither has a `write_report()`, a `parts` list,
   or a `dest_path` — they resolve a label list and `print()` it directly. Nothing to extract there.
7. **§10's actual formatting rules (casing, section markers, blank-line structure, the redirect
   rule, the 120-column wrap, the `command:` header) are explicitly roadmap step 9, not step 7** —
   confirmed by reading §10 and §12's roadmap table directly: step 7's own verification column says
   "byte-identical output," step 9's says "first step where output text is *intentionally* allowed to
   change everywhere." This step only wires today's exact wording through the new backend unchanged
   — no section text, ordering, or casing changes here.
8. **No shared `main()` extraction** — the `isdir` check → `dest = args.dest or
   os.path.join(...)` → call → `print(f"wrote {dest}")` shape repeats across all 6 `main()`s, but
   with real per-tool variation (1 vs 2 vs N directories checked, different default filenames,
   different kwargs forwarded to `write_report()`). The roadmap's step-7 scope names only
   `report_builder.py`/`run_metadata.py` — not a shared main()-runner — and forcing one here would be
   a new abstraction the roadmap didn't ask for. Each tool's `main()` stays as its own thin composer.

## Approach

### New file: `postprocess/stage6_report_builder.py`

```python
def write_report_file(dest_path, parts):
    """Joins parts (a list of strings) into one report string, writes it to dest_path, and
    returns the string -- the file-writing primitive every write_report() in this codebase needs,
    whether or not it also uses render_report() below."""
    report = "".join(parts)
    with open(dest_path, "w") as f:
        f.write(report)
    return report


def render_report(header, sections, footer=""):
    """Builds the parts list for one report: header (a single pre-built string -- metadata/run-info
    lines, entirely up to the caller), then each (title, body) pair in `sections` rendered as
    title line (skipped if title is falsy -- a titleless prose block) + body + one blank line,
    then footer (another pre-built string, e.g. closing notes/redirects). Returns a list ready for
    write_report_file().

    Every tool's write_report() has the same real structure underneath its own wording: compute
    data, then assemble a header + a sequence of title+body sections + a footer. This function
    generalizes the "assemble a sequence of sections" part; each tool keeps full control of what
    its own header/sections/footer text actually says -- this step changes HOW that text gets
    assembled, never WHAT it says. Every section body is expected to end with exactly its own
    content's newline and no more (the same convention render_table()/format_aligned_rows() already
    follow) -- the blank line between sections is always this function's job, never a leaf
    renderer's.
    """
    parts = [header]
    for title, body in sections:
        if title:
            parts.append(title)
        parts.append(body)
        parts.append("\n")
    if footer:
        parts.append(footer)
    return parts
```

Module docstring: stage 6 — the two structural pieces every report-writing tool needs: assembling
a header + N title/body sections + a footer into one report's text (`render_report()`), and
writing that text to a file while also returning it (`write_report_file()`). Has no opinion on
report content, wording, or formatting rules (see `docs/plans/2.1-...md` §10 for those — roadmap
step 9, not this one).

### New file: `postprocess/stage6_run_metadata.py`

```python
def load_json_file(output_dir, glob_pattern):
    """Best-effort find-and-parse the first file under output_dir matching glob_pattern (recursive)
    as JSON -- returns {} on missing file, read error, or non-dict content, never raises."""

def find_first_key(d, candidate_keys, _depth=0):
    """Best-effort case-insensitive key search, one level of nested dicts deep -- the JSON schema
    isn't documented, so this is a guess, not a parse."""

def guess_executable(data, keys):
    """First non-empty string (or first element of a non-empty list) found under any of keys,
    basename of its first whitespace-separated token."""

def guess_total_runtime(data, keys):
    """First numeric or non-empty-string value found under any of keys, formatted as '{:.6f} sec'
    if numeric."""

def guess_run_datetime(data, keys, output_dir=None, scanned_files=(), dir_pattern=None):
    """First non-empty string found under any of keys. If that fails and dir_pattern is given,
    falls back to matching dir_pattern against output_dir, then against each scanned file's own
    directory name -- omit dir_pattern for a tool with no such directory-name convention to fall
    back to."""

def guess_num_ranks(data, pid_suffix_re, scanned_files, keys=None):
    """If keys is given, tries a numeric value under any of them first. Otherwise (or if that
    fails), counts distinct PIDs found by pid_suffix_re across scanned_files' basenames."""
```

Bodies are the verbatim shared logic already confirmed identical (or made identical by
parameterizing the one real difference) between `extract_CPU_hotspots.py`'s and
`extract_GPU_hotspots.py`'s current copies.

`extract_CPU_hotspots.py`'s own `gather_run_info()` stays put, now calling the shared primitives
with its own constants:

`extract_GPU_hotspots.py`'s own `gather_run_info()` stays put too, same shape, its own constants,

pure structural extraction with no wording/behavior change, so the existing
`WriteReportTests`/`MainCliTests` classes across all 6 tools' test files should keep passing
unchanged (they assert on report content/file existence, not on which internal function produced
it) — run them first and only touch what actually breaks (an import of a moved function).

  + footer assembles in the right order with one blank line per section; a section with a falsy

- Update `tests/test_stage5_tree_render.py`'s existing `RenderCalltreeTextTests`/

  match the corrected single-newline-only behavior.

  (found/missing/corrupt file), `find_first_key()` (flat + one-level-nested), `guess_executable()`/
  `guess_total_runtime()` (value found/missing, list-unwrapping for executable),

## Verification

1. Run the full test suite; fix any breakage caused by the import moves.
2. Back up `test_apps/results/*/{calltree,calltree_traced,hotspots,pop_metrics}.txt` (gitignored),
   regenerate all of them from all 6 real captures, and diff old vs. new with `generated:` lines
   filtered out.
3. Expect **zero diffs, with one narrow class of exception**: a blank-line-only difference is
   allowed when (a) the new placement matches what §10's blank-line/section structure will require
   anyway (so it's not a step backwards, just an early, incidental step towards it), and (b) it
   lets `write_report()` use a genuinely uniform section shape instead of a special case built only
   to dodge the diff. Concretely: `extract_GPU_hotspots.py`'s current output has no trailing blank
   line after its last (load-imbalance) block — the one place among all 6 tools' current output
   where the "section body, then blank line" pattern isn't followed. Rather than route that block
   through `footer` (which never gets a trailing blank) just to preserve that one accidental gap,
   its `write_report()` uses `render_report()`'s plain, uniform section list like every other tool
   does — CPU hotspots' own shape, not a special case — and gains the one trailing blank line that
