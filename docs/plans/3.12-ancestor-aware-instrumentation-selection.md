# Plan 3.12: instrument enough of a hotspot's real ancestry

## Context

`select_hotspot_functions.py` currently selects which CPU functions `instrument_hotspots.sh`
instruments purely by a self-time/inclusive-time threshold, with zero awareness of call-tree
structure. This causes exactly the problem plan 3.8/3.11 already found evidence of: a GPU kernel's
real CPU owner, or an MPI call's real caller, can end up uninstrumented even though the kernel/MPI
call itself is expensive -- leaving it structurally disconnected in the resulting trace (nested
under a generic OMPT/launch-site node instead of its real, specific position). The user's three
questions are really one general principle with two specific instances:

1. A GPU kernel hotspot's real CPU owner needs instrumenting, regardless of the owner's own
   hotspot status.
2. An MPI call's real caller needs instrumenting, same reasoning.
3. General: enough of any hotspot's real post-filtering ancestry should be instrumented to keep
   its position in the resulting tree meaningful -- (1) and (2) are specific cases of this.

Each addition must be weighed against its own overhead (more instrumented functions = more
distortion of the very timing being measured, the whole reason selective instrumentation exists).

Also folded in, per explicit request: given how central this selection logic now is,
`select_hotspot_functions.py` is renamed to **`select_instrumented_functions.py`** and its new
logic (ancestor-expansion, GPU-owner resolution) is built as **generic, reusable primitives** in
`stage4`/`stage5` from the start -- capable of selecting whatever a *future* tool needs from a
table or tree output, not hardwired to "hotspots for instrumentation" specifically. The CLI tool
itself keeps serving its one concrete job (feeding `instrument_hotspots.sh`), just honestly renamed
for what it now does and built on top of primitives any later tool could import directly.

Researched via two parallel Explore agents plus direct reads: every mechanism this needs already
exists in the codebase, just not wired into selection --

- `stage4_rocprofsys_common.caller_chains_for_label(flat, label)` already walks UP from any tree
  node to every distinct root-to-it ancestor chain -- this is the exact upward-walk requirement 3
  needs, already used by `extract_hotspot_callers.py` for reporting (not selection).
- `stage4_rocprofsys_common.kernel_owner_label(name)` recovers a GPU kernel's real owning
  subroutine name directly from the kernel's own compiler-generated name -- a pure string
  operation, no tree walk needed at all, directly serving requirement 1.
- MPI-tagged rows (`mpi_territory`) are tag-only in this codebase -- they keep real `parent` links
  in the merged tree even when a report hides them as noise, so `caller_chains_for_label()` already
  finds and walks them like any other row, directly serving requirement 2.
- `select_hotspot_kernels.labels_from_output_dir()` already selects GPU kernel hotspots from a
  rocprofv3 directory, by the same top/threshold/all convention -- directly reusable to get the
  candidate kernel names for requirement 1.
- No existing "weigh selection size against overhead" policy exists anywhere in this codebase
  (confirmed by search) -- this plan is the first to need one.
- Real data to verify against already exists: `Heat_Convection_Solver/instrument_hotspots-scan-2026-08-10_12.55.53/`
  has `rocprof-sys/` (CPU sample data), `rocprofv3/` (GPU kernel data), and both `hotspots.txt` +
  a sibling `calltree.txt` -- everything needed to exercise every new code path against a real
  profiling run, not just hand-built fixtures.

## Confirmed decisions

1. **Ancestor-pulling is on by default, depth 1** (the immediate real parent only) --
   `instrument_hotspots.sh`'s auto-profiling step already produces a real sample tree at zero
   extra profiling cost, so this fixes the stated problem for every existing user without a new
   flag to discover. `--ancestor-depth N` changes it; `--ancestor-depth 0` disables it entirely.
2. **No separate hard cap.** Depth-limiting already bounds the worst case per hotspot to a small,
   predictable number of real, distinct call sites; a transparent count report (see below) gives
   the overhead visibility the request calls for without a second, harder-to-reason-about knob.
3. **GPU-kernel-owner resolution wired automatically via a new `--gpu-output-dir DIR`** --
   `instrument_hotspots.sh`'s own scan step already runs `profile_hotspots.sh`, which already
   produces `$OUTPUT_DIR/rocprofv3`; wiring it through costs nothing extra to profile.
4. **`--report FILE` mode also supports ancestor-pulling**, by requiring a sibling `calltree.txt`
   in the same directory as the given report (every launcher that writes `hotspots.txt` also
   writes `calltree.txt` right alongside it by default, per the user's own observation) -- parsed
   back into ancestor-chain data rather than needing the raw rocprof-sys output directory.
5. **Rename + generalize**: `select_hotspot_functions.py` → `select_instrumented_functions.py`;
   the new ancestor-expansion and GPU-owner-resolution logic is built as importable functions in
   `stage4_rocprofsys_common.py` (alongside the primitives they're built from), not as private
   logic embedded in the CLI tool -- so a future tool needing "these labels plus enough of their
   real ancestry" doesn't need to reimplement it or import a tool module for it.

## Design

### New generic primitives (in `stage4_rocprofsys_common.py`, next to `caller_chains_for_label()`/`kernel_owner_label()`)

- **`expand_labels_with_ancestors(flat, labels, depth)`**: given a flat parent-linked row pool
  (the same shape `caller_chains_for_label()` already consumes) and a set of target labels,
  returns the set of *additional* labels found within `depth` levels of any of them (via
  `caller_chains_for_label()` per label, reading each returned chain's nearest `depth` entries
  before the target). Generic -- no hotspot/instrumentation concept in it at all, reusable by any
  future tool that has a flat tree pool and a label set.
- **`resolve_kernel_owners(kernel_labels)`**: given a set of GPU kernel names, returns the set of
  successfully-decoded owner names (via `kernel_owner_label()`), skipping any kernel whose name
  matches neither the Cray `$ck_` marker nor the generic `__omp_offloading_...` shape -- same
  "no owner to match, no guessing" behavior `kernel_owner_label()` already has everywhere else.

### New parsing primitive (`postprocess/stage5/stage5_calltree_text_parser.py`, new module)

`flat_rows_from_calltree_text(text)`: reconstructs the same `{"label", "parent"}` flat shape
`caller_chains_for_label()` expects, directly from a *rendered* `calltree.txt`'s text -- the one
genuinely new piece of non-trivial parsing this plan needs (no existing report-parser in this
codebase handles a hierarchical indented tree, only flat tables). Confirmed exactly implementable
from reading `stage5_tree_render.py`'s own rendering functions:
- `format_aligned_rows()`'s exact line shape: `f"{chunks[0]:<{label_width}}  " + "  ".join(cells)`
  for a real data row's first physical line, vs. bare, unpadded continuation text (`chunks[1:]`)
  for a hard-wrapped long label's later physical lines -- `REPORT_HEADERS`'s own widths give
  `suffix_width = sum(2 + width for _, width, _ in REPORT_HEADERS)` exactly, so a line is a real
  data row iff its final `suffix_width` characters parse as that many right-aligned numeric/`-`
  cells; otherwise it's a continuation fragment, appended to the previous real row's label text
  (mirroring `wrap_leading_labels()`'s own character-level-cut convention, so concatenation
  reconstructs the exact original label).
- Depth from each real row's leading tree-connector prefix (`├── `/`└── `, with `│   `/`    `
  prefix groups above it; a root has none) -- reconstructed via a depth-tracked stack (pop while
  the top's depth >= this row's depth, parent = the new top, push), exactly like parsing any
  indented-text tree (e.g. `tree` command output).
- The **default** (not `--show-all-internals`) `calltree.txt` is sufficient -- confirmed by
  reasoning through this project's own noise-handling semantics: wrapper-splicing/MPI-collapsing
  never hide a real ancestor above a visible node (they only remove/collapse *within*/*below* a
  subtree), and whole-subtree pruning (GPU-API/compiler-runtime) can only hide a pruned node's own
  descendants -- so if a hotspot is visible in the default tree at all, nothing between it and the
  tree's root was pruned away.

Once built, this feeds the exact same, already-existing `caller_chains_for_label()` unchanged, so
the ancestor-walk logic itself is 100% reused regardless of which data source produced the pool.

### `select_instrumented_functions.py` (renamed CLI, thin composition over the above)

1. Base selection unchanged: `labels_from_output_dir()`/`labels_from_report()`'s existing
   self/inclusive-time threshold produces the starting label set.
2. If `--gpu-output-dir DIR` given: `select_hotspot_kernels.labels_from_output_dir(DIR, ...)` gets
   GPU kernel hotspot names, `resolve_kernel_owners()` decodes them, decoded owners join the set.
3. If `--ancestor-depth` > 0 (default 1): build the flat pool (from `--output-dir`'s live tree via
   `load_rank_trees()`/`merge_rank_trees()`/`flatten_tree()` -- `extract_hotspot_callers.py`'s
   exact existing pipeline, no new tree-building code -- or from `--report`'s sibling
   `calltree.txt` via the new parser, erroring clearly if that file is missing), then
   `expand_labels_with_ancestors(flat, current_labels, depth)`, adding whatever it returns.
4. Prints a clear breakdown to stderr, mirroring `instrument_hotspots.sh`'s existing
   `"selected hotspot functions (N):"` line, now split: *N hotspot function(s) selected by
   [self/inclusive] time* + *M ancestor/owner function(s) added for tree connectivity
   (--ancestor-depth D)* -- direct, user-visible answer to "weighed against its overhead."

Output contract unchanged: `label<TAB>regex` lines via the existing `escape_for_instrument_regex()`,
so `instrument_hotspots.sh` only needs its `SELECTOR=` path and one new passthrough flag updated,
not a protocol change. `--check-instrumented`/`find_lost_functions()` move to the renamed file
unchanged.
