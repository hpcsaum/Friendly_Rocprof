# Plan 3.8: time-ordering-based kernel re-anchoring, baked into the cached per-rank aggregate

## Context

Running `extract_trace_calltree.py` against the real 4-rank `Heat_Convection_Solver` trace showed
every GPU kernel nested under one single `hipModuleLaunchKernel` node, losing which real Fortran
subroutine each kernel conceptually belongs to. Traced directly (not guessed): this is **not** a
filtering/aggregation-ordering bug — the raw trace's own captured call-tree structure genuinely is
`ompt_implicit_task → ompt_target → hipModuleLaunchKernel → [every kernel in the whole program]`.
rocprof-sys's OMPT-based instrumentation captures one generic entry point per `omp target` region
across the *entire* program, not a per-callsite-distinct one — so the `corr_id` join (which links
each kernel dispatch to the exact host-side launch call that issued it) correctly finds that exact
launch call, but that launch call itself sits at a structurally uninformative, shared position for
every kernel in the program. `corr_id` can't recover ownership information the trace's own
structural ancestry never captured in the first place.

Cray's kernel naming convention embeds the real owning subroutine directly in the kernel's own name
(`<subroutine>$<module>_mod_$ck_L<line>_<n>...`, decoded by
`stage4_rocprofsys_sample_tree.kernel_owner_label()`), and that owning subroutine does appear as its
own CPU tree node elsewhere in the real trace — confirmed directly: the kernel
`convection_stable_dt$convection_time_integrator_mod_$ck_L558_99.kd` and a CPU node literally named
`convection_stable_dt$convection_time_integrator_mod_` both exist in the same merged tree, just not
adjacent.

**Checked whether `test_apps`'s HIP-launched kernels hit this same bug — they don't.** Every
`test_apps` app also has a native HIP path (`kernel_hip.cpp`'s `stencil_kernel`, launched via
`hipLaunchKernelGGL` from a plain, real C/C++/Fortran-bound function, `launch_hip_kernel` — not an
`omp target` region at all). The existing `trace_single_rank` fixture already models exactly this
shape (`hipLaunchKernel` nested directly under `jacobi_sweep`, a real, call-site-specific node, not
a shared one) and its corr_id join already places the kernel correctly, unmodified by this plan.
The underlying reason: OMPT registers a single, program-wide callback for every `ompt_target`/
`ompt_implicit_task` event, so that "frame" is structurally the same node no matter which `omp
target` region triggered it; a HIP API call, by contrast, is intercepted at its real call site, so
its ancestry already reflects the actual (and already call-site-unique) caller. `stencil_kernel`'s
own name also matches neither the `$ck_` marker nor the generic pattern below, so
`kernel_owner_label()` returns it unchanged and this plan's whole re-anchoring mechanism is
correctly a no-op for it — it was never broken, and stays untouched.

**Checked whether the OMPT-specific bug is Cray-Fortran-specific, using `test_apps/results/` (real
`rocprofv3` `kernel_stats.csv` output from all 6 language × compiler combos this project already
tests against — C/C++/Fortran, each with both AMD's and Cray's toolchain)**: Cray's own Fortran
frontend is the only one using the `$ck_` marker. Every other combo (AMD C, AMD C++, AMD Fortran,
Cray C, Cray C++) instead uses the standard LLVM OpenMP-offloading kernel name shape:
`__omp_offloading_<hex>_<hex>_<name>_l<line>[_cce$noloop$form]`, e.g.
`__omp_offloading_4f_8fb8861__Z17launch_omp_kernelPdi_l6` (AMD C++, `<name>` Itanium-mangled) or
`__omp_offloading_4f_8fb7ea6__QMkernel_omp_modPlaunch_omp_kernel_l12` (AMD Fortran, `<name>`
Flang-module-mangled). Stripping the `__omp_offloading_<hex>_<hex>_` prefix and `_l<line>[_cce...]`
suffix, then demangling the simple, common shape of `<name>` (Itanium `_Z<len><name>...`; Flang
`_QM<module>P<name>` or `_QP<name>`), recovers the plain source function name — `launch_omp_kernel`
for every one of those examples — confirmed directly against all 5 non-Cray-Fortran samples in
`test_apps/results/`. This generalizes `kernel_owner_label()` from "Cray Fortran only" to every
compiler this project already tests, at no cost to the Cray-Fortran case (the `$ck_` check stays,
tried first). A name matching neither pattern (`__amd_rocclr_copyBuffer`, `stencil_kernel`,
`__omp_dm_init_kernel` — a generic device-runtime init/copy kernel, not tied to any one source
function) is left unchanged, same as today — no owner to match, no guessing.

Matching by name alone still is not enough even with this broadened decoding: checked directly
against the real rank-0 data, 15 of 26 real kernels have their owner name matching **two** distinct,
genuinely real CPU tree positions (not a merge artifact) — a subroutine legitimately called from two
different places. A design that only reanchors on an unambiguous single match produced zero visible
improvement on the real data (every real kernel hit 0 or 2+ candidates, never exactly 1); a design
that falls back to splitting a kernel's time proportionally across ambiguous candidates (by each
candidate's own call count, mirroring
`stage4_rocprofsys_sample_tree._attach_kernel_group()`'s existing approach for its own equivalent
problem) is an *estimate*, and checked directly against the real ambiguous case
(`jacobi_sweep$pressure_solver_mod_`), it would be a **measurably wrong** one — see below.

**The chosen design instead uses the trace's own timeline.** A rank's CPU side runs on one thread
per call stack — at any instant, exactly one frame on a given thread's stack is active — so a
kernel dispatch's real caller isn't ambiguous in the trace's own timestamps, even when it's
ambiguous by label alone. Validated directly against real rank-0 data before committing to this:

- Unambiguous case (`compute_rhs$heat_operator_mod_`, single owner position, 80 raw call
  instances): each of its 10 real kernel dispatches lands 49,000–100,000 ns after its nearest
  preceding owner-call instance ends, and 300,000,000+ ns before the *next* owner-call instance
  starts — a huge, unambiguous margin, no ties.
- The actual ambiguous-by-label case this plan exists for (`jacobi_sweep$pressure_solver_mod_`):
  raw data shows 24,000 instances of that label across two real parent chains — 6,000 as a direct
  child of `ompt_implicit_task`, 18,000 nested *inside another instance of the same label* (a
  compiler-inserted inner frame for the actual offload region). All 3,000 real kernel dispatches
  for this subroutine resolve, via nearest-preceding-instance-in-time, to the **same one** of the
  two candidate positions every single time (the inner, self-nested one), with gaps of 49–478
  microseconds — zero ties. The outer position never launches a single kernel in the real data, so
  a proportional split (weighted by call count) would have given it a nonzero, wrong share.

This supersedes an earlier proportional-split design considered while drafting this plan — real-data
testing showed the underlying timeline evidence resolves the same cases exactly, so there's no case
left that genuinely needs an estimate.

**Stated limitation, not solved here (per explicit direction)**: this technique's correctness rests
on "the launching thread's own recorded call frames never overlap in time" — true by construction
for a single thread's real call stack, but not a property of the *whole rank* being single-threaded.
The design below scopes candidate matching to the same CPU thread (`tid`) that issued the launch, so
it does not require the whole rank's CPU side to be single-threaded — but it does still assume each
individual thread's own instrumented frames are strictly serial (no coroutines/fibers/signal-handler
reentrancy interleaving frames on one thread with overlapping `[ts, ts+dur]` ranges). That's true for
this project's target profile (C/C++/Fortran, MPI + OpenMP), and is called out explicitly in code
comments and in `extract_trace_calltree.py`'s help text rather than silently assumed.

**Directed correction from an earlier draft of this plan**: re-anchoring runs *inside*
`build_rank_aggregate()`, right after the `corr_id` join, not later at
`stage5_trace_calltree_view.py`'s tree-render time — the same *kind* of operation as the `corr_id`
join itself (a structural correction based on additional evidence, not a display-only decision), so
it belongs in the same place, computed once per rank and baked into the cached aggregate.

## Approach

### Move + generalize `kernel_owner_label()` in `stage4_rocprofsys_common.py`

Moves verbatim first (it's a single-line, purely generic string function with zero sample-format
dependency — the same "this turned out to be generic, not sample-specific" pattern plans 3.4 and
3.5 already found twice for other functions); `stage4_rocprofsys_sample_tree.py`'s own
`attach_kernel_summaries()` (its only existing caller) updates its import to pull it from
`stage4_rocprofsys_common` instead of defining it locally.

Then broadened, per the `test_apps/results/` finding above, to decode two patterns instead of one
(tried in order, first match wins; no match returns the name unchanged, same as today):
1. Cray Fortran's existing `$ck_` marker (unchanged): `name.split("$ck_", 1)[0]`.
2. The generic LLVM OpenMP-offloading shape:
   `__omp_offloading_<hex>_<hex>_<mangled>_l<line>[_cce$noloop$form]`, one regex to strip the
   prefix/suffix and isolate `<mangled>`, then a small demangle step for `<mangled>`: Itanium
   C++ (`_Z<len><name>...` → take the next `<len>` characters as `<name>`) or Flang Fortran
   (`_QM<module>P<name>` or `_QP<name>` → `<name>`); anything else in `<mangled>` (a plain C
   function name) is returned as-is. A `<mangled>` shape neither pattern recognizes (e.g. a
   namespaced or templated C++ symbol) falls back to returning the raw `<mangled>` segment
   unchanged, rather than guessing — consistent with this function's existing "no marker, no
   match" behavior.

Its two existing tests in `test_stage4_rocprofsys_sample_tree.py` move to
`test_stage4_rocprofsys_common.py` alongside it, joined by new cases for the generic pattern —
one per `test_apps/results/` combo actually observed (AMD C, AMD C++, AMD Fortran, Cray C, Cray
C++), plus a name matching neither pattern staying unchanged.

### New: `stage4_rocprofsys_trace_aggregate._reanchor_kernels_by_owner_and_time(rows)`

Operates on **raw, per-instance rows** — the same shape/stage `_attach_kernels_by_corr_id()`
already operates on (`parse_trace_csv()` + `attach_ancestry()`'s output: individual call instances,
each with its own `ts`/`dur`/`tid`/`parent`, before `merge_rank_trees()` collapses repeated
same-position calls). This must run at this stage, not later: only here does each raw instance still
carry its own `ts`; a post-merge design would already have collapsed instances into one row per
tree position, discarding exactly the timestamps this technique needs.

For every row where `tag_for_category(row.get("category")) == "gpu_kernel"` (same classification
`_attach_kernels_by_corr_id()` already uses):
1. `owner = kernel_owner_label(row["name"])`. If `owner == row["name"]` (neither the `$ck_` marker
   nor the generic `__omp_offloading_...` shape matched), skip — no name to match, leave the row at
   whatever `_attach_kernels_by_corr_id()` already gave it.
2. Determine the launching thread: `launch_tid = row["parent"]["tid"]` if the corr_id join above
   already gave this row a parent (it always will have attempted to; a kernel row's `parent` is
   `None` only when corr_id genuinely didn't resolve). No resolved parent → skip, same as today —
   there's no launching frame to anchor the search to.
3. Candidates: every *other* raw row with `row["name"] == owner` **and** `row["tid"] == launch_tid`
   — scoping to the same thread is what makes this correct without assuming the whole rank's CPU
   side is single-threaded; it only relies on that one thread's own frames being serial.
4. Sort candidates by `ts`; binary-search for the last one starting at or before this kernel row's
   own `ts`. Found → `row["parent"] = that candidate`, overriding the corr_id-based placement from
   step 2 (intentional — this is a refinement layered on top, using the same `parent` link). Not
   found (kernel dispatched before any candidate on that thread even started, or zero candidates
   exist on that thread at all) → leave the row exactly where `_attach_kernels_by_corr_id()` already
   put it. No proportional splitting, no guessing — an unresolvable case is left at its existing,
   honest position, matching every other "don't guess" precedent already in this codebase
   (`attach_ancestry()`, `_attach_kernels_by_corr_id()`'s own ambiguous-corr_id case).

Implemented as a void mutator (mutates `row["parent"]` in place), exactly like
`_attach_kernels_by_corr_id()` — no row splitting, no returned/replaced list, so
`build_rank_aggregate()` needs no reassignment plumbing.

Called in `build_rank_aggregate()` right after `_attach_kernels_by_corr_id(rows)` and before
`tag_rows(rows)` — same ordering reason already documented for the corr_id join: `tag_rows()`'s
sibling-group derivation must see each kernel row's **final** structural position, not an
intermediate one, or it can wrongly flag a real sibling's subtree as noise-contaminated. Runs before
`roots = [...]`/`merge_rank_trees(...)` so the ordinary intra-rank merge naturally collapses however
many kernel instances end up parented at each real position, with exact counts — no changes needed
in `_flatten_rank_merge()` or the merge step itself. `stage4_rocprofsys_trace_tree.merge_ranks()`'s
cross-rank merge also needs no changes: every rank runs the same binary and reanchors the same way,
so the existing cross-rank "merge by label at each tree level" recombines correctly with zero new
code there.

This is a strict improvement layered on top of the existing `corr_id` join, not a replacement — a
kernel whose owner name can't be matched on the launching thread still ends up exactly where
`corr_id` alone placed it, same as today.

### Documentation

`extract_trace_calltree.py`'s `HELP_BLURB` gets one added paragraph, in the existing caveat style: a
kernel sharing a generic launch entry point with every other kernel in the program (common under
OMPT-based `omp target` instrumentation) is further reanchored onto the exact CPU call instance —
found via the kernel's own embedded owner name (Cray Fortran's `$ck_` marker, or the generic LLVM
OpenMP-offloading kernel name shape every other tested compiler uses) and the trace's timestamps,
not a guess — that was actually running on the same thread immediately before the kernel dispatched.
This is exact, not an estimate, but relies on that one CPU thread's own recorded call frames never
overlapping in time (true for a normal call stack); a kernel whose owner name doesn't appear on its
launching thread at all, or whose name matches neither recognized convention, still shows up at its
exact `corr_id` position, unchanged.

### A real operational caveat worth stating, not solving here

The on-disk cache's only invalidation check is "cache mtime ≥ every source CSV's mtime" — it has no
notion of "the code that builds it changed." Any `.agg.json` file already on disk from before this
fix (including ones already written into the real `Heat_Convection_Solver` directory) will be
silently reused as-is until its source CSV is touched or the cache file is deleted by hand.
Verification below deletes the existing real-data cache files explicitly, and this is called out as
a known gap, not something this plan adds versioning for.

### Tests

Updated fixture (`trace_kernel_owner_reanchor/rank0.csv`): raw rows carrying `tid` on every host
row, with causally-correct timestamps (the owner call starts before the kernel it launches
dispatches) covering the end-to-end unambiguous case. Additional scenarios — the genuinely
ambiguous-by-label case (two same-thread candidates at different times, resolved to the
chronologically correct one, not split), a same-label collision across different threads (proving
`tid`-scoping picks the correct same-thread candidate over a naive rank-wide nearest-preceding
search), no candidate on the launching thread, no recognizable owner-name convention, and no
corr_id-resolved parent — are covered by hand-built raw-row unit tests directly against
`_reanchor_kernels_by_owner_and_time()` in `test_stage4_rocprofsys_trace_aggregate.py`'s
`ReanchorKernelsByOwnerAndTimeTests` class. Existing `trace_two_rank`/`trace_calltree_noise`/
`trace_single_rank` fixtures use kernel names matching neither owner-name convention, so this change
stays confirmed as a no-op there — full existing suite must stay green, including the cache
round-trip tests (the cached shape itself doesn't change).
