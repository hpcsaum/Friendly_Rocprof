# Plan 3.13: time-range filtering for the trace-CSV report tools

## Context

The trace-CSV pipeline (`extract_trace_hotspots.py`/`extract_trace_calltree.py`/`extract_trace_pop_metrics.py`)
currently always reports over a run's *entire* recorded span. That mixes initialization/teardown
time in with the steady-state work, and makes it impossible to isolate a single iteration or phase
of interest -- exactly the two examples the user gave. This plan adds an optional `--time-range`
flag to all three report tools so every final table and the call tree only reflect activity within
one or more user-chosen windows, with two precise requirements: (1) a call straddling a window
boundary still contributes its in-window portion of self/inclusive time, not all-or-nothing; (2) a
whole call-tree subtree with zero overlap anywhere within it is cut from the rendered tree, but the
ancestor chain down to any surviving descendant stays intact. Every report should also always show,
in its header, exactly what time window it reflects -- the real full run span by default, or the
requested window(s) (with any open start/end resolved against that real span) when `--time-range`
is given.

Researched via 3 parallel Explore agents (trace data model/timestamps, CLI/shared-flag
conventions, tree-pruning mechanics) plus direct reads of every touched file, then validated
end-to-end by a Plan agent that re-derived the clipping math's correctness and caught two real
gaps in an earlier draft (see Design notes below). Key finding that shapes the whole design: raw
per-call `ts`/`dur` only exist, per rank, up through
`stage4_rocprofsys_trace_aggregate.build_rank_aggregate()` -- specifically everything before its
`merge_rank_trees()` call, which is the one place per-call rows collapse into pre-summed
`count`/`self_sum`/`sum` at each tree position. Every downstream consumer (hotspots' `pct_total`
denominator, pop metrics' `total_time`/`comm_time`/`gpu_busy_time`, load imbalance, the calltree)
only ever reads that pre-summed aggregate. This means clipping durations to the requested range(s)
at that one point, before the collapse, makes every downstream report automatically range-scoped
with **no changes needed** to `stage4_rocprofsys_trace_flat.py`'s math, `stage5_fused_hotspots_table.py`,
`stage5_load_imbalance_table.py`, or `stage5_pop_metrics_table.py`.

Per the user's explicit direction, the active range is threaded through as **process-wide global
state, not a parameter passed down through every intervening function** -- exactly the precedent
`postprocess/stage6/stage6_noise_config.py` already established for `--extra-noise-config` (plan
2.12): a module-level singleton, configured once by a tool's own `main()` right after
`parse_args()`, read directly by whichever lower-stage function needs it. That module's own
docstring states the reasoning this plan reuses verbatim: "every real invocation of this codebase
is a single, one-shot CLI process with exactly one configuration for its whole run, so a
module-level singleton is simpler and just as correct as parameter-threading." Following this
precedent means `stage4_rocprofsys_trace_flat.py` and `stage4_rocprofsys_trace_tree.py` need **no
changes at all** for range-*filtering* -- only `stage4_rocprofsys_trace_aggregate.py` (the one
place `ts`/`dur` are read) and `stage5_trace_calltree_view.py` (which needs to know whether to add
the new pruning predicate) ever read the new config module.

Separately (per the user's follow-up direction on reporting the active window): the run's real,
unfiltered time extent is a **generic fact about the trace, independent of whether any range was
requested at all** -- so it's computed once in `stage4_rocprofsys_trace_aggregate.py` (the module
that already reads raw `ts`/`dur`) as its own small addition, not folded into the range-filtering
machinery. Producing the report-header note from it is a genuinely new kind of pipeline output --
a stage4 fact flowing straight into a report header/footer, bypassing stage5's table/tree rendering
entirely, for a concern (self-documenting the active window) shared identically by all three
tools. Per the user's direction, this is handled by one common stage6 function rather than
duplicated per tool: `stage6_time_range_config.describe_time_range()` is explicitly allowed to
import and call the stage4 extent function directly -- a deliberate, one-off stage6 -> stage4
dependency for exactly this new kind of output, not a general pattern.

## Confirmed decisions (from the user)

1. **CLI syntax**: `--time-range START:END`. Either half may be omitted (`10:` = 10s to the end,
   `:10` = start to 10s). Multiple comma-separated windows may be given (`0:5,10:`), combined as a
   union. Units are seconds, matching every other duration already shown in these reports.
2. **Scope**: only `extract_trace_hotspots.py`, `extract_trace_calltree.py`, and
   `extract_trace_pop_metrics.py` get the flag this round. `convert_trace_to_csv.py` (full-fidelity
   proto->CSV conversion) and `scripts/profile_traced_hotspots.sh` are explicitly out of scope.
3. **Caching**: the per-rank on-disk cache (`<rank_key>.agg.json`) must never proliferate into one
   file per distinct range. The active range is stored *inside* that single cache file and compared
   on read; a mismatch rebuilds and overwrites the same file (never a second one).
4. **Range threading**: process-wide global config (mirroring `stage6_noise_config.py`), not
   parameter-passing down through `stage4_rocprofsys_trace_flat.py`/`stage4_rocprofsys_trace_tree.py`.
5. **Report header note**: always printed, in every report, regardless of whether `--time-range`
   was used -- the real run extent by default, the requested window(s) (with open ends resolved
   against that real extent) when given. Built by one common stage6 function
   (`stage6_time_range_config.describe_time_range()`) that each tool's `write_report()` calls once
   -- not duplicated per tool, and not left to the CLI/config module's parsing logic alone, since
   resolving an open bound needs the real extent, which only stage4 has.

## Design

### 1. The global config module (new `postprocess/stage6/stage6_time_range_config.py`)

Mirrors `stage6_noise_config.py`'s exact shape:
- `_RANGES = None` module-level global (canonical form, or `None` meaning "no filtering" -- the
  correct default with nothing to lazily load, unlike noise config's bundled-JSON case).
- `parse_time_range(raw)` -- a pure, directly-testable function: `None` in, `None` out. Otherwise
  splits `raw` on `,`; each segment **must** contain a literal `:` (a bare `--time-range 10` is
  rejected with a clear `SystemExit`, not silently guessed as start or end); splits into
  `(start_str, end_str)`, empty half -> `None`, non-empty half -> `float()` (bad parse ->
  `SystemExit`); at least one bound required per segment; `start < end` strictly enforced when both
  are given. Then sorts and merges overlapping-**or-touching** segments (`end_i == start_{i+1}`
  counts as mergeable, so a call landing exactly on a shared boundary between two given windows
  isn't ambiguously double-counted or dropped) into a canonical, minimal, disjoint
  `[(start_or_None, end_or_None), ...]` list, treating `None` as -inf/+inf for ordering only (and
  preserving it as `None` in the output).
- `configure(raw)` -- `global _RANGES; _RANGES = parse_time_range(raw)`. Safe to call again (always
  fully replaces, never merges) -- needed so tests can reset between cases
  (`self.addCleanup(configure, None)`, the same convention `test_stage6_noise_config.py` already
  uses for its own module).
- `active_ranges()` -- returns `_RANGES` directly.
- `add_cli_argument(parser)` -- adds `--time-range` (`dest="time_range"`, `type=str`,
  `default=None`), same shape as `stage6_noise_config.add_cli_argument()`.
- `configure_from_args(args)` -- `configure(args.time_range)`, the one line each tool's `main()`
  needs right after `parser.parse_args()` -- mirrors `stage6_noise_config.configure_from_args()`
  exactly, called the same way, right next to the existing noise-config call in each tool.
- `describe_time_range(rank_inputs, cache_dir=None)` -- the one call each tool's `write_report()`
  makes for its always-printed header note (see section 8). Loops `rank_inputs` calling
  `stage4_rocprofsys_trace_aggregate.get_rank_time_extent()` per rank (an explicit, deliberate
  `stage6 -> stage4` import -- see the Context note on why this one function is allowed to reach
  past stage5), combines into one run-wide `(start, end)`, reads `active_ranges()`, and returns one
  formatted line covering both the "no range" and "range given" cases (section 8 has the exact
  formatting). The per-rank-extent-combining and formatting logic is kept in a private, pure,
  directly-testable helper (`_format_note(run_extent, ranges)`) that this function calls after
  gathering its two inputs -- so the formatting rules stay unit-testable without any file I/O or
  global-state setup.

This module owns *parsing/storing the requested range* and *describing the active window for a
report header*. The "storing" half never reaches outside its own global; the "describing" half is
the one deliberate exception to the "stage6 doesn't reach into stage4" default (see Context) --
and, per the user's direction, this exception is documented as a **general, reusable pattern**, not
a one-off: `postprocess/README.md`'s existing "Cross-stage imports" section already states the
codebase's current import rules explicitly (stage4/stage5 import from stage1-3, stage3 imports from
stage6); it gains one more clause covering this case -- a stage6 module may import directly from
stage4 specifically to produce a **non-table-specific** report output (a header/footer note, not a
rendered table or tree) that has no reason to route through stage5's rendering machinery at all.
`describe_time_range()` is the first instance of this pattern, written up as the reusable
precedent for the next one.

### 2. Clipping (`postprocess/stage4/stage4_rocprofsys_trace_aggregate.py`)

New private `_overlap_with_ranges(ts, dur, ranges)` -> `(clipped_width, touches)`, where `touches`
is a separate closed-interval intersection test (not `clipped_width > 0`) -- needed because a
zero-duration event landing exactly inside a window has `clipped_width == 0` either way, and must
not be misclassified as "never touched the range."

New private `_clip_rows_to_time_ranges(rows, ranges)`, run inside `build_rank_aggregate()` right
after the extent is computed (section 3) and before `_synthesize_self_sum(rows)`, guarded by
`ranges = stage6_time_range_config.active_ranges()` (only when truthy): for every row, sets
`row["dur"] = clipped_width` and a transient `row["_touches_range"] = touches`.
**Critical invariant: this must mutate only `"dur"`, never `"ts"`.** `_reanchor_kernels_by_owner_and_time()`
runs later in the same function and depends on every row's real, unclamped start time for its
bisect-based "most recent same-owner instance on this thread" search; clamping `ts` would corrupt
that chronological ordering.

`_synthesize_self_sum(rows)` gets a one-line change: `row["count"] = 0 if row.get("_touches_range")
is False else 1` (absent key on the unranged path falls through to `1`, so no `if ranges:` branch
is needed inside this function). This makes "calls" in a ranged report mean "calls with any overlap
with the window," matching what `stage5_fused_hotspots_table.py` and
`stage4_rocprofsys_common.aggregate_node_stats()` both render it as.

**Why this is provably safe**: for any row `P` with structural children `C_1..C_n` (already
wall-clock nested via `parent_slice_id`, pairwise disjoint since one thread's frames don't
overlap), intersecting every interval with the same range set preserves both nesting and
disjointness, so `clipped_self_sum = overlap(P) - sum(overlap(C_i)) >= 0` always holds -- clipping
can't manufacture a new negative self-time case. The one place nesting doesn't hold today (a
GPU-kernel-dispatch row reparented via corr_id, which can run concurrently with its launch call
rather than strictly inside it -- see `_synthesize_self_sum()`'s own existing docstring) is
unaffected: both reparenting steps run *after* self-time synthesis, so a kernel's own duration
never feeds into its new parent's self-time math, clipped or not.

`get_rank_aggregate(csv_paths, rank_key, cache_dir=None)` keeps its **current public signature and
return contract (just `rows`)** -- it reads `stage6_time_range_config.active_ranges()` itself,
internally, rather than accepting it as a parameter (adds one import,
`stage6_time_range_config`, following the exact `stage3 -> stage6` one-directional-dependency
precedent `stage3_rocprofsys_common.tag_rows()` already established for the noise-config module).

### 3. Real time extent (new, same file) -- independent of any active range

New private `_compute_time_extent(rows)` -> `(start, end)`: `(min(r["ts"] for r in rows),
max(r["ts"] + r["dur"] for r in rows))` over the **raw, unclipped** rows, or `(0.0, 0.0)` if empty.
Called inside `build_rank_aggregate()` right after `attach_ancestry(rows)` -- i.e. *before* any
clipping runs (section 2) -- so it always reflects this rank's true full span regardless of
`--time-range`. `build_rank_aggregate()`'s return value becomes `(flat_rows, extent)` (a local,
contained change: it's called only from `get_rank_aggregate()` and this module's own tests, never
from `stage4_rocprofsys_trace_flat.py`/`stage4_rocprofsys_trace_tree.py`, which only ever call
`get_rank_aggregate()`).

`get_rank_aggregate()`'s cache payload (section 4 below) gains an `"extent"` field alongside
`"rows"`; its own public return value stays `rows`-only, unpacking the tuple internally.

New public `get_rank_time_extent(csv_paths, rank_key, cache_dir=None)` -> `(start, end)`: calls
`get_rank_aggregate(csv_paths, rank_key, cache_dir=cache_dir)` first (guaranteeing a fresh cache
file exists on disk, built or hit), then re-opens that same `<rank_key>.agg.json` and returns its
`"extent"` field -- no second freshness check needed, since the preceding call already guarantees
one. A little redundant I/O (one extra small JSON read) in exchange for not restructuring
`get_rank_aggregate()`'s existing contract or duplicating its cache-freshness logic -- consistent
with this module's own cache being "a pure performance optimization," not a hot path.

This is the one function `stage6_time_range_config.describe_time_range()` (section 1) calls per
rank to combine into one run-wide extent -- kept as a single, common call site there instead of
duplicated inline in each of the 3 tools' `write_report()`.

### 4. Cache format (same file, `stage4_rocprofsys_trace_aggregate.py`)

New private `_encode_ranges(ranges)` -> `None` or a JSON-safe `[[start_or_None, end_or_None], ...]`.
`_encode_rows`/`_decode_rows` stay row-only; `get_rank_aggregate()` wraps everything:
`{"ranges": _encode_ranges(ranges), "extent": list(extent), "rows": _encode_rows(rows)}`, where
`ranges` here is the same `active_ranges()` value already read for the clip step. A cache hit now
requires the existing mtime-freshness check **and** `isinstance(payload, dict)` **and**
`payload.get("ranges") == _encode_ranges(active_ranges())`. Any mismatch -- including an old,
pre-this-plan cache file (a bare JSON array, no `"ranges"` key) -- is a graceful miss: rebuild via
`build_rank_aggregate()`, overwrite the *same* `<rank_key>.agg.json` path. No cache format-version
field or separate migration step needed; the explicit `isinstance` guard is preferred over
broadening the caught-exception tuple, since that would also silently swallow unrelated bugs.

### 5. Subtree pruning (new function in `postprocess/stage4/stage4_rocprofsys_common.py`)

New `make_zero_time_pruned(merged_roots)`: a bottom-up (post-order) walk of the merged tree via
each node's own native `"children"` dict (`merge_rank_trees()`'s own output shape -- no auxiliary
children-map needed, and no dependency on `flatten_tree()`'s flat list). Per node:
`has_time = sum(entry["self_sum"] for entry in node["per_rank"].values()) > 0 or any(child has
time for a child)`. Returns an `is_pruned(node)`-compatible closure (same shape as
`stage3_rocprofsys_trace.make_is_pruned(tags)`) over the resulting "entirely zero" node-id set.

This must be bottom-up, not a plain per-node check, specifically because of the corr_id/owner
kernel-reparenting exception above: a brief `hipLaunchKernel` call's own instant can fall outside a
window while the kernel it dispatched -- reparented as its child, but independently timed -- falls
inside it. A per-node-only check would wrongly prune that whole branch, breaking the "ancestor
chain stays intact" requirement. `self_sum` (not `sum`) is used for the per-node contribution, since
it's the minimal non-redundant signal -- the recursion itself already accounts for descendants.

This predicate composes with the existing tag-based `is_pruned` via a simple OR, and only when a
range was actually requested -- so it has zero effect on any report that doesn't use the new flag.

### 6. `stage4_rocprofsys_trace_flat.py` / `stage4_rocprofsys_trace_tree.py`

**No changes.** `aggregate()`, `aggregate_per_rank()`, `gather_timing_summary_per_rank()`, and
`merge_ranks()` all route through `get_rank_aggregate()`, which now resolves the active range
itself -- this is the direct payoff of using global config instead of parameter-threading. Extent
reporting also avoids these files entirely (section 3) -- the per-rank-to-run-wide reduction lives
in `stage6_time_range_config.describe_time_range()`, not here.

### 7. `stage5_trace_calltree_view.py`

`build_calltree_view()` keeps its **current signature** (no new parameter). It imports
`stage6_time_range_config` and, right after `merged_roots` is built, checks
`stage6_time_range_config.active_ranges()`: when truthy, ORs `make_zero_time_pruned(merged_roots)`
into the existing tag-based `is_pruned`. No other change.

### 8. Report header note -- formatting (inside `stage6_time_range_config.describe_time_range()`)

Its private `_format_note(run_extent, ranges)` helper (section 1) -> one formatted line, **always**
returning a real string (never conditional/`None`) -- covers both "no `--time-range` given" (formats
`run_extent` itself, the real full span, e.g. `"  time range: 0.000s-45.321s (full run)\n"`) and "a
range was given" (formats each window in `ranges`, resolving any `None` start/end against
`run_extent`'s corresponding bound, e.g. `"  time range: 5.000s-12.500s, 20.000s-45.321s\n"`). Kept
private and pure/argument-only (not reading the globals itself) so it's directly unit-testable
without global-state setup or file I/O -- `describe_time_range()` is the thin public wrapper that
gathers the two real inputs (via `get_rank_time_extent()` and `active_ranges()`) and calls it.

`stage6_report_builder.py` itself is **not touched** -- it already accepts arbitrary
`extra_lines` per `runs[i]` entry (used today by `extract_trace_pop_metrics.py`), which is exactly
the slot each tool's `write_report()` puts this note into (section 9). It stays a generic,
pipeline-agnostic report-assembly module with no new knowledge of time ranges at all.

### 9. Wiring into the 3 CLI tools

Each `main()`: call `stage6_time_range_config.add_cli_argument(parser)` and, right after
`parser.parse_args()`, `stage6_time_range_config.configure_from_args(args)` -- placed directly next
to the tool's existing `stage6_noise_config.configure_from_args(args)` call, same pattern, same
spot. Append the raw `args.time_range` string verbatim to the tool's own `command_header()` token
list (matching every other flag's echo-back convention).

`write_report()` functions keep their **current signatures** (no new `ranges` parameter) -- they
already end up calling `aggregate()`/`aggregate_per_rank()`/`gather_timing_summary_per_rank()`/
`build_calltree_view()`, all of which now resolve the active range on their own via the global.
Each additionally calls `stage6_time_range_config.describe_time_range(rank_inputs, cache_dir=...)`
once and adds the returned line, **unconditionally**, to every `runs[i]["extra_lines"]` list it
builds for `standard_header()` (for pop metrics specifically, once per `run_dir` in its multi-run
loop, each against that run's own `rank_inputs`).
