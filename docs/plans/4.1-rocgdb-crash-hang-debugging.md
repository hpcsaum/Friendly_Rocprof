# Roadmap: rocgdb-based crash/hang debugging for MPI jobs

## Context

Users porting/debugging MPI+ROCm codebases on this project's target HPC systems hit crashes and
hangs they don't know how to root-cause, because attaching `rocgdb` correctly across many MPI ranks
(and, for GPU code, matching `amd-dbgapi`'s expected environment) is genuinely fiddly. The goal is
two small, `-h`-documented launcher tools, consistent with every other tool in `scripts/` — both
named `debug_<what>` and both taking the same `--mpi "<launch cmd>"` convention every other launcher
here uses (this always runs inside a submitted PBS/Slurm job script, same as the profiling launchers)
— that do this automatically and drop a backtrace per rank on disk.

A colleague already solved the **hang** half of this for a real case: `hangwatch.py`, at
`/home/saumet/Documents/Porting_Adventure/hangwatch-backtrace-kill/hangwatch.py` (sibling directory,
outside this repo, not version-controlled) — validated end-to-end on HLRS's Hunter (PBS) and
supporting Slurm too. It watches a job's output for silence, then live-attaches `rocgdb -p PID
--batch` to every GPU-holding rank on every node (via `pbsdsh`/`srun --overlap`, auto-detecting the
scheduler), and cancels the job afterward. Its one genuinely non-obvious finding, worth preserving
exactly: the remote `collect` step must run `rocgdb` under the **submitting shell's own environment**
(captured post module-load), or `amd-dbgapi` version-mismatches against the app's ROCm build and GPU
wavefronts silently go missing from the backtrace.

That script does **not** cover the immediate-crash case (a rank that segfaults just exits — no hang,
no backtrace collected) — that needs a different technique: wrap the process under `rocgdb -batch -ex
run -ex bt` from the moment it launches, so gdb is already attached when the signal arrives.

Both tools must also work standalone on a single rank with no MPI and (for `debug_hang.py`) no
scheduler at all — e.g. reproducing a crash/hang locally on one process before escalating to a full
HPC job. `--mpi` is optional on both, exactly like every other launcher in `scripts/`.

Two decisions made during exploration/planning (confirmed with the user):
- Adopt `hangwatch.py` into this repo largely unchanged for the hang case, renamed **`debug_hang.py`**
  to match the new **`debug_crash.sh`** crash-catcher and this repo's `debug_<what>` naming, brought
  up to repo conventions (help text, `--dry-run`, dependency checks, `--mpi`).
- **Stay in Python for `debug_hang.py`** rather than porting it to bash. A bash port is technically
  possible (node discovery, the silence-vs-exit race, multi-node fan-out, and even the NUL-safe
  env-capture/replay trick all have bash equivalents), but the script's real complexity is the
  *orchestration* around rocgdb (concurrent per-node dispatch, a monitor loop, careful env replay),
  which Python's `threading`/`subprocess` handle far more robustly than bash job control — and the
  existing code is already validated on real HLRS hardware. Rewriting it is new, unvalidated code for
  a cosmetic consistency win, since `scripts/` already isn't bash-only in spirit (`postprocess/tools/`
  is entirely Python).

`debug_crash.sh` rides inside the same `mpirun`/`srun` launch line, so per-rank distribution is
already handled by the MPI launcher itself — it doesn't need `debug_hang.py`'s multi-node fan-out
machinery, and stays a plain bash script like every other launcher.

This is a new, distinct phase of work (not part of the `3.x` trace-postprocessing family).

## Phase 1 — Adopt `hangwatch.py` as `scripts/debug_hang.py`

Copy `hangwatch.py` to `scripts/debug_hang.py` (leave the colleague's original in
`Porting_Adventure/hangwatch-backtrace-kill/` untouched — it's outside this repo and not mine to
move/delete). Keep its CLI shape (`wrap` vs `--log` modes, `collect` subcommand) and all existing
orchestration logic (scheduler detection, node fan-out via `pbsdsh`/`srun --overlap`, the
env-capture-and-replay trick in `dump_env`/`load_env`/`backtrace`) — this is an adoption pass, not a
rewrite.

Changes to bring it up to `CLAUDE.md`'s conventions:

- **Rename** `hangwatch` → `debug_hang` throughout (file name, `prog=`, internal `log()` prefix,
  the `hangwatch-<job>-<ts>` default output-dir pattern, the `hangwatch-<pid>.log` default log
  name, the `hangwatch collect` sub-dispatch routing in `main()`).
- **`--mpi "<launch cmd>"`**, matching every other `scripts/` launcher exactly instead of requiring
  the MPI launcher baked into the trailing command: `debug_hang.py --mpi "mpirun -n 8 --ppn 4"
  --timeout 300 -- ./app` instead of `-- mpirun -n 8 --ppn 4 ./app`. Parse with `shlex.split()`
  (Python equivalent of the bash scripts' `read -ra MPI_ARR <<< "$MPI_STR"`) and prepend it to
  `args.command` before `subprocess.Popen(...)` in `watch()`. No effect on `--log`-only mode (no
  command is launched there).
- **Help text**: `CLAUDE.md` requires every `scripts/` tool's `-h`/`--help` to lead with a ~10-15
  line jargon-free explanation ending in a line naming the underlying AMD tool + a doc link. Split
  the current `description=__doc__` (used verbatim for both the module docstring and the argparse
  description) into two: keep a technical module docstring for maintainers, and add a new
  `HELP_BLURB` constant (matching the pattern in `postprocess/tools/extract_calltree.py:56`) passed
  as `description=HELP_BLURB` with `formatter_class=argparse.RawDescriptionHelpFormatter` (already
  used). End it with: "Under the hood, this uses AMD's rocgdb — see
  https://rocm.docs.amd.com/projects/ROCgdb/en/latest/ for details."
- **Explicit dependency checks at startup** (matching `scripts/profile_CPU_hotspots.sh:140`'s
  `command -v rocprof-sys-sample` pattern): always check `rocgdb` is on `PATH`; additionally check
  `pbsdsh`/`srun` only when the *detected* scheduler is `pbs`/`slurm` respectively — under
  `detect_scheduler()`'s existing `"local"` fallback (no `PBS_JOBID`/`SLURM_JOB_ID`, no
  `qdel`/`scancel` on `PATH`) `dispatch()` already runs `collect()` directly with no fan-out tool
  needed, so a single-rank/no-scheduler run must not be blocked on `pbsdsh`/`srun` being installed.
  Fail with a clear message before any background thread/monitoring starts rather than deep inside
  `collect()`.
- **`--dry-run` flag**, matching every other `scripts/` launcher's contract: prints the detected
  scheduler, job id, node list, the resolved command that would be launched (`--mpi` prefix +
  trailing command, wrap mode) or the log path being watched, and the output directory — without
  starting the watch loop, launching the command, or creating the output directory.
- `os.makedirs(args.outdir, exist_ok=True)` (in `watch()`, only once a hang is actually detected) is
  already correctly placed — no `mkdir`-timing change needed here, unlike the bash scripts' earlier
  fix.

**Verify**: `python3 scripts/debug_hang.py -h` reads clearly and ends with the rocgdb link;
`python3 scripts/debug_hang.py --dry-run --mpi "mpirun -np 4" -- ./some_app` prints its plan and
exits 0 without creating any directory or launching anything; `python3 scripts/debug_hang.py
--dry-run -- ./some_app` (no `--mpi`, single rank, no scheduler present) resolves `scheduler=local`
and does **not** demand `pbsdsh`/`srun`; missing-`rocgdb` produces a clear one-line error
(temporarily rename/hide the binary on `PATH` to confirm, or mock `shutil.which`).

## Phase 2 — New crash-catcher: `scripts/debug_crash.sh`

New bash script, structured like `scripts/profile_CPU_hotspots.sh` (`usage()` heredoc,
arg-parsing loop, `--dry-run` early exit, `mkdir -p` right after it, dependency check, `set -euo
pipefail`), reusing the same `--mpi "<launch cmd>"` convention as every other launcher.

Core command per rank:
```
rocgdb -q --batch -nx -ex "set pagination off" -ex run -ex "thread apply all bt" -ex quit --args <cmd>
```
`run` blocks until the process stops (clean exit or a fatal signal, which gdb intercepts by
default); the batch commands then fire and gdb exits. Non-MPI case writes straight to
`$OUTPUT_DIR/backtrace.txt`. MPI case needs each rank to resolve its own identity and output path at
its *own* runtime (not the launcher's), so the gdb invocation is wrapped in `bash -c '...'` executed
by each spawned rank, resolving rank via `${OMPI_COMM_WORLD_RANK:-${PMI_RANK:-${PMIX_RANK:-${SLURM_PROCID:-$$}}}}`
(OpenMPI / MPICH-PMI / Cray PMIx / Slurm, falling back to PID) and writing
`$OUTPUT_DIR/rank_<id>.bt`.

Help text: same jargon-free-intro + rocgdb-link requirement as Phase 1, explicitly stating this
replaces a normal run for one debug session — meant for catching a reproducible crash, not for
performance data (every rank is wrapped in gdb from process start, unlike the profiling launchers).

**Verify**: `bash -n scripts/debug_crash.sh`; `--dry-run` **without** `--mpi` (single rank, the
default/simple path) resolves the plain `rocgdb ... --args <cmd> > backtrace.txt` form with no
`bash -c`/rank-resolution wrapper; `--dry-run --mpi "mpirun -np 4"` resolves the per-rank wrapped
form instead; neither creates the output dir; missing-`rocgdb` produces the same clear-error pattern
as Phase 1. Full end-to-end behavior (does gdb actually catch the signal, does
the per-rank file land where expected) can only be confirmed by the user on real HPC hardware with
`rocgdb` installed, per `CLAUDE.md`'s environment-constraints note — say so plainly, don't claim more.

- `README.md`: new `## Debugging crashes and hangs` section (after `## Trace-based tools` /

  tools: `debug_crash.sh` usage (plain + `--mpi`), and `debug_hang.py` usage distilled from the
  colleague's real PBS example, adapted to the new `--mpi` convention — `python3 scripts/debug_hang.py
  --mpi "mpirun -n 8 --ppn 4" --timeout 300 -- ./app` — plus the note about the env-matching
  requirement being handled automatically.

  used by this tool family, alongside the existing `profile_<what>`/`extract_<what>` sentence.
- `docs/plans/4.1-rocgdb-crash-hang-debugging.md`: this plan's full verbatim text, written after
  approval per the existing plan-documentation convention.

## Phase 4 — Lightweight tests

- New `scripts/tests/test_debug_hang.py` (plain `unittest`, top-of-file docstring per `CLAUDE.md`'s
  comment policy): cover the pure-logic pieces that don't need real HPC hardware — `pbs_node_indices()`
  (dedup/index-mapping against a fake `PBS_NODEFILE`), `load_env()` (NUL-separated round-trip),
  `detect_scheduler()` (via monkeypatched env vars / `shutil.which`), and CLI parsing edge cases
  (`--timeout`, `--mpi` prefixing, the leading `--` stripped from `command`). Explicitly out of
  scope: anything needing `rocgdb`/`rocm-smi`/`pbsdsh`/`srun`, consistent with this environment's
  constraints.
- `bash -n scripts/debug_crash.sh` (already covered by Phase 2's own verification) is the only check
  available for the new bash script — no existing `scripts/*.sh` has a unittest-style suite, so none
  is introduced here either.

**Verify**: `python3 -m unittest scripts.tests.test_debug_hang -v` (or run from `scripts/` per
whatever import convention matches `postprocess/tests`) → `OK`.
