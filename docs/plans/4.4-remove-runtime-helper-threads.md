# Plan 4.4: remove runtime helper threads (RPC server loop) from the sampling views

Branch: `fix-runtime-helper-threads` (from `master` at `dad8888`, 4.x line — a bugfix on top of 4.3).

## Context

A real OpenMP-offload run (ROCm, LLVM `libomptarget` AMDGPU plugin) contains a second OS thread per
rank, the OpenMP-offload **RPC server thread**:

```
start_thread
 └─ std::pair<...>                       (mis-resolved wrapper frames above the loop)
     └─ std::pair<...>
         └─ std::error_code::default_error_condition
             └─ llvm::omp::target::RPCServerTy::ServerThread::run
                 └─ rocr::HSA::hsa_signal_wait_scacquire
                     └─ rocr::core::InterruptSignal::WaitAcquire
                         └─ ___restore_rt            (sampler signal handler, folded by plan 4.2)
```

It lives for the whole run (~335 s of a ~338 s rank) and only waits on a signal for GPU-initiated
host requests: it is **not on the critical path**. Measured with `extract_frame_callers.py` on the
real profile: thread 1 spends 263.7 of 320.2 s of CPU time (82%) in `InterruptSignal::Wait*` under
`ServerThread::run`; the main thread (thread 0) spends 65% of its time waiting under
`AMDGPUStreamTy::synchronize`, which is real GPU wait and stays untouched.

Today the helper thread's rows land in the CPU-hotspot and call-tree views:
- the `rocr::`/`llvm::` rows are tagged `gpu_api` (so they inflate the GPU-API table),
- the generic wrapper frames (`std::pair<...>`, `std::error_code::default_error_condition`) carry
  no `gpu_api` tag and rank as CPU hotspots; filtering them by name is not an option because a
  `std::map` insert is legitimately labelled `std::pair<std::_Rb_tree_iterator<...>, bool>` and a
  blanket pattern once emptied a whole report (plan 4.2).

The fix is structural, not by name: a thread whose own chain runs a known runtime **server loop** is
a helper thread; the whole thread subtree is removed from the sampling views and reported in a note
instead.

## Design

1. **New tag `runtime_helper_loop`** in `postprocess/stage6/default_noise_patterns.json`:
   `{"substrings": ["rpcserverty::serverthread::run"], "descendant_for_thread_roots": true}`.
   Only the RPC server loop is bundled. `Runtime::AsyncEventsLoop` is deliberately *not* included: it
   executes real async handlers and is already counted as GPU-API overhead; users can add it (or any
   other loop) through `--extra-noise-config` (`add` substrings) or switch the whole mechanism off
   with `disable`.

2. **New tag-definition key `descendant_for_thread_roots`** in `tag_rows()`
   (`stage3_rocprofsys_common.py`). For every row whose own label matches the tag, walk up through
   parents while the parent is in the same `thread_id` and the row is not a thread root, and tag the
   top of that same-thread chain. That top row is a thread root (`is_thread_root`) or an untethered
   root (`parent is None`), i.e. the thread's own entry point (`start_thread`). Guards:
   - never tag a chain whose `thread_id` equals the file's first row's `thread_id` (the main thread),
   - never cross into a different `thread_id`,
   so a profile that reports every thread under one thread id (so threads are indistinguishable)
   is left untouched instead of flagging the main tree.
   Tagging only the top row is enough: `remove_tagged_subtrees()` already drops a tagged row's whole
   subtree.

3. **Removal** in both sample-pipeline loaders, right after `splice_openmp_runtime()`:
   - `stage4_rocprofsys_sample_flat.scan_ranks()`: `root_sum` is taken first (unchanged), helper
     subtrees are recorded and removed before the noise-drop loop.
   - `stage4_rocprofsys_sample_tree.load_rank_trees()`: removed before the `postprocess` hook so all
     call-tree tools and `extract_hotspot_callers` see the same view.
   A removed subtree is summarised as `{"rank", "label", "loop", "sum"}` (thread entry label, matched
   loop name, inclusive seconds).

4. **Report note.** `scan_ranks()` rank dicts gain `"helper_threads"`; `aggregate()` gains an optional
   `helper_threads_out` list (backwards-compatible with every existing 4-tuple caller) that
   `extract_CPU_hotspots.py` and `build_combined_view()` (→ `extract_hotspots.py`) pass to print
   `helper_thread_note()` (new, in `stage5_table_render.py`): which threads were excluded, their
   total seconds, and that they are runtime waiters off the critical path.

5. **Trace-CSV pipeline untouched** (different data; no evidence of this artifact there). The tag is
   defined only for the sample pipeline's `tag_rows()` call sites; `tag_rows()` with
   `label_key="name"` behaves identically because rows without `thread_id` never get the tag.

## Known limits (documented, not fixed here)

- **Same-thread-id profiles:** when rocprof-sys lists every thread under one thread id, helper threads
  cannot be told apart from the main thread and nothing is removed.
- **Only the bundled loop is recognised.** Other runtime waiter threads (e.g. `AsyncEventsLoop`) keep
  their current handling until real data justifies a rule.
- **The wrapper frames' odd names** (`std::pair<...>`) are not explained; the structural rule makes
  them irrelevant. A helper thread that is *not* idle (the part of its time outside the loop) is
  removed with the rest of the thread.
- Per-thread CPU-clock data (`sampling_cpu_clock-*.txt`) is not used by the hotspot views and is
  unaffected.
