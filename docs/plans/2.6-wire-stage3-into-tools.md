# Plan 2.6: wire stage 3 into CPU hotspots, calltree, calltree_traced (roadmap step 5)

## Context

`docs/plans/2.1-postprocess-consolidation-refactor.md` §12 roadmap step 5 wires the isolated
engine from plan 2.5 into its real consumers: delete each tool's own bespoke noise-classification
functions, replace with `stage3_rocprofsys.tag_rows()` + a small per-tool action map, and migrate
`extract_pop_metrics.py`'s inline MPI check onto the shared tag. This is explicitly **the first
step where report output is allowed to change** — everything through steps 1-4 was a pure
relocation; this one actually swaps the classification logic underneath.

Read all four consumer files in full before planning the wiring precisely (not just plan 2.5's
earlier research, since two of them import directly from `extract_CPU_hotspots.py`). Three real
gaps in the initial approach were caught and corrected before finalizing this plan:

**1. `extract_pop_metrics.py` should consume an already-tagged stage-4 output, not re-derive
classification itself.** `compute_run_metrics()` gets its per-label self-time from
`cpu_tool.aggregate_per_rank()`, which already flattens rows to `{label: float}` — the row/parent
tree `tag_rows()` needs is gone by then. The fix is NOT to give pop_metrics its own bare-string
matching path (a second, independent way to ask "is this MPI?") — it's to make `scan_ranks()`
(which already calls `tag_rows()` on the real tree) carry the `mpi_territory` tag forward on its
per-row output, the same way it already carries `gpu`. `extract_pop_metrics.py` already has a
precedent for this exact shape: `gpu_sync_wait_per_rank()` calls `cpu_tool.scan_ranks()` directly
because `aggregate_per_rank()` throws away the `gpu` tag it needs. A new `mpi_comm_time_per_rank()`
follows the identical pattern for `mpi_territory`.

**2. `GPU_FILE_HINTS` is still just a pattern match against a string — it's the wrong call to carve
it out of the engine as a hard exception.** It matches `roctracer`/`hsa` against the *source file's*
basename instead of the row's label, but that's a difference of *which string*, not a different
kind of operation. The engine gains an optional `filename_substrings` field per tag and an optional
`filename` parameter on `tag_rows()` — when given, it's matched into every row's self-match for any
tag that declares it, exactly like `prefixes`/`substrings`/`suffixes` already are. One shared
matching mechanism for both cases, not two.

**3. `compiler_runtime_noise` gets enabled in CPU hotspots now, not deferred.** §9 already names
this as "a one-line addition to its own action map" once the engine ships — there's no reason to
defer a change we're about to empirically verify anyway. Wire it in and let the real-data diff show
exactly what it does.

Two additional real gaps, found while actually wiring the engine's existing (plan-2.5) design in:

**4. `mpi_territory`'s self-match and ancestor-match need different actions in CPU hotspots, and
`tag_rows()` doesn't expose which one fired.** Today, a real `MPI_Init` row is a normal CPU hotspot
entry — `is_mpi_territory()` is never checked against a row's own label to decide inclusion. Only
`is_runtime_thread_noise()`'s ancestor-only walk (thread-root rows only) drops a row. But
`tag_rows()` merges self + ancestor + first-real-descendant matches into one `row["tags"]` set, so
"is `mpi_territory` in tags" can't tell self-matched `MPI_Init` apart from an ancestor-inherited
noise thread. Fix: `tag_rows()` also sets `row["self_tags"]` (the raw self-match set, computed
before ancestor/first-real-descendant enrichment, including any filename-hint match from #2 above)
— additive, doesn't change any of plan 2.5's 26 passing tests. CPU hotspots' drop condition becomes
`"mpi_territory" in row["tags"] and "mpi_territory" not in row["self_tags"]` — exactly "matched via
an ancestor, not directly," reconstructing `is_runtime_thread_noise()`'s old semantics from the tag
data. Once that resolution happens inside `scan_ranks()`, every row that SURVIVES with
`mpi_territory` in its tags is guaranteed self-matched (the ancestor-only case was already dropped),
so the new `row["mpi"]` field pop_metrics needs (#1 above) has no such ambiguity to worry about.
(`gpu_api` needs no self/ancestor split: both cases already get the identical action — bucket into
the GPU table, or prune — in every tool today, so merging was always fine for that tag.)

**5. Tag naming is inconsistent and worth fixing now, while every reference is already being
touched.** The 5 tag names use 4 different terminal words with no shared pattern: `gpu_api`,
`wrapper_noise`, `mpi_territory`, `compiler_runtime_noise`, `wrapper_branch_contamination`. One of
these is a real, unjustified inconsistency: `wrapper_branch_contamination` is `wrapper_noise`'s
sibling-group derivative (same source tag, same underlying concept — a wrapper-noise-infested
branch) but reads as unrelated next to it, and the pre-refactor code's own field name for this
exact concept was `wrapper_branch_noise` (see `mark_wrapper_contaminated_branches()`'s docstring in
`extract_CPU_hotspots.py`) — renaming back to `wrapper_branch_noise` fixes the inconsistency *and*
restores continuity with the name this concept already had. `gpu_api` and `mpi_territory`, by
contrast, are kept as-is on purpose, not out of inertia: both name a *domain* a row falls into,
where the row can legitimately be either real, wanted content (an `MPI_Init` call, GPU launch
overhead broken out into its own table) or noise, depending on which tool and which specific match
mechanism fired — calling either one `..._noise` would be actively wrong for the common case where
it isn't. `wrapper_noise`/`compiler_runtime_noise`/`wrapper_branch_noise`, by contrast, name
categories that really are noise in every tool, every time — the shared `_noise` suffix there is
accurate, not just decorative. Net: one rename (`wrapper_branch_contamination` →
`wrapper_branch_noise`), not a mechanical flattening of five names that classify two genuinely
different kinds of things.

**6. The "exactly 2 tracked exceptions" the roadmap promises turn out to be a lower bound, not the
total, once #3 above is also turned on.** `docs/plans/2.1-...md` (~line 1043) confirms finding #1 is
`extract_pop_metrics.py`'s `_f08_`/`_f08ts_` Fortran-shim gap; finding #2 (§9's second "closes
structurally" bullet) is `extract_calltree.py`'s untethered-root first-real-descendant generalizing
from `gpu_api`-only to `mpi_territory` too. Beyond those two, this plan *also* expects real diffs
from: enabling `compiler_runtime_noise` in CPU hotspots (#3), and `default_noise_patterns.json`'s
`gpu_api` pattern list being `extract_calltree.py`'s broader superset (adds `rocprofiler::`,
`cray_acc`, `hiphardwaredevice`, `present_table`, `pluginmanager::`, `devicety::`,
`llvm::omp::target::plugin::` beyond `extract_CPU_hotspots.py`'s narrower
`GPU_API_PREFIXES`/`GPU_COMPILE_NOISE_SUBSTRINGS`, and beyond `extract_calltree_traced.py`'s even
narrower `classify_gpu()`) — now shared by every tool. Real-data verification (below) will show
exactly which of these actually produce a diff in the 6 `test_apps/results/` captures; this plan
documents the true final count precisely rather than forcing it to match "2."

  tag with a `"filename_substrings"` list, `os.path.basename(filename).lower()` is checked against

  file-level fact, true for every row parsed from that file) before the rest of tagging proceeds
  unchanged. Also sets `row["self_tags"] = set(self_match[key])` per row, alongside the existing

**`extract_pop_metrics.py`** — delete `MPI_PREFIXES = cpu_tool.MPI_PREFIXES` (the `cpu_tool` import
itself stays — `aggregate_per_rank()`/`scan_ranks()` are still used). New function, next to
`gpu_sync_wait_per_rank()` and following its exact shape:
```python
def mpi_comm_time_per_rank(cpu_dir):
    """Per-rank self-time sum of every row tagged mpi_territory -- reads the tag scan_ranks()
    already computed on the real row tree, rather than re-deriving MPI classification from a bare
    label string a second time. Can't use aggregate_per_rank() for this, same reason
    gpu_sync_wait_per_rank() can't: it only returns non-GPU rows with the tag already discarded."""
    ranks = cpu_tool.scan_ranks(cpu_dir)
    return [sum(row["self_sum"] for row in r["rows"] if row["mpi"]) for r in ranks]
```
`compute_run_metrics()` replaces its inline
`comm_time = sum(v for label, v in self_totals.items() if label.lower().startswith(MPI_PREFIXES))`
with a single `comm_time_per_rank = mpi_comm_time_per_rank(cpu_dir)` call before the per-rank loop,
then `comm_time = comm_time_per_rank[i]` inside it (closes finding #1 — now also catches the
`_f08_`/`_f08ts_` suffix, since that's part of `mpi_territory`'s own pattern definition). Update the
Caveats footer's `f"...function-name prefix (case-insensitive: {', '.join(MPI_PREFIXES)}) --\n"`
line to read from `TAG_DEFS["mpi_territory"]["prefixes"]` (loaded via
`from stage3_rocprofsys import load_default_patterns`) and mention the Fortran-shim suffix
explicitly, so the report's own text stays accurate about what actually gets classified as
communication now.

## Implementation notes (divergences from the plan above, found during implementation/verification)

**Finding #2 (calltree's untethered-root generalization to `mpi_territory`) was NOT enabled.**
Testing the engine against the real `mpi_spawned_thread_noise` fixture immediately surfaced why:
`mpi_territory`'s `first_real_descendant_skip_tag` mechanism can't distinguish a genuine program
root (`main`, `parent=None`) from an actual untethered thread-spawn artifact -- both look identical
to the engine. A real `main` whose first traced child happens to be `MPI_Init` (true of nearly every
MPI program) inherited `mpi_territory` from that child and got misclassified. `gpu_api` has this
same theoretical gap but it's never manifested in practice (a real `main`'s first child is
essentially never GPU-API-labeled); `MPI_Init`-as-first-child is near-universal, so the same
mechanism is unsafe to enable for `mpi_territory`. Fixed by removing
`first_real_descendant_skip_tag` from `mpi_territory`'s definition in `default_noise_patterns.json`
-- the engine capability stays generic and tested (`test_stage3_rocprofsys.py`), just not turned on
for this tag. A new test, `test_real_root_with_matching_first_child_is_a_known_limitation`,
documents the limitation directly.

**`structural_drop_tags` isn't cascaded to descendants by `tag_rows()` itself** -- confirmed via the
real `wrapper_contaminated_branch` fixture, which caught this immediately: it's only set on the top
of a contaminated subtree; a flat-list consumer (CPU hotspots) that checked it per-row without
routing rows through `remove_tagged_subtrees()` first only dropped the top row, not its children.
Fixed by having `scan_ranks()` call `remove_tagged_subtrees(rows, {"wrapper_branch_noise"})` before
its per-row loop, matching how the tree-rendering tools already use the same primitive.
`tag_rows()`'s docstring now states this explicitly to prevent the same mistake recurring.

**Two real transcription/design bugs found via real-data diffing, both in `gpu_api`'s pattern list**:
- `__tgt_target_kernel` was dropped when porting `extract_calltree.py`'s `GPU_NOISE_SUBSTRINGS` into
  `default_noise_patterns.json` during plan 2.5 -- a plain copy error, caught by
  `test_extract_calltree.py`'s `test_omp_target_offload_internals_hidden_by_default` failing.
- `GPU_API_PREFIXES` (`hip`, `hsa`, `roctx`, `kfd`, `rocdecode`, `rocjpeg`, `rocr`) were placed in
  the new `"prefixes"` field (`startswith`-only), matching `extract_CPU_hotspots.py`'s original
  strictness -- but `extract_calltree.py`'s `GPU_NOISE_SUBSTRINGS` had *always* matched these same
  strings as substrings anywhere (`"hip" in "launch_hip_kernel"` is true, `"launch_hip_kernel".startswith("hip")`
  is not), and real-data diffing on `profile_hotspots_fortran_amd/calltree.txt` showed a real,
  already-relied-upon wrapper function (`launch_hip_kernel`) losing its GPU classification --
  correctly spliced/pruned before this step, silently un-filtered after. Moved these 7 tokens into
  `"substrings"` instead of `"prefixes"`, restoring `extract_calltree.py`'s exact prior behavior and
  additionally widening `extract_CPU_hotspots.py`/`extract_calltree_traced.py` the same way (part of
  the same GPU-pattern-superset unification, just one more instance of it).

**Test rework was much smaller than estimated.** The master plan's §11 "rework" table listed
`GpuNoiseTierTests`, `RocprofsysWrapperSpliceTests`, `WrapperContaminatedBranchTests`,
`UntetheredThreadRootGpuPropagationTests`, `MpiCollapseTierTests`, `CompilerRuntimeTierTests` in
`test_extract_calltree.py` as needing rework wholesale. Running them against the wired code first
(before touching anything) showed all of them already end-to-end (via `write_report()`/`render()`),
testing observable behavior rather than removed internals -- they needed zero changes. Only one
method in the whole set (`MpiCollapseTierTests.test_open_mpi_prefixes_matched_probably`, which
called the now-deleted `is_mpi_territory()` directly) actually broke; its Open-MPI-prefix and
GOTCHA-template-false-positive coverage moved to a new `OpenMpiPrefixTests` class in
`test_stage3_rocprofsys.py`, checked against the real shipped patterns. Same story in
`test_extract_calltree_traced.py`: only `KdArtifactFilteringTests.test_is_kernel_descriptor_artifact`
broke; its two sibling end-to-end tests needed no changes.
