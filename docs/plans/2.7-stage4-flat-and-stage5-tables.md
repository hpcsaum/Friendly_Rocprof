# Plan 2.7: stage4 flat modules + stage5 table/tree-render modules (roadmap step 6)

## Context

`extract_CPU_hotspots.py`, `extract_GPU_hotspots.py`, and `extract_hotspots.py` still each carry
their own copy of "stage 4" (merge per-rank data into aggregated entries) and "stage 5" (turn
those entries into ranked/selected/formatted tables) logic inline, alongside the CLI/report-writing
"stage 6" code. Roadmap step 6 in `docs/plans/2.1-postprocess-consolidation-refactor.md` §12 calls
for pulling that stage-4/5 logic out into shared modules per §8's target architecture, and for
fixing the nondeterministic tie-order bug in `compute_load_imbalance()`'s sort (found during Plan
2.3's real-data verification: two labels with identical std_dev can print in either order between
runs, since Python's set/dict hashing for strings is randomized per-process) as part of relocating
that function rather than as a separate patch.

Both dependencies for this step are satisfied: Plan 2.3 built `rank_merge_math.py` (renamed to
`stage4_rank_merge_math.py` as part of this plan, see below; `stats_across_ranks()`), and Plan 2.6
finished wiring `stage3_rocprofsys.py` into every tool.

**Decisions made during exploration/review, both confirmed via full reads of every function
involved:**

1. **Both stage-4 flat modules are built this round** — `stage4_rocprofsys_flat.py` (CPU/
   rocprof-sys side, explicitly requested) and `stage4_rocprofv3.py` (GPU/rocprofv3 side, per §8's
   "Stage 4 splits three ways" table) — matching the master plan's target architecture exactly.
2. **Selection and rendering are split into a generic backend, used by every stage-5 table alike.**
   Rather than a hand-written `select_entries`/`format_table` pair per table (CPU hotspots, GPU
   hotspots, fused, load-imbalance, POP metrics), there is ONE generic `select_entries()` (rank +
   threshold-filter + truncate, parameterized by *which field* to rank/filter on — the same
   mechanism serves hotspots-by-%total and load-imbalance-by-coefficient-of-variation, since both
   are just "rank by field X, filter by field Y") and ONE generic `render_table()` (renders a list
   of column specs against a list of entries, with no idea what the entries represent). What
   differs per table — which columns, in what order, which optional sub-metric columns appear — is
   *data* (a column-spec list), not a new function. Adding a column to an existing table becomes
   "add an entry to that table's column list," not "write a new formatting function."
3. **Stage-5 modules get a `stage5_` prefix**, matching the `stage1_`/`stage2_`/`stage3_`/`stage4_`
   naming already used by every other stage module. `rank_merge_math.py` gets a `stage4_` prefix
   too (renamed to `stage4_rank_merge_math.py`) for the same consistency reason, even though it's a
   primitive rather than a full stage module — every other stage-numbered file already has the
   prefix, and there's no reason for this one to be the exception.
4. **Run-metadata guessing helpers stay put**, deferred to a future `run_metadata.py` (§8's stage 6,
   "not yet put to a decision"). `find_extra_artifacts`, `load_metadata`, `find_first_key`,
   `guess_executable`, `guess_run_datetime`, `guess_total_runtime`, `guess_num_ranks`,
   `gather_run_info`, and their constants exist in both `extract_CPU_hotspots.py` and
   `extract_GPU_hotspots.py`. None of them are called by any stage-4/5 function — only by each
   file's own `write_report()` (stage 6). They stay in the two `extract_*_hotspots.py` files
   unchanged; moving them now would be scope creep.
5. **`tree_render.py` gets renamed to `stage5_tree_render.py`**, for the same naming-convention
   reason as point 3, and because rendering an aggregated tree into report-ready text is the same
   stage-5 job as rendering an aggregated table into report-ready text — it was previously grouped
   under §8's stage-6 table, but belongs alongside the other stage-5 renderers. Read in full: it
   already IS the generic-backend/column-spec split this plan applies elsewhere —
   `format_aligned_rows(rows, headers)` is the generic renderer, `REPORT_HEADERS` is the one shared
   column spec `extract_calltree.py` and `extract_calltree_traced.py` both already import and use
   unchanged (confirmed via direct grep — neither file has its own duplicate header/formatting
   logic). This is a pure rename, no functional consolidation needed.
6. **`extract_calltree.py` and `extract_calltree_traced.py` each get their own stage-5 module that
   builds the merged/rendered tree, separate from their stage-6 CLI/report-prose code.** Read both
   files in full: today, each `write_report()` inlines everything from `load_rank_trees()` (parse +
   tag every rank's rows) through predicate/`node_values` construction, `merge_rank_trees()`,
   optional GPU-kernel attachment, and the actual `render_forest()`/`format_aligned_rows()` calls —
   only the header/caveats prose and file I/O around that are genuinely stage 6.
   Within that, the same split applied to the hotspots tables applies here too: the
   GPU-kernel-pairing/attachment/fallback-table block (`_kernel_totals_with_counts`, the
   `aggregate_per_rank`-and-warn pairing logic, and the "unattached kernels" fallback table), the
   main-tree-rendering call (`build_children_map`/`render_forest`/`format_aligned_rows`), and even
   `load_rank_trees()` itself are identical or near-identical between the two tools — confirmed by
   direct comparison — so they become shared functions in `stage5_tree_render.py` (the same file
   being renamed in point 5, which already holds the generic renderer these build on).
   `load_rank_trees()`'s only real differences are which glob pattern is primary vs. fallback
   (`sampling_wall_clock-*.txt`/`wall_clock-*.txt` in one order or the other) and an optional extra
   row-editing step (the sampling tool's conditional wrapper-noise splice; the traced tool has
   none) — both become parameters (`primary_pattern`/`fallback_pattern`, and a `postprocess=None`
   callable hook), the same "generic function, one no-op-by-default hook for the one tool that needs
   something extra" shape as `select_entries()`'s `prepare` parameter. What's genuinely
   irreducible per tool — which prune/collapse predicates its own `--show-*` flags build, and (for
   the sampling tool) the `postprocess` closure's own body — stays in each tool's own
   `stage5_calltree_view.py`/`stage5_calltree_traced_view.py`, which becomes a thin orchestrator
   over the shared functions.

### New file: `postprocess/stage5_table_render.py` — the generic backend

Domain-agnostic infrastructure shared by every stage-5 table module. Two functions:

```python
def select_entries(entries, rank_field, threshold_field=None, top=None, threshold=None,
                    show_all=False, tie_break_field="label", threshold_unit="of total",
                    prepare=None):
    """prepare, if given, is called as prepare(entries) first, for in-place data prep a caller
    needs before ranking (e.g. CPU hotspots' self-vs-inclusive pct_total recompute); GPU and
    load-imbalance callers simply omit it (a no-op). Then sorts entries descending by rank_field
    (ties broken ascending by tie_break_field, for deterministic output regardless of dict/set
    iteration order), then applies exactly one of: show_all (return everything), threshold (keep
    entries where threshold_field >= threshold), or top (default 20). Returns (selected,
    description_string)."""
```

This one function replaces: CPU's `select_entries` (including its `rank_by`-driven `pct_total`
recompute, now the `prepare` callable), GPU's `select_entries`, and the top/threshold/show_all
block that used to be hand-copied inside both `compute_load_imbalance()` bodies. It is also where
**the tie-order fix lives**: the old code did
`sorted(entries, key=lambda e: e["std_dev"], reverse=True)` with no secondary key, so two labels
with identical `std_dev` could print in either order depending on Python's per-process string-hash
randomization. `select_entries()` always sorts by `(-entry[rank_field], entry[tie_break_field])` —
descending primary, ascending secondary, no `reverse=True` (which would also flip the tie-break) —
so every caller gets deterministic output for free, not just load-imbalance tables.

```python
def render_table(columns, entries):
    """columns: list of {"header": str, "width": int|None, "align": "left"|"right" (default
    "right"), "value": callable(entry, index) -> str}. width=None means unpadded (used for the
    trailing name/label column, which is never truncated). Renders one right-aligned header row
    plus one row per entry; knows nothing about what an "entry" represents."""
```

This replaces: CPU's `format_table`, GPU's `format_table`, `format_table_fused`, both copies of
`format_table_load_imbalance`, and the row-rendering half of `extract_pop_metrics.py`'s metrics
table.

### One file per table: `stage5_cpu_hotspots_table.py`, `stage5_gpu_hotspots_table.py`,
### `stage5_load_imbalance_table.py`

One table, one file — easier to open exactly the table you're touching without wading through the

**`postprocess/stage5_cpu_hotspots_table.py`**:
- `CPU_HOTSPOTS_COLUMNS` — column list matching CPU's current 6-column table (`self(s)`/`%total`/
  `total(s)`/`calls`/`%self`/`function`).

Call site (illustrative — exact call sites finalized during implementation). CPU's only genuinely
CPU-specific piece of logic — recomputing `pct_total` against whichever of `self_sum`/`sum`
`rank_by` selects — is passed in as `select_entries()`'s `prepare` callable, rather than living in
its own named/exported function:
```python
key_field = "sum" if rank_by == "inclusive" else "self_sum"
def _set_pct_total(entries):
    for e in entries:
        e["pct_total"] = (e[key_field] / total_runtime * 100.0) if total_runtime > 0 else None
selected, desc = select_entries(entries, rank_field=key_field, threshold_field="pct_total",
                                 prepare=_set_pct_total, ...)
text = render_table(CPU_HOTSPOTS_COLUMNS, selected)
```

**`postprocess/stage5_gpu_hotspots_table.py`**:
- `GPU_HOTSPOTS_COLUMNS` — column list matching GPU's current 5-column table (`total(s)`/`%total`/
  `calls`/`avg(us)`/`kernel`).
```python
selected, desc = select_entries(gpu_entries, rank_field="sum", threshold_field="pct_total", ...)
text = render_table(GPU_HOTSPOTS_COLUMNS, selected)
```

**`postprocess/stage5_load_imbalance_table.py`** (one table, used by both CPU and GPU call sites —
still one file, since it's one table concept):
- `load_imbalance_columns(item_label="function")` — column-list *builder* (the one thing that
  varies between CPU's and GPU's load-imbalance table is the trailing column header text).
- `compute_load_imbalance(per_file_totals, top=None, threshold=None, show_all=False)` — **one
  shared implementation** (was duplicated verbatim between `extract_CPU_hotspots.py` and
  `extract_GPU_hotspots.py` — confirmed byte-identical by direct comparison). Builds the per-label
  `{label, avg, std_dev, min, max, cv_pct}` stats entries, then delegates selection to
  `stage5_table_render.select_entries(entries, rank_field="std_dev", threshold_field="cv_pct",
  tie_break_field="label", threshold_unit="coefficient of variation", ...)` — with no `prepare`
  (load-imbalance entries have nothing to recompute before ranking).
```python
selected, desc = compute_load_imbalance(per_file_totals, top, threshold, show_all)
text = render_table(load_imbalance_columns(item_label="kernel"), selected)
```
Imports (all three files): `select_entries`/`render_table` from `stage5_table_render`;
`stage5_load_imbalance_table.py` also imports `stats_across_ranks` from `stage4_rank_merge_math`.

helpers, so it stays in `extract_CPU_hotspots.py` and `extract_GPU_hotspots.py` respectively (each

Each file's module docstring: stage 5 — this table's column spec (and, for load-imbalance, the
shared CPU+GPU computation); the actual selecting and rendering is generic

### Rename + extend: `postprocess/tree_render.py` → `postprocess/stage5_tree_render.py`

A `git mv` plus import-line updates for the existing functions (no changes to their own code) —
but this file also gains five new functions, moved out of `extract_calltree.py`/
`extract_calltree_traced.py` because they're identical or near-identical between the two tools
(confirmed by direct comparison), the same reasoning as the hotspots-table consolidation elsewhere
in this plan:

- `load_rank_trees(cpu_dir, primary_pattern, fallback_pattern, postprocess=None)` — was each file's
  own `load_rank_trees`, now generalized: `primary_pattern`/`fallback_pattern` are the two glob
  patterns (e.g. `"sampling_wall_clock-*.txt"`/`"wall_clock-*.txt"`, in whichever order a tool
  prefers — a rank's primary-pattern file always wins, the fallback pattern is only used for a rank
  with no primary file at all). After parsing/ancestry-linking/tagging each rank's rows,
  `postprocess(rows)` is called if given, for any further tool-specific row-set editing (the
  sampling tool's conditional wrapper-noise splice); it defaults to `None` (a no-op), which is
  exactly the traced tool's current behavior — the same "generic function, an optional no-op hook"
  shape as `select_entries()`'s `prepare` parameter. `TAG_DEFS = load_default_patterns()` moves
  here too (only used by this function).
- `kernel_totals_with_counts(gpu_dir, rank_index)` (was each file's own `_kernel_totals_with_counts`
  — now public since it's shared). Re-parses one rank's `*_kernel_stats.csv` directly for its
  `Calls` column, since `aggregate_per_rank()` only returns total seconds.
- `pair_gpu_per_rank(gpu_dir, run_dir, rank_keys)` — wraps the `aggregate_per_rank`-and-warn block:
  returns the per-rank GPU kernel total-seconds dicts if `gpu_dir` is given and its rank count
  matches `rank_keys`, else `None` (printing the existing mismatched-rank-count warning, not
  raising, matching current behavior).
- `attach_and_render_gpu_kernels(flat, gpu_per_rank, gpu_dir, rank_keys, is_pruned, node_values)` —
  wraps the "re-derive counts via `kernel_totals_with_counts`, `attach_kernel_summaries`, build the
  `=== GPU kernels ... ===` fallback table" block. Returns fallback text (empty string if
